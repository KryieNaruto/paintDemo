# 审阅门控构建流水线

## 核心原则

任何项目或特性都必须走完「计划 → 审阅 → 执行 → 测试 → 收尾 → 汇报」全流程；两道门（审阅、测试）任一不达标即打回重做，不得跳级进入下一阶段。**违反流程的字面规定即违反其精神。**

## 适用范围与原则

- 本工作流用于**当前工作空间**的**快速验证**类项目，适用于任何工作空间（不绑定特定目录结构）。
- **不回退原则**：计划与实现**不得设计「回退/兜底」路径**（如依赖失败改用替代库、工具缺失改用预编译产物、无头环境降级跳过）。依赖或工具缺失 → **直接补齐并走主路径**，或如实报告阻塞。审阅据此评估：技术可行性/风险与健壮性维度**不因「未提供回退方案」扣分**。
- **审阅门槛 80 分**（加权总分，满分 100）：≥80 放行，<80 打回。
- **CLI + 离屏渲染硬约束**仍强制（见①制定计划）。
- **重新接管已中断的任务时**，第一步先按「进程与内存卫生」查杀遗孤进程，再读取进度继续，不得跳过。

## 流程与门控

```
需求
  │
  ▼
① 制定计划 ──(必须含 CLI 模式 + 离屏渲染输出图像)──▶ 计划文档
  │
  ▼
② 审阅门 ◄──┐   review AGENT 五维加权打分
  │ ≥80 放行 │   <80 → 带反馈打回修订
  ▼          └──(循环直到 ≥80)
③ 执行 ──▶ implement AGENT 拉取/编译/写码
  │
  ▼
④ 测试门 ◄──┐   test AGENT 全用例跑分
  │ 全绿放行 │   任一失败/跳过 → 修复后重测
  ▼          └──(循环直到 0失败0跳过)
⑤ 收尾 ──▶ finish AGENT 清理/文档/git 干净
  │
  ▼
⑥ 汇报 ──▶ 回主会话输出最终结果
```

## 阶段细则

### ① 制定计划
- 先 `superpowers:brainstorming` 澄清需求，再 `superpowers:writing-plans` 产出计划。
- 计划文档落当前工作空间约定的目录（如 `docs/specs/` 与 `docs/plans/`，或 `docs/superpowers/specs/` 与 `docs/superpowers/plans/`）。
- **硬约束（缺失则整份计划直接打回，不进入审阅打分）**：
  1. **CLI 模式**：必须有无头/脚本化入口，可脱离 GUI 交互运行。
  2. **离屏渲染输出图像**：必须能离屏渲染并落盘一张执行图像（如 PNG），供无头验收与 golden 对比。

### ② 审阅门（≥80 分放行）
- 派 `review` AGENT，按其输出契约返回五维得分 + 加权总分 + 逐维度扣分原因。
- 总分 ≥80 → 放行进入执行；<80 → 带反馈打回修订计划，重新审阅，循环至达标。

### ③ 执行
- 派 `implement` AGENT，严格按已通过审阅的计划执行：拉取/编译三方库、写业务代码。不得偏离计划中未经审阅的部分。

### ④ 测试门（100 分放行）
- 派 `test` AGENT 编写并运行测试用例。
- **100 分 = 全用例 0 失败、0 跳过、无回归**。任一失败/跳过 → 打回修复，重测，循环至全绿。

### ⑤ 收尾
- 派 `finish` AGENT：清理临时产物、补文档、确认 `git status` 干净、**按「进程与内存卫生」查杀本工作空间遗孤编译/adb 进程并把清理前后 RSS 记入收尾摘要**、产出收尾摘要。

### ⑥ 汇报
- 回到主会话，汇总：审阅得分、测试结果、变更清单、遗留项，作为最终交付说明。

## 进程与内存卫生（强制，四个触发点必须执行）

**触发时机（命中任一即执行，不得跳过、不得留到"以后再清"）：**

| 触发点 | 时机 |
|---|---|
| 重新接管任务 | 会话被打断（compact/崩溃/人工中断）后再次进入本流水线，**先清理再读进度**，是第一件事 |
| 启用 adb 调试 | 连接/操作真机之前 |
| 触发编译 | 执行任何 cmake/make/ninja/gradle/clang 等构建命令之前 |
| ⑤ 收尾 | finish AGENT 收尾摘要的必报字段之一 |

**只杀与当前工作空间关联的遗孤进程**：判定关联的方法是进程 cwd/命令行包含当前 worktree 绝对路径，或 `ppid=1`（父进程已死，是真孤儿）。**禁止按进程名做无差别全局 `pkill`**（会误杀其它工作空间/其它任务的构建，是破坏性操作，必须控制影响面）。

**标准操作（先查、写入清单、再杀，不得跳过确认直接强杀）：**
```bash
# 1. 定位与本 workspace 关联、或已成孤儿（ppid=1）的编译/adb/模拟器/调试器进程
ps -eo pid,ppid,rss,etime,cmd --sort=-rss \
  | grep -E 'cc1plus|clang|gradle|ninja|cmake|adb|qemu|emulator|gdb|lldb' \
  | grep -F "$(pwd)"

ps -eo pid,ppid,rss,cmd | awk '$2==1' \
  | grep -E 'cc1plus|clang|gradle|ninja|cmake|adb|qemu|emulator'

# 2. 确认后按 pid 精确终止：先 TERM 给进程收尾机会，仍存活再 KILL
kill -TERM <pid>; sleep 2; kill -0 <pid> 2>/dev/null && kill -9 <pid>

# 3. gradle daemon 走官方停止命令，而非直接 kill（避免留下损坏的 daemon 状态文件）
./gradlew --stop

# 4. adb server 若怀疑残留陈旧会话，重启而非强杀
adb kill-server && adb start-server
```

**释放确认**：清理前后各记一次 `ps -eo rss --no-headers | awk '{s+=$1} END{print s/1024/1024" GB"}'`（或 `free -h`）。清理后 RSS 未下降 → 说明识别范围不够，需重新排查，**不得直接宣告清理完成**。

**收尾摘要必报字段**：清理前/后 RSS、被终止的进程列表（pid + cmd）、gradle daemon 是否已 `--stop`、adb server 是否已重启。缺此字段视为收尾未完成。

## 审阅五维评分表

| 维度 | 权重 | 满分要点 |
|---|---|---|
| 架构合理性 | 25% | 模块边界清晰、职责单一、接口解耦、符合 workspace 约定 |
| 需求完整性 | 25% | 需求全覆盖、验收标准可度量、可回溯到需求点 |
| 技术可行性 | 20% | 依赖可拉/可编、API 用法正确、版本兼容、无已知 blocker |
| 可测试性 | 15% | 每模块可独立测试、测试点明确、可注入 |
| 风险与健壮性 | 15% | 风险已识别、有错误处理、边界/异常路径已考虑 |

加权总分 = Σ(维度得分 × 权重)，满分 100，**≥80 通过**，<80 打回。

**评分口径（快速验证项目）**：技术可行性按「主路径能跑通 + 依赖可拉可编」评估；风险与健壮性按「主路径有基本错误处理、阻塞如实报告」评估。**不要求、也不加分于回退/兜底方案设计**。

## AGENT 输出契约

### review AGENT（审阅结果）
```
## 审阅结果
总分：{加权总分}/100 → 通过 / 打回
| 维度 | 权重 | 得分 | 扣分原因 |
| 架构合理性 | 25% | {x} | {原因} |
| 需求完整性 | 25% | {x} | {原因} |
| 技术可行性 | 20% | {x} | {原因} |
| 可测试性   | 15% | {x} | {原因} |
| 风险与健壮性 | 15% | {x} | {原因} |
[打回时] 修改建议：{逐条可执行}
```

### test AGENT（测试结果）
```
## 测试结果
用例 {通过}/{总数}，失败 {n}，跳过 {n}
结果：100 分（全绿）通过 / 打回
[打回时] 失败用例 + 修复建议
```

## 常见借口（红旗）

| 借口 | 事实 |
|---|---|
| 「计划明显没问题，跳过审阅」 | 审阅门是硬门，跳过即违规 |
| 「测试 90% 通过够用了」 | 测试门只有 100 分，任一失败即打回 |
| 「这项目不需要 CLI/离屏」 | CLI + 离屏是全局硬约束，无例外 |
| 「直接实现更快」 | 未经审阅的执行作废重来 |
| 「先做兜底方案更稳」 | 本工作空间是快速验证项目，不做回退；缺失即补齐或报阻塞 |
| 「差 1 分（79）也算过」 | <80 就是打回，无四舍五入 |
| 「先接着干，遗孤进程回头再清」 | 遗孤进程不会自己退出，拖到收尾时往往已吃满数十 GB RSS；重新接管的第一步就是清理，不是收尾时才做 |

## 常见错误
- 描述里省略「CLI + 离屏」硬约束 → 计划直接打回。
- 审阅只给总分不给逐维度扣分 → 无法定位问题，重审。
- 测试只报「通过/失败」不报失败用例与修复建议 → 无法闭环修复。
- 执行阶段擅自扩范围 → 超出审阅范围的改动视为未审阅。
- 计划里设计回退/兜底路径（替代库、预编译产物、降级跳过）→ 与快速验证原则冲突，修订移除。
- 重新接管任务/启用 adb 调试/触发编译前不查杀遗孤进程 → 遗孤累积吃满 RSS，多次打断后可拖垮 host，需回头补清理才算收尾完成。
