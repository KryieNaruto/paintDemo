# 审阅门控缺陷修复流水线

## 核心原则

任何 bug 修复都必须走完「问题查找 → 制定计划 → 审阅 → 修复 → 测试 → 收尾 → 汇报」全流程；两道门（审阅、测试）任一不达标即打回重做，不得跳级进入下一阶段。**违反流程的字面规定即违反其精神。**

**先复现，后修复。** 未复现的 bug 不做根因推断，未写回归用例（先红后绿）的修复视为未完成。

## 适用范围与原则

- 本工作流用于**当前工作空间**的**快速验证**类 **bug 修复**，适用于任何工作空间（不绑定特定目录结构）。
- **不回退原则**：修复计划与实现**不得设计「回退/兜底」路径**（依赖失败改用替代库、工具缺失改用预编译产物、无法复现就跳过验证、改用绕过方案掩盖症状）。依赖或工具缺失 → **直接补齐并走主路径**，或如实报告阻塞。审阅据此评估：技术可行性/风险与健壮性维度**不因「未提供回退方案」扣分**。
- **审阅门槛 80 分**（加权总分，满分 100）：≥80 放行，<80 打回。
- **CLI + 离屏渲染硬约束**仍强制（见①问题查找），回归测试必须走无头路径。
- **修复必带回归用例**：凡修复，必配一条先红后绿（TDD）的回归用例，防复发。

## 流程与门控

```
Bug 报告
  │
  ▼
① 问题查找 ──(无头复现 + 根因定位)──▶ 复现报告 + 根因
  │
  ▼
② 制定计划 ──(必须含回归用例设计 + 无头验证)──▶ 计划文档
  │
  ▼
③ 审阅门 ◄──┐   review AGENT 五维加权打分
  │ ≥80 放行 │   <80 → 带反馈打回修订
  ▼          └──(循环直到 ≥80)
④ 修复 ──▶ implement AGENT 先红后绿：回归用例→修复→转绿
  │
  ▼
⑤ 测试门 ◄──┐   test AGENT 全用例跑分
  │ 全绿放行 │   任一失败/跳过 → 修复后重测
  ▼          └──(循环直到 0失败0跳过)
⑥ 收尾 ──▶ finish AGENT 清理/文档/git 干净
  │
  ▼
⑦ 汇报 ──▶ 回主会话输出最终结果
```

## 阶段细则

### ① 问题查找（复现 + 根因）
- 先做**最小无头复现**（CLI 单命令或最小用例），确认 bug 稳定可复现，记录输入/输出对照。
- 再定位**根因**：用 `superpowers:systematic-debugging` 排查，二分/最小化/探针，给出实证（不靠猜测）。
- **硬约束（缺失则整份计划直接打回，不进入审阅打分）**：
  1. **CLI 复现入口**：必须能无头复现 bug（一条 CLI 命令或一个最小测试），可脱离 GUI。
  2. **离屏渲染输出图像**：若 bug 涉及渲染/图像，必须能离屏渲染并落盘一张执行图像（如 PNG），供无头验收与前后对比。
- 产出：`复现命令 + 期望/实际输出 + 根因 + 影响面`（哪些调用方共用出错代码路径）。

### ② 制定计划
- 计划文档落当前工作空间约定的计划目录（如 `docs/plans/` 或 `docs/superpowers/plans/`）；规格/根因说明落对应 specs 目录（如 `docs/specs/` 或 `docs/superpowers/specs/`）。
- 计划必须含：根因、修复方案、**回归用例设计（先红后绿步骤）**、影响面核对、验证方式（无头 CLI + 离屏图像，若涉及渲染）。
- **硬约束**：计划若缺「CLI 复现 + 回归用例」两要素（涉及渲染时再加离屏验证），直接打回，不进入审阅打分。

### ③ 审阅门（≥80 分放行）
- 派 `review` AGENT，按其输出契约返回五维得分 + 加权总分 + 逐维度扣分原因。
- 总分 ≥80 → 放行进入修复；<80 → 带反馈打回修订计划，重新审阅，循环至达标。

### ④ 修复（TDD 先红后绿）
- 派 `implement` AGENT，严格按已通过审阅的计划执行：**先加回归用例并确认红（失败）→ 修复代码 → 确认转绿（通过）**。
- 不得偏离计划中未经审阅的部分；不得为让测试通过而绕过根因。

### ⑤ 测试门（100 分放行）
- 派 `test` AGENT 编写并运行测试用例。
- **100 分 = 全用例 0 失败、0 跳过、无回归**，且新增回归用例已确认先红后绿（可查记录）。任一失败/跳过 → 打回修复，重测，循环至全绿。

### ⑥ 收尾
- 派 `finish` AGENT：清理临时诊断产物/探针、补文档、确认 `git status` 干净、核对**用户实际运行的二进制/进程非陈旧**（`pgrep` + 构建时间戳 + debug/release 预设），产出收尾摘要。

### ⑦ 汇报
- 回到主会话，汇总：根因、审阅得分、测试结果（含回归用例先红后绿证据）、变更清单、陈旧二进制核对结果、遗留项，作为最终交付说明。

## 审阅五维评分表（bug 修复版）

| 维度 | 权重 | 满分要点 |
|---|---|---|
| 架构合理性 | 25% | 修复点在正确抽象层、模块边界清晰、接口解耦、不破坏既有约定 |
| 问题覆盖性 | 25% | 根因定位准确、修复覆盖全部受影响路径、验收标准可度量可回溯到 bug 报告 |
| 技术可行性 | 20% | 依赖可拉/可编、API 用法正确、版本兼容、无已知 blocker |
| 可测试性 | 15% | 回归用例可独立复现、先红后绿步骤明确、可无头运行 |
| 风险与健壮性 | 15% | 影响面已核对、有错误处理、边界/异常路径已考虑、不引入新回归 |

加权总分 = Σ(维度得分 × 权重)，满分 100，**≥80 通过**，<80 打回。

**评分口径（快速验证项目）**：技术可行性按「主路径能跑通 + 依赖可拉可编」评估；风险与健壮性按「主路径有基本错误处理、阻塞如实报告」评估。**不要求、也不加分于回退/兜底方案设计**。

## AGENT 输出契约

### review AGENT（审阅结果）
```
## 审阅结果
总分：{加权总分}/100 → 通过 / 打回
| 维度 | 权重 | 得分 | 扣分原因 |
| 架构合理性 | 25% | {x} | {原因} |
| 问题覆盖性 | 25% | {x} | {原因} |
| 技术可行性 | 20% | {x} | {原因} |
| 可测试性   | 15% | {x} | {原因} |
| 风险与健壮性 | 15% | {x} | {原因} |
[打回时] 修改建议：{逐条可执行}
```

### test AGENT（测试结果）
```
## 测试结果
用例 {通过}/{总数}，失败 {n}，跳过 {n}
回归用例：{新增用例名} 先红后绿 {已确认/未确认}
结果：100 分（全绿）通过 / 打回
[打回时] 失败用例 + 修复建议
```

## 常见借口（红旗）

| 借口 | 事实 |
|---|---|
| 「bug 明显，不用复现直接改」 | 未复现的修复不作数，①先复现是硬约束 |
| 「改动很小，跳过审阅」 | 审阅门是硬门，跳过即违规 |
| 「测试 90% 通过够用了」 | 测试门只有 100 分，任一失败即打回 |
| 「这 bug 不需要 CLI/离屏验证」 | CLI 复现 + 离屏验证是全局硬约束，无例外 |
| 「先直接修更快」 | 未经审阅的执行作废重来 |
| 「加个绕过/规避处理更稳」 | 本工作空间是快速验证项目，不做回退/掩盖；缺失即补齐或报阻塞 |
| 「没写回归用例，但手动验过」 | 修复必带先红后绿回归用例，手动验证不算数 |
| 「差 1 分（79）也算过」 | <80 就是打回，无四舍五入 |

## 常见错误
- 未复现就猜根因、直接改码 → 修复不可验证，作废重来。
- 描述/计划里省略「CLI 复现 + 回归用例（渲染 bug 再加离屏验证）」硬约束 → 计划直接打回。
- 审阅只给总分不给逐维度扣分 → 无法定位问题，重审。
- 测试只报「通过/失败」不报失败用例与修复建议 → 无法闭环修复。
- 执行阶段擅自扩范围（顺手改无关代码）→ 超出审阅范围的改动视为未审阅。
- 计划里设计回退/兜底路径（替代库、预编译产物、绕过方案）→ 与快速验证原则冲突，修订移除。
- 只验证 release、不核对用户实际跑的二进制/进程（`pgrep` + 构建时间戳）→ 用户仍跑陈旧二进制，视为未交付。
