# 双端性能瓶颈分析报告

> 日期：2026-08-26　范围：PC（Windows, UHD770 集显）与 iPad/平板（XP-Pen MDP1221, Android 14, Mali-G57 MC2, 1440×2160）
> 复现：绘制时 PC 40fps（25ms/帧）、iPad 7fps（143ms/帧）。性能远差于预期，本报告为隔离基准 + 插桩测量的证据链结论。

---

## 1. 结论速览

**帧耗时的真相：GPU 真实只干约 5ms，剩下全部是 CPU 侧同步空泡与全画布搬运。**

| 环节 | 设备端（app 实测） | 占比 |
|---|---|---|
| GPU composite（真实计算） | ~5ms | ~5% |
| CPU 侧 sync 排队 + 空泡 | ~100–170ms | 70%+ |
| 全画布读回（app JNI 路径） | 76–80ms | 60–80% |

三个根因，全部有对照实验与可复现数据：

1. **每个输入点单独 `composite` + `SubmitAndWait`** —— GPU 只做 5ms，sync 排队吃掉 170ms。
2. **每个 dab dispatch 整张画布** —— 10px dab 只需要 ~400px，却派发 12,150 线程，浪费约 30 倍，耗时随画布面积线性增长。
3. **每帧全画布同步读回 + JNI 拷贝链** —— app 80ms vs 纯 SDK 5.85ms；SDK 读回 buffer 是 `HOST_COHERENT`（Mali 非缓存），JNI 每帧 `std::vector`+`NewByteArray`+`SetByteArrayRegion`+GC。

**双端差异**：PC 以 composite 主导（168ms/帧），读回便宜（0.94ms）；设备双因素（composite 同样慢 + 读回 JNI 链路极贵）。

---

## 2. 测量基建

- SDK 三处 `DGCPAIN_PERF` 插桩（ifdef 默认关）：`core/engine.cpp`（render loop composite 计时）、`kernels/brush/brush.cpp`（strokeTo 计时）、`render/vulkan/vk_backend.cpp`（composite/readback 分段计时）。
- `/tmp/bench_perf.cpp`：纯 C-API 隔离基准，`composite / readback / frame` 三模式，frame 模式把 submit/composite/readback 三段分开计时。
- 设备调试：adb 反向 SSH 隧道指向 **adb server**（`ssh -R 5558:127.0.0.1:5037`），正确客户端是 `adb -H localhost -P 5558 devices`，**不是** `adb connect`（那连的是设备 daemon 5555）。
- app 侧测量：`adb shell dumpsys gfxinfo` + `uiautomator dump` + app 浮层（FPS/Frame/Readback ms）。

> ⚠️ 基准计时标签易错位（如 RunFrame 的 readback 段曾误归为 composite）。凡改基准务必 submit/composite/readback 三段分开归属，并用 probe 验证 `dgcFlush` 确实阻塞（120 点后 117ms，正常）。

---

## 3. 根因一：每个输入点单独 composite + SubmitAndWait

### 证据

- `engine.cpp` render thread 对每个输入点调用一次 `backend_->composite(stamps)`（一次 `vkCmdDispatch` 集 + 一次 `vkWaitForFences(UINT64_MAX)`）。
- 隔离基准 `probe_batch.cpp`（同 120 dab）：
  - **1 批（单点 300px 跳跃）**：flush=84ms
  - **120 批（120 点×2.5px）**：flush=171ms
  - 30 批×10px：约 120 dab，同样偏慢
- 结论：sync 开销 ~0.73ms/批（Mali），批量数线性放大；GPU 真实计算只 ~5ms。

### 代码位置

- `core/engine.cpp`（render loop 每输入点 `composite`）
- `render/vulkan/vk_backend.cpp` `CompositeLocked` → `SubmitAndWait()`

### 优化方向

批量 composite：把一批输入点攒够再一次性 `SubmitAndWait`（在 flush / 帧边界提交）。预计 120 点场景从 171ms → 接近 84ms。

---

## 4. 根因二：每个 dab 全画布 dispatch

### 证据

- `vk_backend.cpp` 每 stamp：`vkCmdDispatch(ceil(w/8), ceil(h/8), 1)`，local_size 8×8，即整画布。
- 1080×720 画布 → 每 dab 12,150 线程；10px radius dab 实际只需 ~(10+2×2)² ≈ 400px。
- composite 随画布面积线性增长（对照实验，1080×720 下）：
  - 64² = 4.7ms
  - 540×360 = 50.5ms
  - 1080×720 = 167ms
- 每 dab 成本：~0.7ms（Mali）/ 0.33ms（host UHD770）。

### 代码位置

- `render/vulkan/vk_backend.cpp` `CompositeLocked` 循环内 `vkCmdDispatch(gx, gy, 1)`

### 优化方向

按 stamp 半径计算覆盖矩形，只 dispatch 该区域。对 10px dab 约省 30× 线程数；对大面积 dab 影响小（但正常笔刷 dab 都很小）。

---

## 5. 根因三：每帧全画布同步读回 + JNI 拷贝链

### 证据

- 纯 C-API 读回：host 0.94ms / device 5.85–19ms。
- app 读回：PC 浮层 Readback 数待确认（预计 ~1ms，PC 瓶颈在 composite）；设备 76–80ms。
- SDK 读回 buffer 是 `HOST_COHERENT`：Mali 上非缓存，3.1MB memcpy 实测 8.7ms。
- JNI 每帧：`std::vector<uint8_t> buf(w*h*4)` + `dgcReadbackPixels` + `env->NewByteArray` + `env->SetByteArrayRegion`（3.1MB/帧）+ GC 压力。

### 代码位置

- `render/vulkan/vk_backend.cpp` `ReadbackLocked`（`vkCmdCopyImageToBuffer` + `SubmitAndWait` + HOST_COHERENT memcpy）
- `paint-android/jni/paint_android_jni.cpp` `nativeReadback`

### 优化方向（按杠杆排序）

1. **免读回**：SDK 层 external image 直接上屏，或消费方把 readback 挪出每帧关键路径（只在内容变化时读，或降采样/脏矩形）。
2. **脏矩形读回**：只读回本帧有变化的区域。
3. **HOST_CACHED + invalidate**：把读回 buffer 改成 cached，`vkInvalidateMappedMemoryRanges` 手动失效（Mali coherent = uncached）。
4. **JNI 零分配**：复用 buffer（`ByteBuffer` + `GetDirectBufferAddress`，或池化 `NewByteArray`），消除每帧 vector/数组/GC。

---

## 6. 关键对比与影响排序

| 优化 | PC 收益 | 设备收益 | 改动面 |
|---|---|---|---|
| 批量 composite | 极大（168→~84ms） | 大（sync 减少） | SDK 引擎 |
| 包围盒 dispatch | 极大（面积线性） | 大 | SDK backend |
| 免/脏矩形读回 | 小（读回本就 1ms） | 极大（80ms） | SDK + 消费方 |
| JNI 零分配 | — | 极大（链路 70ms） | 消费方 Android |

PC 主战场是 composite（根因一+二）；设备是三因素叠加。

---

## 7. 优化实施与实测结果（2026-08-27）

### 已落地两项（纯 SDK 侧）

1. **批量 composite**（`core/engine.{h,cpp}`）：渲染线程把多个输入点的 stamp 批攒进 batch，
   在 flush 请求 / 队列排空时合批提交一次（`composited_` 按批内点数递增，屏障语义不变）。
   120 点 flush：170ms → ~14ms（host）/ 5.2ms（Mali）。
2. **dab 包围盒 dispatch**（`render/vulkan/brush_composite.comp` + `vk_backend.cpp`）：
   shader 写范围硬边界 = 圆心 ± radius，每 dab 只 dispatch 覆盖区（8px workgroup 对齐），
   全画布外/画布外的 dab 直接跳过；pipeline/descriptor 绑定提出循环。

### 实测对比（1080×720，`/tmp/bench_perf.cpp`）

| 平台 | composite 前→后 | frame avg 前→后 | frame best |
|---|---|---|---|
| Host UHD770 | 168ms → **9.53ms** (~17×) | ~168ms → **19.05ms** | 8.39ms |
| Mali-G57 | 174ms → **2.42ms** (~72×) | ~174ms → **13.46ms** | 7.50ms |

设备上瓶颈已翻转：composite 从主导（174ms）变廉价（2.4ms），**readback 成为纯 SDK 路径
主要剩余瓶颈**（Mali 上 avg 13.4ms，HOST_COHERENT memcpy ~11ms + JNI 链路 app 内 70ms+）。

### ⚠️ 设备陷阱：不要用 vkCmdDispatchBase

第一版包围盒用 `vkCmdDispatchBase`（Vulkan 1.1 core），**Mali-G57 驱动实测
`gl_GlobalInvocationID` 不含 base workgroup**（非零 base 区域画不到，探针暗像素 bbox 为空）。
已改为 **push-constant `dispatchOffset` + 普通 `vkCmdDispatch`**（纯 1.0 core，全设备一致）。
若未来再引入依赖 dispatch base 的优化，先在设备上跑 probe_bbox 验证。

### 剩余动作（消费方 / 读回专项）

- [ ] 优化 3（消费方）：Android JNI 零分配 + 读回移出每帧（app 内 readback 76-80ms → 纯 SDK 13ms，链路差 ~70ms）
- [ ] 优化 4：读回 buffer 改 HOST_CACHED + invalidate（Mali coherent memcpy 3.1MB ~11ms）
- [ ] PC 浮层确认 Readback 数值，锁定 PC 侧最终归因

测量基建保留：`DGCPAIN_PERF` 插桩 + `/tmp/bench_perf.cpp` / `probe_bbox.cpp` 可双端复用做回归对比。
