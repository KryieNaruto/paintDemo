# 路线 A–E 基础划分 · 中间层分类与复用分析

> **目标**：对 5 条技术路线进行基础划分，找出可共享同一中间层、通过插拔替换的路线组，以及需要额外计划中间层的独立路线。
> **依据**：5 条路线的详细技术方案（A/B/C/D/E） + 评审汇总
> **日期**：2026-08-20

---

## 一、统一架构底座（所有路线共享）

无论选哪条路线，以下层**完全不变**，是项目的可复用基础设施：

```
┌──────────────────────────────────────────────────────────────────┐
│  L6 · UI 层（插拔·编译期选）                                       │
│  Android Pad: Jetpack Compose        PC: ImGui + GLFW             │
└───────────────────────────┬──────────────────────────────────────┘
                            │ 引擎控制 API（设笔刷/颜色/undo）
┌───────────────────────────▼──────────────────────────────────────┐
│  L1 · 引擎核心（完全共享）                                          │
│  engine.h/.cpp（3 线程模型编排）                                    │
│  ring_buffer.h（SPSC 无锁队列）                                     │
│  stroke_predictor.h/.cpp（速度外推预测）                            │
└──────────┬───────────────────────────────────────────┬────────────┘
           │                                           │
┌──────────▼───────────┐                 ┌─────────────▼────────────┐
│  L5 · 绘画内核（插拔）  │                 │  L4 · 渲染后端（插拔）     │
│  IPaintKernel 实现     │                 │  IRenderBackend 实现      │
└───────────────────────┘                 └──────────────────────────┘
           ▲                                           ▲
           └─────────── L3 · 平台层（完全共享）───────────┘
                       IPlatform 实现
                  Android（ANativeWindow）
                  PC（GLFW 窗口）
```

### 共享清单（L0–L3 + L6，所有路线 100% 复用）

| 层 | 内容 | 文件路径 | 说明 |
|----|------|---------|------|
| **L0·类型与接口** | `StrokePoint` / `BrushParams` / `StampData` / `IPaintKernel` / `IRenderBackend` / `IPlatform` | `core/types.h` `core/interfaces/` | 所有路线的契约层，零改动 |
| **L1·引擎核心** | 3 线程模型编排、ring buffer、速度外推预测 | `core/engine.h/.cpp` `core/ring_buffer.h` `core/stroke_predictor.h/.cpp` | 所有路线共享同一引擎编排逻辑 |
| **L2·输入层** | Jetpack Ink 点流（Android）、GLFW 鼠标/数位笔（PC） | `app/.../ink/` `platform/pc/` | 输入点流统一进 `StrokePoint` → ring buffer |
| **L3·平台层** | Android ANativeWindow + JNI、PC GLFW 窗口 | `platform/android/` `platform/pc/` | IPlatform 实现，与渲染后端解耦 |
| **L6·UI 层** | Compose 面板（Android）、ImGui 面板（PC） | `ui/android/` `ui/pc/` | 调用引擎 API，不感知内核/渲染实现 |

> **结论**：L0–L3 + L6 是**一次开发、五路复用**的固定成本。换路线 = 只换 L4 和/或 L5 的目录，中间层不动。

## 二、路线分类：同一中间层 + 插拔替换组

### 组 A/E · CPU dab + Vulkan Compute（最高共享度）

**路线**：A（链接 libmypaint）+ E（白盒移植自研 C++）

```
┌──── L0-L3+L6 完全共享 ────┐
│  engine / 输入 / 平台 / UI  │
└──────────┬────────────────┘
           │ IPaintKernel 接口（签名完全一致：strokeTo → StampData[]）
           │
┌──────────▼──────────┐   ┌────────────────────────┐
│  L5 绘画内核（插拔）   │   │  L4 渲染后端（共享）     │
│  ┌──────────────┐    │   │  render/vulkan/         │
│  │ kernels/mypaint│   │   │  vk_backend             │
│  │ （A: 链接 C 库）│   │   │  vk_canvas              │
│  ├──────────────┤   │   │  vk_composite            │
│  │ kernels/brush │   │   │  brush_composite.comp    │
│  │ （E: 自研 C++）│   │   │  staging buffer 池       │
│  └──────────────┘   │   └────────────────────────┘
└─────────────────────┘
       ▲ CMake 选项切换（DGCPAIN_USE_LIBMYPINT=ON/OFF）
```

**共享的中间层**：L0–L3 + L6 + **L4（render/vulkan/ 完全共享）**

**差异点**：仅 `kernels/` 目录不同

| 维度 | 路线 A（kernels/mypaint/） | 路线 E（kernels/brush/） |
|------|---------------------------|--------------------------|
| 实现方式 | 链接 libmypaint C 库（.a） | 自研 C++，移植算法 |
| 依赖 | json-c、glib shim、config.h vendor | nlohmann/json（header-only） |
| 交叉编译 | 需要（NDK r18b 预编译） | 不需要 |
| GPU 化路径 | 被黑盒挡死 | 可平滑演进到 B |
| 测试方式 | 验证链接成功 + 跑通 stroke_to | host oracle 对照 diff dab 参数 |

**CMake 集成方案**：
```cmake
# 两条路线共享 render/vulkan/，通过 option 切换内核实现
option(DGCPAIN_USE_LIBMYPINT "Use libmypaint C library (Route A, else Route E)" OFF)

if(DGCPAIN_USE_LIBMYPINT)
    add_subdirectory(kernels/mypaint)   # 链接 libmypaint.a
else()
    add_subdirectory(kernels/brush)     # 自研 C++ 内核
endif()
add_subdirectory(render/vulkan)         # 共享，零改动
```

**适用场景**：
- **默认选 E**（自研 C++）：无交叉编译、全可控、可演进到 B
- **A 仅作为对照基准**：host 版 libmypaint 作 oracle，用于 E 的移植正确性 diff 测试
- **A 仅在「有现成预编译产物」时作为捷径**（如从 mypaint_ffi 直接拿 .so）

## 三、需要额外中间层的独立路线

### 路线 B · 全 GPU 笔刷内核（需要 IGpuContext 共享层）

**路线**：B（自研 GPU dab + Vulkan Compute）

```
┌── L0-L3+L6 共享 ──────────────────────────────────┐
│  engine / 输入 / 平台 / UI（大部分复用）            │
└──────────┬────────────────────────────────────────┘
           │
           │  IPaintKernel 语义变化！
           │  strokeTo → StampData[] 不再适用
           │  变为：submitPoints + flushCommands
           │
┌──────────▼────────────────────────────────────────┐
│  ★ 新增中间层：IGpuContext（GPU 共享上下文）         │
│                                                    │
│  ┌──────────────────────────────────────────────┐  │
│  │  IGpuContext 接口                              │  │
│  │  - VkDevice / VkQueue 持有                    │  │
│  │  - Descriptor 池管理                          │  │
│  │  - Command buffer 分配                        │  │
│  │  - 同步原语（fence/semaphore）                  │  │
│  └──────────────────────────────────────────────┘  │
│           ▲                        ▲                │
│           │ 持有                    │ 持有           │
│  ┌────────┴──────────┐  ┌──────────┴────────────┐  │
│  │  L5 绘画内核（GPU） │  │  L4 渲染后端          │  │
│  │  kernels/gpu/      │  │  render/vulkan/      │  │
│  │  dab_generate.comp │  │  brush_composite.comp│  │
│  │  dab_raster.comp   │  │  present             │  │
│  │  （CPU 参数层薄）    │  │  （合成 + 上屏）      │  │
│  └────────────────────┘  └──────────────────────┘  │
└────────────────────────────────────────────────────┘
```

#### 为什么需要额外的中间层？

1. **IPaintKernel 语义变化**：
   - 原接口：`strokeTo(StrokePoint) → std::vector<StampData>`（CPU 物化像素）
   - 路线 B：`submitPoints(StrokePoint[])` + `flushCommands() → GpuBrushCommands`（GPU 生成）
   - 接口签名不兼容，不能直接插拔替换

2. **GPU 上下文共享需求**：
   - 内核（dab_generate / dab_raster）与渲染（composite）在同一 VkDevice 上
   - 需要共享 descriptor 池、command pool、同步原语
   - 原三插拔架构没有「GPU 上下文共享」的接口

3. **线程模型调整**：
   - 原 3 线程：Input → Brush(CPU) → Render(GPU)
   - 路线 B 形态一：Input → Prep(CPU轻量) → Render(GPU)
   - 路线 B 形态二：Input → Render（2 线程）
   - engine 需要支持线程模型切换

#### 需新增的中间层组件

| 组件 | 文件 | 说明 |
|------|------|------|
| **IGpuContext 接口** | `core/interfaces/i_gpu_context.h` | 封装 VkDevice/queue/descriptor 池，供内核和渲染后端共享 |
| **VulkanGpuContext 实现** | `render/vulkan/vk_gpu_context.h/.cpp` | IGpuContext 的 Vulkan 具体实现 |
| **GpuBrushCommands 描述** | `core/types.h` 扩展 | 平台无关的 GPU 命令描述（SSBO 引用 + dispatch 尺寸 + barrier 描述） |
| **线程模型配置** | `core/engine_config.h` | 枚举 3 线程 / 2 线程 / 形态一 / 形态二，engine 按配置启动 |

#### 与组 A/E 的兼容性

```
组 A/E（CPU dab）                    路线 B（GPU dab）
─────────────────                    ─────────────────
engine 3 线程                        engine 2 线程（形态二）
IPaintKernel::strokeTo               IPaintKernel::submitPoints + flushCommands
  → StampData[]                        → GpuBrushCommands
IRenderBackend::composite(StampData)  IRenderBackend::composite(GpuBrushCommands)
  → 自管 VkDevice                       → 共享 IGpuContext
```

**关键结论**：路线 B 不能直接复用组 A/E 的 `engine` 和 `IPaintKernel` 实现，需要：
1. 新增 `IGpuContext` 中间层
2. 修改 `IPaintKernel` 接口（或新增 `IGpuPaintKernel` 子接口）
3. engine 支持线程模型配置
4. `render/vulkan/` 可部分复用（composite shader、present），但需适配 IGpuContext

## 四、中间层复用矩阵

### 4.1 各层复用情况

| 层 | 组件 | A | E | C | D | B |
|----|------|---|---|---|---|---|
| **L0** | `core/types.h` + `core/interfaces/` | ✅ | ✅ | ✅ | ✅ | ⚠️ 需扩展 IPaintKernel + 新增 IGpuContext |
| **L1** | `core/engine` + `ring_buffer` + `predictor` | ✅ | ✅ | ✅ | ✅ | ⚠️ 线程模型需调整 |
| **L2** | Jetpack Ink 输入 + GLFW 输入 | ✅ | ✅ | ✅ | ✅ | ✅ |
| **L3** | `platform/android/` + `platform/pc/` | ✅ | ✅ | ✅ | ✅ | ✅ |
| **L4** | `render/vulkan/` | ✅ | ✅ | ❌ Skia | ❌ bgfx | ✅ 部分复用（需适配 IGpuContext） |
| **L5** | `kernels/` | mypaint | brush | mypaint | brush | gpu（全新） |
| **L6** | `ui/android/` + `ui/pc/` | ✅ | ✅ | ✅ | ✅ | ✅ |

### 4.2 路线分组总结

| 分组 | 路线 | 共享中间层 | 插拔点 | 额外需要 | 切换成本 |
|------|------|-----------|--------|---------|---------|
| **组1** | A ↔ E | L0-L4+L6 全共享 | 仅 L5（kernels/mypaint/ ↔ kernels/brush/） | 无 | **极低**：CMake option 切换内核目录 |
| **组2** | A/C/E → C | L0-L3+L6 共享 | L4（render/vulkan/ → render/skia/）+ L5（固定 mypaint/） | 无 | **低**：只换 render/ 目录 |
| **组3** | E/D → D | L0-L3+L6 共享 | L4（render/vulkan/ → render/bgfx/）+ L5（固定 brush/） | shaderc 编译管线 | **低**：只换 render/ 目录 + 新增 bgfx 依赖 |
| **组4** | E → B | L0-L3+L6 共享 | L4（适配）+ L5（kernels/gpu/ 全新） | **IGpuContext 中间层** + 线程模型调整 + IPaintKernel 扩展 | **高**：需新增中间层组件 |

### 4.3 实施建议

```
开发顺序建议（按复用最大化）：
  1. 先开发 L0-L3+L6 共享底座（三插拔接口 + engine + 输入 + 平台 + UI）
  2. 再开发【组1】的默认实现（路线 E：kernels/brush/ + render/vulkan/）
  3. 组1 的 A 作为对照基准（kernels/mypaint/，host 仅测试用途）
  4. 组2/组3 的 C/D 渲染后端替换，在共享底座就绪后独立开发
  5. 路线 B 的 IGpuContext 中间层和 GPU 内核，在 E 验证手感后启动
```

## 六、关键结论

1. **A 和 E 共享度最高**（连 render/vulkan/ 都一样），通过 CMake 选项切换内核即可。建议默认走 E，A 仅作对照基准。

2. **C 和 D 的 core 层完全共享**，只换渲染后端目录。它们与 A/E 的差异也只是渲染后端——所有 4 条路线的 L0-L3+L6 一致。

3. **路线 B 需要额外的 IGpuContext 中间层**，因为 GPU dab 改变了 IPaintKernel 的语义，且内核与渲染后端需要共享 GPU 上下文。这是**唯一需要额外计划中间层的路线**。

4. **推荐开发路径**：
   - 第一期：共享底座（L0-L3+L6） + 路线 E（kernels/brush/ + render/vulkan/）
   - 第二期：路线 A 作对照测试、路线 C/D 渲染后端替换（可选）
   - 第三期：路线 B 的 IGpuContext 中间层 + GPU 内核（在 E 验证手感后启动）
