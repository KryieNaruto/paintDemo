# 路线 A–E 基础划分 · 中间层分类与复用分析

> **目标**：对 5 条技术路线进行基础划分，找出可共享同一中间层、通过插拔替换的路线组，以及需要额外计划中间层的独立路线。
> **依据**：5 条路线的详细技术方案（A/B/C/D/E） + 评审汇总
> **日期**：2026-08-20

---

## 一、统一架构底座（所有路线共享）

无论选哪条路线，以下层**完全不变**，是项目的可复用基础设施：

```
┌──────────────────────────────────────────────────────────────────┐
│  L6 · UI 层（插拔·编译期选）                                       │
│  Android Pad: Jetpack Compose        PC: ImGui + GLFW             │
└───────────────────────────┬──────────────────────────────────────┘
                            │ 引擎控制 API（设笔刷/颜色/undo）
┌───────────────────────────▼──────────────────────────────────────┐
│  L1 · 引擎核心（完全共享）                                          │
│  engine.h/.cpp（3 线程模型编排）                                    │
│  ring_buffer.h（SPSC 无锁队列）                                     │
│  stroke_predictor.h/.cpp（速度外推预测）                            │
└──────────┬───────────────────────────────────────────┬────────────┘
           │                                           │
┌──────────▼───────────┐                 ┌─────────────▼────────────┐
│  L5 · 绘画内核（插拔）  │                 │  L4 · 渲染后端（插拔）     │
│  IPaintKernel 实现     │                 │  IRenderBackend 实现      │
└───────────────────────┘                 └──────────────────────────┘
           ▲                                           ▲
           └─────────── L3 · 平台层（完全共享）───────────┘
                       IPlatform 实现
                  Android（ANativeWindow）
                  PC（GLFW 窗口）
```

### 共享清单（L0–L3 + L6，所有路线 100% 复用）

| 层 | 内容 | 文件路径 | 说明 |
|----|------|---------|------|
| **L0·类型与接口** | `StrokePoint` / `BrushParams` / `StampData` / `IPaintKernel` / `IRenderBackend` / `IPlatform` | `core/types.h` `core/interfaces/` | 所有路线的契约层，零改动 |
| **L1·引擎核心** | 3 线程模型编排、ring buffer、速度外推预测 | `core/engine.h/.cpp` `core/ring_buffer.h` `core/stroke_predictor.h/.cpp` | 所有路线共享同一引擎编排逻辑 |
| **L2·输入层** | Android MotionEvent 点流 → Ink Stroke Modeler 平滑预测、GLFW 鼠标/数位笔（PC） | `core/stroke_predictor/` `platform/pc/` | 平滑后点流统一进 `StrokePoint` → ring buffer |
| **L3·平台层** | Android ANativeWindow + JNI、PC GLFW 窗口 | `platform/android/` `platform/pc/` | IPlatform 实现，与渲染后端解耦 |
| **L6·UI 层** | Compose 面板（Android）、ImGui 面板（PC） | `ui/android/` `ui/pc/` | 调用引擎 API，不感知内核/渲染实现 |

> **结论**：L0–L3 + L6 是**一次开发、五路复用**的固定成本。换路线 = 只换 L4 和/或 L5 的目录，中间层不动。

## 二、路线分类：同一中间层 + 插拔替换组

### 组 A/E · CPU dab + Vulkan Compute（最高共享度）

**路线**：A（链接 libmypaint）+ E（白盒移植自研 C++）

```
┌──── L0-L3+L6 完全共享 ────┐
│  engine / 输入 / 平台 / UI  │
└──────────┬────────────────┘
           │ IPaintKernel 接口（签名完全一致：strokeTo → StampData[]）
           │
┌──────────▼──────────┐   ┌────────────────────────┐
│  L5 绘画内核（插拔）   │   │  L4 渲染后端（共享）     │
│  ┌──────────────┐    │   │  render/vulkan/         │
│  │ kernels/mypaint│   │   │  vk_backend             │
│  │ （A: 链接 C 库）│   │   │  vk_canvas              │
│  ├──────────────┤   │   │  vk_composite            │
│  │ kernels/brush │   │   │  brush_composite.comp    │
│  │ （E: 自研 C++）│   │   │  staging buffer 池       │
│  └──────────────┘   │   └────────────────────────┘
└─────────────────────┘
       ▲ CMake 选项切换（DGCPAIN_USE_LIBMYPINT=ON/OFF）
```

**共享的中间层**：L0–L3 + L6 + **L4（render/vulkan/ 完全共享）**

**差异点**：仅 `kernels/` 目录不同

| 维度 | 路线 A（kernels/mypaint/） | 路线 E（kernels/brush/） |
|------|---------------------------|--------------------------|
| 实现方式 | 链接 libmypaint C 库（.a） | 自研 C++，移植算法 |
| 依赖 | json-c、glib shim、config.h vendor | nlohmann/json（header-only） |
| 交叉编译 | 需要（NDK r18b 预编译） | 不需要 |
| GPU 化路径 | 被黑盒挡死 | 可平滑演进到 B |
| 测试方式 | 验证链接成功 + 跑通 stroke_to | host oracle 对照 diff dab 参数 |

**CMake 集成方案**：
```cmake
# 两条路线共享 render/vulkan/，通过 option 切换内核实现
option(DGCPAIN_USE_LIBMYPINT "Use libmypaint C library (Route A, else Route E)" OFF)

if(DGCPAIN_USE_LIBMYPINT)
    add_subdirectory(kernels/mypaint)   # 链接 libmypaint.a
else()
    add_subdirectory(kernels/brush)     # 自研 C++ 内核
endif()
add_subdirectory(render/vulkan)         # 共享，零改动
```

**适用场景**：
- **默认选 E**（自研 C++）：无交叉编译、全可控、可演进到 B
- **A 仅作为对照基准**：host 版 libmypaint 作 oracle，用于 E 的移植正确性 diff 测试
- **A 仅在「有现成预编译产物」时作为捷径**（如从 mypaint_ffi 直接拿 .so）

## 三、需要额外中间层的独立路线

### 路线 B · 全 GPU 笔刷内核（需要 IGpuContext 共享层）

**路线**：B（自研 GPU dab + Vulkan Compute）

```
┌── L0-L3+L6 共享 ──────────────────────────────────┐
│  engine / 输入 / 平台 / UI（大部分复用）            │
└──────────┬────────────────────────────────────────┘
           │
           │  IPaintKernel 语义变化！
           │  strokeTo → StampData[] 不再适用
           │  变为：submitPoints + flushCommands
           │
┌──────────▼────────────────────────────────────────┐
│  ★ 新增中间层：IGpuContext（GPU 共享上下文）         │
│                                                    │
│  ┌──────────────────────────────────────────────┐  │
│  │  IGpuContext 接口                              │  │
│  │  - VkDevice / VkQueue 持有                    │  │
│  │  - Descriptor 池管理                          │  │
│  │  - Command buffer 分配                        │  │
│  │  - 同步原语（fence/semaphore）                  │  │
│  └──────────────────────────────────────────────┘  │
│           ▲                        ▲                │
│           │ 持有                    │ 持有           │
│  ┌────────┴──────────┐  ┌──────────┴────────────┐  │
│  │  L5 绘画内核（GPU） │  │  L4 渲染后端          │  │
│  │  kernels/gpu/      │  │  render/vulkan/      │  │
│  │  dab_generate.comp │  │  brush_composite.comp│  │
│  │  dab_raster.comp   │  │  present             │  │
│  │  （CPU 参数层薄）    │  │  （合成 + 上屏）      │  │
│  └────────────────────┘  └──────────────────────┘  │
└────────────────────────────────────────────────────┘
```

#### 为什么需要额外的中间层？

1. **IPaintKernel 语义变化**：
   - 原接口：`strokeTo(StrokePoint) → std::vector<StampData>`（CPU 物化像素）
   - 路线 B：`submitPoints(StrokePoint[])` + `flushCommands() → GpuBrushCommands`（GPU 生成）
   - 接口签名不兼容，不能直接插拔替换

2. **GPU 上下文共享需求**：
   - 内核（dab_generate / dab_raster）与渲染（composite）在同一 VkDevice 上
   - 需要共享 descriptor 池、command pool、同步原语
   - 原三插拔架构没有「GPU 上下文共享」的接口

3. **线程模型调整**：
   - 原 3 线程：Input → Brush(CPU) → Render(GPU)
   - 路线 B 形态一：Input → Prep(CPU轻量) → Render(GPU)
   - 路线 B 形态二：Input → Render（2 线程）
   - engine 需要支持线程模型切换

#### 需新增的中间层组件

| 组件 | 文件 | 说明 |
|------|------|------|
| **IGpuContext 接口** | `core/interfaces/i_gpu_context.h` | 封装 VkDevice/queue/descriptor 池，供内核和渲染后端共享 |
| **VulkanGpuContext 实现** | `render/vulkan/vk_gpu_context.h/.cpp` | IGpuContext 的 Vulkan 具体实现 |
| **GpuBrushCommands 描述** | `core/types.h` 扩展 | 平台无关的 GPU 命令描述（SSBO 引用 + dispatch 尺寸 + barrier 描述） |
| **线程模型配置** | `core/engine_config.h` | 枚举 3 线程 / 2 线程 / 形态一 / 形态二，engine 按配置启动 |

#### 与组 A/E 的兼容性

```
组 A/E（CPU dab）                    路线 B（GPU dab）
─────────────────                    ─────────────────
engine 3 线程                        engine 2 线程（形态二）
IPaintKernel::strokeTo               IPaintKernel::submitPoints + flushCommands
  → StampData[]                        → GpuBrushCommands
IRenderBackend::composite(StampData)  IRenderBackend::composite(GpuBrushCommands)
  → 自管 VkDevice                       → 共享 IGpuContext
```

**关键结论**：路线 B 不能直接复用组 A/E 的 `engine` 和 `IPaintKernel` 实现，需要：
1. 新增 `IGpuContext` 中间层
2. 修改 `IPaintKernel` 接口（或新增 `IGpuPaintKernel` 子接口）
3. engine 支持线程模型配置
4. `render/vulkan/` 可部分复用（composite shader、present），但需适配 IGpuContext

## 四、中间层复用矩阵

### 4.1 各层复用情况

| 层 | 组件 | A | E | C | D | B |
|----|------|---|---|---|---|---|
| **L0** | `core/types.h` + `core/interfaces/` | ✅ | ✅ | ✅ | ✅ | ⚠️ 需扩展 IPaintKernel + 新增 IGpuContext |
| **L1** | `core/engine` + `ring_buffer` + `predictor` | ✅ | ✅ | ✅ | ✅ | ⚠️ 线程模型需调整 |
| **L2** | Stroke Modeler 平滑预测 + GLFW 输入 | ✅ | ✅ | ✅ | ✅ | ✅ |
| **L3** | `platform/android/` + `platform/pc/` | ✅ | ✅ | ✅ | ✅ | ✅ |
| **L4** | `render/vulkan/` | ✅ | ✅ | ❌ Skia | ❌ bgfx | ✅ 部分复用（需适配 IGpuContext） |
| **L5** | `kernels/` | mypaint | brush | mypaint | brush | gpu（全新） |
| **L6** | `ui/android/` + `ui/pc/` | ✅ | ✅ | ✅ | ✅ | ✅ |

### 4.2 路线分组总结

| 分组 | 路线 | 共享中间层 | 插拔点 | 额外需要 | 切换成本 |
|------|------|-----------|--------|---------|---------|
| **组1** | A ↔ E | L0-L4+L6 全共享 | 仅 L5（kernels/mypaint/ ↔ kernels/brush/） | 无 | **极低**：CMake option 切换内核目录 |
| **组2** | A/C/E → C | L0-L3+L6 共享 | L4（render/vulkan/ → render/skia/）+ L5（固定 mypaint/） | 无 | **低**：只换 render/ 目录 |
| **组3** | E/D → D | L0-L3+L6 共享 | L4（render/vulkan/ → render/bgfx/）+ L5（固定 brush/） | shaderc 编译管线 | **低**：只换 render/ 目录 + 新增 bgfx 依赖 |
| **组4** | E → B | L0-L3+L6 共享 | L4（适配）+ L5（kernels/gpu/ 全新） | **IGpuContext 中间层** + 线程模型调整 + IPaintKernel 扩展 | **高**：需新增中间层组件 |

### 4.3 实施建议

```
开发顺序建议（按复用最大化）：
  1. 先开发 L0-L3+L6 共享底座（三插拔接口 + engine + 输入 + 平台 + UI）
  2. 再开发【组1】的默认实现（路线 E：kernels/brush/ + render/vulkan/）
  3. 组1 的 A 作为对照基准（kernels/mypaint/，host 仅测试用途）
  4. 组2/组3 的 C/D 渲染后端替换，在共享底座就绪后独立开发
  5. 路线 B 的 IGpuContext 中间层和 GPU 内核，在 E 验证手感后启动
```

## 六、关键结论

1. **A 和 E 共享度最高**（连 render/vulkan/ 都一样），通过 CMake 选项切换内核即可。建议默认走 E，A 仅作对照基准。

2. **C 和 D 的 core 层完全共享**，只换渲染后端目录。它们与 A/E 的差异也只是渲染后端——所有 4 条路线的 L0-L3+L6 一致。

3. **路线 B 需要额外的 IGpuContext 中间层**，因为 GPU dab 改变了 IPaintKernel 的语义，且内核与渲染后端需要共享 GPU 上下文。这是**唯一需要额外计划中间层的路线**。

4. **推荐开发路径**：
   - 第一期：共享底座（L0-L3+L6） + 路线 E（kernels/brush/ + render/vulkan/）
   - 第二期：路线 A 作对照测试、路线 C/D 渲染后端替换（可选）
   - 第三期：路线 B 的 IGpuContext 中间层 + GPU 内核（在 E 验证手感后启动）

## 七、架构升维：绘画内核 SDK 化 + 跨平台（新增分析）

### 7.1 核心诉求

> 绘画内核（笔刷引擎 + 渲染合成）一套代码跨平台，UI 各平台各做各的。

当前架构中 `kernels/` + `render/` **已经是纯 C++、平台无关**的代码，不依赖任何平台 API。但存在三个问题阻碍它成为真正的跨平台 SDK：

| 问题 | 表现 | 后果 |
|------|------|------|
| **① C++ ABI 不稳定** | UI 层直接调 C++ 虚接口（`IPaintKernel`/`IRenderBackend`） | 跨编译器（MSVC vs GCC vs Clang）name mangling 不同，无法互换 |
| **② 无独立 SDK 产物** | 必须跟 UI 项目同一 CMake 编译 | 不能单独给 iOS(Swift)/Windows(C#) 消费 |
| **③ 输入/平台与内核耦合** | `platform/` + `ui/` 跟 `core/` 在同一编译单元 | 新平台接入必须改仓库内代码，无法黑盒消费 |

### 7.2 目标架构：SDK 化 + 一层 C API 边界

```
┌───────────────────────┐   ┌───────────────────────┐   ┌───────────────────────┐
│  Android UI           │   │  iOS UI               │   │  Windows UI           │
│  Compose              │   │  SwiftUI + PencilKit  │   │  WPF + Pointer Events │
│  ↓ 调 C API           │   │  ↓ 调 C API           │   │  ↓ 调 C API           │
├───────────────────────┴───┴───────────────────────┴───┴───────────────────────┤
│                        dgc_paint SDK（C API 边界）                             │
│                                                                               │
│  ┌─────────────────────────────────────────────────────────────────────────┐  │
│  │  ★ C API 层（sdk_api/）—— 唯一稳定的 ABI 边界，~20 个函数                 │  │
│  │  dgcCreate / dgcDestroy / dgcStrokeTo / dgcRender / dgcSetSurface       │  │
│  │  dgcBeginStroke / dgcEndStroke / dgcCreateBrush / dgcLoadBrushFromMyb   │  │
│  └──────────────────────────┬──────────────────────────────────────────────┘  │
│                             │                                                 │
│  ┌──────────────────────────▼──────────────────────────────────────────────┐  │
│  │  core/ + kernels/ + render/（纯 C++，平台无关，5 路线完全共享）          │  │
│  │  engine → Brush::strokeTo → StampData → Vulkan compute → present         │  │
│  └─────────────────────────────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────────────────────────┘
                         libdgc_paint.so / .a / .dll / .dylib
```

### 7.3 C API 设计（新增的 SDK 边界）

```c
// dgc_paint_c_api.h — 唯一的 SDK 头文件，C 链接，所有平台/编译器兼容

// 生命周期
DgcContext* dgcCreate();
void        dgcDestroy(DgcContext*);

// 画布 Surface（由 UI 层创建并传入原生窗口句柄）
void dgcSetSurface(DgcContext*, void* nativeWindow, int w, int h);
void dgcResize(    DgcContext*, int w, int h);

// 输入（标准化 StrokePoint，UI 层负责捕获+归一化）
void dgcBeginStroke(DgcContext*, float x,float y,float pressure,float tiltX,float tiltY);
void dgcStrokeTo(   DgcContext*, float x,float y,float pressure,float tiltX,float tiltY);
void dgcEndStroke(  DgcContext*);

// 笔刷
DgcBrush dgcCreateBrush(      DgcContext*, const DgcBrushParams*);
DgcBrush dgcLoadBrushFromMyb( DgcContext*, const char* mybJson);
void     dgcDestroyBrush(     DgcContext*, DgcBrush);
void     dgcSetBrush(         DgcContext*, DgcBrush);

// 渲染
void dgcRender(DgcContext*);  // 每帧调一次
void dgcClear( DgcContext*, float r, float g, float b, float a);
```

**为什么是 C API 不是 C++**：C 的 ABI 在所有平台/编译器之间稳定。C++ 的 name mangling / RTTI / 异常处理在不同编译器之间不兼容。C API 可以被任何语言调用——C++ 直接调，Kotlin 通过 JNI，Swift 通过桥接头，C# 通过 P/Invoke。

### 7.4 各路线在 SDK 架构下的映射

所有 5 条路线共享**同一套 C API**，切换路线 = 换 SDK 内部实现，UI 层代码**零改动**：

```
                        ┌──────────────────────┐
                        │  C API（完全不变）     │
                        │  dgc_paint_c_api.h    │
                        └──────┬───────────────┘
                               │ 内部实现切换
          ┌────────────────────┼────────────────────┐
          │ 内核               │ 渲染                │ 路线
          │ kernels/brush/    │ render/vulkan/      │ E（主线，默认）
          │ kernels/mypaint/  │ render/vulkan/      │ A（对照基准）
          │ kernels/gpu/      │ render/vulkan/      │ B（终局形态）
          │ kernels/brush/    │ render/skia/        │ C（备选）
          │ kernels/brush/    │ render/bgfx/        │ D（iOS 储备）
```

| 路线 | 内核实现 | 渲染实现 | C API 层 | UI 层改动 |
|------|---------|---------|---------|----------|
| **E（主线）** | `kernels/brush/` | `render/vulkan/` | 共享 | **零改动** |
| A（对照） | `kernels/mypaint/` | `render/vulkan/` | 共享 | 零改动 |
| B（终局） | `kernels/gpu/` | `render/vulkan/` | 共享 | 零改动 |
| C（备选） | `kernels/brush/` | `render/skia/` | 共享 | 零改动 |
| D（储备） | `kernels/brush/` | `render/bgfx/` | 共享 | 零改动 |

### 7.5 各平台 UI 层职责

UI 层不碰内核、不碰渲染，只做 3 件事：

| 职责 | Android | iOS | Windows | Linux |
|------|---------|-----|---------|-------|
| **(1) 创建窗口表面** | TextureView → `ANativeWindow*` | CAMetalLayer → `void*` | HWND → `void*` | xcb_window → `void*` |
| **(2) 捕获输入归一化** | Android MotionEvent → Ink Stroke Modeler 预测 → `dgcStrokeTo(x,y,p,tilt)` | PencilKit → `dgcStrokeTo` | Pointer events → `dgcStrokeTo` | 事件 → `dgcStrokeTo` |
| **(3) 每帧渲染** | `dgcRender()` | `dgcRender()` | `dgcRender()` | `dgcRender()` |

**UI 层看到的是一个完整的「黑盒画布」**——它不需要知道笔刷引擎怎么算的、渲染后端用的什么 API，它只需要把输入传进去、每帧调一次渲染、把结果贴到窗口上。

### 7.6 对现有架构的改动

| 当前组件 | 改动 | 说明 |
|---------|------|------|
| **新增 `sdk_api/`** | 新增 C API 层 + opaque handle 实现 | 核心改动，~200 行封装 |
| `core/interfaces/` | 保留为内部接口 | 对外不可见，不暴露 C++ ABI |
| `core/engine/` | 不变 | 内部实现 |
| `kernels/` | 不变 | 内部实现 |
| `render/` | 不变 | 内部实现 |
| `platform/` | **删除或瘦身** | 平台职责移给 UI 层，SDK 不再需要 |
| `ui/` | **删除** | UI 各平台自己做，不在 SDK 仓库内 |
| CMake | **改为产出 SDK 库** | `libdgc_paint.so/.a/.dll/.dylib`，独立项目 |

### 7.7 SDK 的跨平台编译（独立 CMake 项目）

```cmake
# SDK 的 CMakeLists.txt（独立项目，不再含 UI/Platform）
cmake_minimum_required(VERSION 3.22)
project(dgc_paint LANGUAGES C CXX)

# 编译产物：libdgc_paint.so / .a / .dll / .dylib
add_library(dgc_paint SHARED
    sdk_api/dgc_paint_c_api.cpp
    core/engine.cpp
    core/ring_buffer.cpp
    core/stroke_predictor.cpp
    kernels/brush/brush.cpp
    kernels/brush/sensors.cpp
    kernels/brush/brush_mapping.cpp
    kernels/brush/brush_settings.cpp
    kernels/brush/rng.cpp
    kernels/brush/myb_parser.cpp
    kernels/brush/brush_kernel.cpp
    render/vulkan/vk_backend.cpp
    render/vulkan/vk_canvas.cpp
    render/vulkan/vk_composite.cpp
)

# 只暴露一个头文件

```

UI 项目通过预编译产物引用 SDK，不参与 SDK 编译：

```kotlin
// Android app/build.gradle.kts
android {
    ndk { abiFilters "arm64-v8a" }
    sourceSets.main.jniLibs.srcDirs = ['libs']
}
// 把 libdgc_paint.so 放进 jniLibs/arm64-v8a/
// Kotlin 通过 JNI 调 C API
```

### 7.8 与现有路线分组的兼容性

```
原分组（L0-L6）               SDK 化的新分层
────────────                  ──────────────
L6 UI 层         → 移出 SDK，各平台独立项目
L5 绘画内核       → SDK 内部实现（kernels/）
L4 渲染后端       → SDK 内部实现（render/）
L3 平台层         → 移出 SDK，合并到 UI 层
L2 输入层         → 移出 SDK，合并到 UI 层
L1 引擎核心       → SDK 内部实现（core/）
L0 类型与接口     → 降级为内部头文件，对外只暴露 C API

新增：sdk_api/    → C API 边界（唯一的外部接口）
```

**关键结论**：SDK 化不是推翻现有架构，而是在现有 L0-L6 分层之上**加一层稳定的 C API 边界**，并把平台/UI/输入职责移出 SDK。路线的插拔替换逻辑（组1-4）完全不变，只是从「CMake option 切换目录」变成「SDK 内部换实现文件」。

### 7.9 实施建议

```
阶段划分：
  第一阶段：先按现有架构（L0-L6+UI+Platform）开发原型，验证技术假设
  第二阶段：在核心稳定后，抽离 sdk_api/ 层，把 platform/ + ui/ 移出
  第三阶段：各平台独立 UI 项目，通过预编译 SDK 集成

理由：
  - 原型阶段快速迭代比 SDK 边界更重要
  - C API 层是纯封装，不改变核心算法，可后期加
  - 等内核/渲染的接口稳定后，C API 的设计才不容易返工
```
