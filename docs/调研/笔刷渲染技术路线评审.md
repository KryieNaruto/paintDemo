# 笔刷 + 渲染技术路线评审

> **阶段**：原型初期设计
> **范围**：仅绘画内核的「笔刷引擎」与「渲染管线」两部分（高优及以上功能）
> **目标**：高扩展、可插拔、模块化内核；性能对标 CSP/Procreate，实际竞品画世界PRO
> **关键约束**：开发全程由 AI 实现（影响复杂度/时间维度的评估权重）
> **日期**：2026-08-20 · v2.0（v1.0 基础上引入「白盒移植折中路线」）

---

## 〇、核心结论（TL;DR）

**推荐路线 E：白盒移植 libmypaint dab 算法 → 自研 C++ 笔刷内核 + Vulkan Compute 合成。**

折中方案（移植 libmypaint 算法而非链接其库）成立，且是当前最优解。三个决定性事实：

| 事实 | 结论 |
|---|---|
| libmypaint 许可证是 **ISC**（非 LGPL/GPL） | 允许直接抄源码进闭源产品，仅需保留版权声明，**无合规风险** |
| glib 依赖可官方去除（`--without-glib`），仅用于随机数 + 少量宏 | 移植时用 `std::mt19937` + `bool` 替换即可，**无交叉编译黑洞** |
| 已有成功先例（hokusai / rustport） | 白盒移植 + `.myb` 兼容已被证明可行 |

加权得分 **4.18**，高于「纯自研 GPU」（4.03）与「链接 libmypaint」（3.33）。

## 一、决策空间拆解

「笔刷 + 渲染」是两个**正交**决策，可独立选择再组合：

| 决策 | 候选 | 说明 |
|---|---|---|
| **① 笔刷 dab 生成** | 链接 libmypaint（CPU） | 成熟引擎，但 glib/json-c 交叉编译黑洞 |
| | **白盒移植 libmypaint（自研 C++）** | ★ 抄算法，去 glib，ISC 许可，无依赖 |
| | 自研 GPU 内核 | compute shader 生成 dab，全 GPU，从零写 |
| **② 渲染合成** | Vulkan Compute | 原生 GPU，性能天花板 |
| | Skia | 成熟 2D 引擎，模型不匹配 stamp 合成 |
| | bgfx | 跨 API 抽象，iOS 红利当前用不上 |

## 二、四维度评审框架

| 维度 | 定义 | 打分方向 |
|---|---|---|
| **复杂度** | AI 实现与维护难度（无黑盒依赖、文档完善、构建简单） | 越高分越**简单** |
| **性能** | 端到端延迟 + 帧率天花板（§3.3：延迟<30ms、合成<2ms） | 越高分越**好** |
| **可控性** | 对算法/像素行为的掌控度，改笔刷/加类型/调底层能力 | 越高分越**可控** |
| **时间** | 从零到「能画 + 手感达标」的落地周期（AI 执行） | 越高分越**快** |

> **权重**：性能 30% · 可控性 25% · 复杂度 25% · 时间 20%。

## 三、候选技术路线

### 路线 E — 白盒移植 libmypaint → 自研 C++ 内核 + Vulkan（★ 推荐）

```
MotionEvent → Jetpack Ink（低延迟点流）
            → 自研 C++ 笔刷内核（移植 mypaint_brush_stroke_to dab 算法，去 glib）
            → Vulkan Compute（premultiplied over 批量合成）→ Compose 上屏
```

- **dab 生成**：把 libmypaint 的 `mypaint_brush_stroke_to()` 核心算法**抄进自己的 C++ 代码**，glib 用 std 替代，ISC 许可允许直接抄
- **合成**：Vulkan Compute（批量 dispatch + 包围盒）
- **优点**：算法成熟（Krita/MyPaint 验证过的手感）；无交叉编译黑洞；代码全掌控可优化；`.myb` 预设兼容
- **风险**：移植正确性（浮点/随机数偏差），需对照测试

### 路线 A — 链接 libmypaint + Vulkan Compute（原规划）

- **dab 生成**：直接链接 libmypaint 库（动态/静态）
- **风险**：glib/json-c 交叉编译是 AI 执行的持续黑盒坑

### 路线 B — 自研 GPU 笔刷内核 + Vulkan（全 GPU）

- **dab 生成 + 合成**：全 GPU compute shader，从零写
- **优点**：性能天花板、全掌控；**缺点**：工作量最大、手感需美术调参

### 路线 C — libmypaint + Skia

- Skia 渲染模型「路径+paint」与「dab stamp」不匹配；最终追求 Vulkan compute 时 Skia 成累赘

### 路线 D — 自研笔刷 + bgfx

- 跨 API 红利（iOS）当前用不上；compute 抽象不如原生

## 四、白盒移植可行性论证（核心）

### 4.1 许可证：ISC，允许直接抄

libmypaint 的 README 明确 `License: ISC`（历史曾为 LGPL，后改为 ISC）。ISC 是极宽松许可，要求仅一条：**保留版权声明与许可证文本**。这意味着：

- ✅ 可直接复制 `mypaint-brush.c` 的代码片段进闭源商业产品
- ✅ 可修改、再分发、闭源，无需开源自身代码
- ❌ 唯一义务：在源码中保留 ISC 版权头

> **对比**：若抄 Krita 的 mypaint 集成代码，则受 GPL-3.0 污染（需整体开源）。**结论：抄 libmypaint（ISC），不抄 Krita（GPL）。** Krita 手册只作算法理解参考，不作代码来源。

### 4.2 glib 依赖：可官方去除，替换成本极低

libmypaint 支持 `--without-glib` 编译。glib 的实际用途（官方文档确认）：

| glib 用途 | std 替代 |
|---|---|
| 随机数 `g_random_double()` / `GRand` | `std::mt19937` + `std::uniform_real_distribution` |
| `gboolean` | `bool` |
| `GList`（笔刷设置列表） | `std::vector` |
| `g_ascii_strtod` / `g_malloc` / `g_assert` | `std::strtod` / `new` / `assert` |

**无 glib 交叉编译问题，因为根本不链接 glib。** 这是「避开交叉编译黑洞」的关键——把外部 C 依赖变成纯 C++ 内部代码。

### 4.3 已有先例（证明可行）

| 项目 | 语言 | 状态 | 说明 |
|---|---|---|---|
| [reearth/hokusai](https://github.com/reearth/hokusai) | Rust | 可用 | 纯 Rust 笔刷引擎，**灵感来自 libmypaint**，`.myb` 兼容，Apache-2.0/MIT |
| [iirelu/rustport](https://github.com/iirelu/rustport) | Rust | 70% | 移植 libmypaint，作者自评「喜欢 bug 才用」 |

两个先例都用不同语言完整复刻了 libmypaint 算法，证明「算法可移植、非黑盒」。

### 4.4 移植范围（MVP 最小集）

**不需要移植全部 ~100 个设置**。MVP（高优及以上功能）只需核心 dab 生成路径：

```
mypaint_brush_stroke_to()  主流程
├── 传感器包（SensorPack）：pressure / speed / tilt 的输入滤波
│   └── speed 的 gamma 滤波、direction_filter
├── dab 数量计算：dabs_per_basic_radius / per_actual_radius / per_second（三设置求和，源码 `res4 = res1+res2+res3`）
├── 核心设置映射（响应曲线）：
│   ├── radius_logarithmic（半径，对数）
│   ├── hardness（边缘软硬）
│   ├── opacity + opaque_multiply + opaque_linearize（压感不透明度）
│   └── spacing（dab 间距）
├── 颜色调制：color_h / color_s / color_v（HSV 随机抖动）
└── dab 形状：圆形 alpha + hardness 边缘 + 纹理 stamp
```

估算核心移植 **~1500–2500 行 C++**，AI 可执行（有 DeepWiki Brush Engine 文档 + Krita 手册 + 原 C 源码对照）。

### 4.5 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 移植正确性（浮点精度/随机数序列偏差） | 中 | 用 libmypaint host 版本跑同样 `stroke_to` 做对照测试，diff dab 输出 |
| 移植工作量（1500–2500 行） | 中 | 只移植 MVP 核心设置；分阶段：先圆形 dab → 再纹理/颜色调制 |
| `.myb` 预设解析（JSON） | 低 | 用 header-only `nlohmann/json`（MIT）替代 json-c，无交叉编译 |

## 五、评审对比矩阵

### 5.1 评分表（5 分制）

| 维度（权重） | **E: 白盒移植+Vulkan** | A: 链接libmypaint+Vulkan | B: 自研GPU+Vulkan | C: libmypaint+Skia | D: 自研+bgfx |
|---|---|---|---|---|---|
| **复杂度**（25%） | 3.5 | 2.5 | 3.5 | 4 | 3 |
| **性能**（30%） | 4.5 | 4.5 | 5 | 4 | 4 |
| **可控性**（25%） | 5 | 3 | 5 | 3 | 4 |
| **时间**（20%） | 3.5 | 3 | 2 | 3.5 | 3 |
| **加权总分** | **4.18** | 3.33 | 4.03 | 3.65 | 3.55 |

### 5.2 评分依据

- **E 复杂度 3.5**：移植代码是 AI 擅长的「写大量清晰代码」，无交叉编译；比 A（2.5 黑洞）高，比 C（4，Skia 零渲染侧编译）略低因需理解 C 算法
- **E 性能 4.5**：同 A（CPU dab + Vulkan 合成）；代码可控，后续可 SIMD/GPU 化逼近 5
- **E 可控性 5**：代码全自研，ISC 允许任意修改，改算法/加类型/调混合全自由
- **E 时间 3.5**：移植 1–2 周，有文档+先例+原码对照，比 A 交叉编译快、比 B 从零快

## 六、结论与推荐

### 6.1 结论：白盒移植（路线 E）为最优，且能平滑演进到全 GPU

**路线 E 在「复杂度、性能、可控性、时间」四维全面占优**，且与用户初步想法（libmypaint 笔刷算法 + Ink + Compose）一脉相承——只是把「链接库」换成「移植算法」，代价相同、收益更大。

### 6.2 演进路径：E → GPU 化 → 全 GPU（B）

```
【首选】路线 E：白盒移植 libmypaint dab 算法 → 自研 C++ 内核（CPU dab）+ Vulkan 合成
        │  验证手感 + 无交叉编译 + 全掌控
        ▼  后续优化（可选）
【终局】把 CPU dab 生成搬到 GPU compute shader → 全 GPU 形态（≈ 路线 B）
        │  性能天花板，对齐画世界PRO shapeTex 模型
        ▼
        因为 dab 算法代码是自己写的（非黑盒），GPU 化是「改自己代码」而非「换依赖」
```

**关键优势**：路线 E 的 dab 算法代码完全自研（ISC 允许改），因此「CPU dab → GPU dab」是一次**平滑的代码演进**，而非「换库」。这正好解决了路线 A 的最大痛点——libmypaint 黑盒无法 GPU 化。

### 6.3 对现有规划与任务线的影响

路线 E 取代路线 A，任务线三处调整：

| 原任务（路线 A） | 调整后（路线 E） |
|---|---|
| T0-2：libmypaint 交叉编译链验证 | **T0-2′：白盒移植 spike** —— 移植核心 `stroke_to` + 去 glib，host 跑通对照测试 |
| T3-1：libmypaint + json-c 交叉编译打包 | **删除**（无需交叉编译，`nlohmann/json` header-only 直接入仓） |
| T3-2：libmypaint 内核（实现 IPaintKernel） | **T3-2′：自研 C++ 笔刷内核**（移植算法，实现 IPaintKernel） |

**收益**：省掉交叉编译打包（T3-1）整个任务 + T0-2 的「编译链验证」变为「算法移植验证」，风险更低、时间更短、可控性更强。

## 附录：AI 执行友好度

「开发全程 AI 实现」重塑了复杂度/时间权重：

| AI 擅长 | AI 不擅长 |
|---|---|
| 写大量结构清晰代码（移植 C→C++、compute shader） | 调试晦涩 C 库交叉编译（glib/config.h） |
| 按既定公式/文档实现（dab 算法有 DeepWiki+Krita 手册） | 处理无文档遗留代码、反复试错构建 |
| 对照测试（跑原版 libmypaint diff 输出） | 主观「手感」调参（需美术人工反馈） |

**推论**：
- **白盒移植恰好落在 AI 最强项**（文档齐全 + 原码对照 + 写清晰 C++），避开最弱项（交叉编译）→ 路线 E 复杂度/时间双优
- libmypaint 的「现成手感」价值（AI 无法替代）被完整保留——算法照抄，非从零
- 后续 GPU 化是「改自己代码」，仍是 AI 强项
