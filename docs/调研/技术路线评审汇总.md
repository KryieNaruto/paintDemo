## 三、各路线一句话结论（agent 独立评审收敛）

- **E（最优）**：把 `mypaint_brush_stroke_to` 逐函数白盒移植成去 glib 的自研 C++，合成走 Vulkan。关键创新——**dab 输出定位为「参数而非位图」**，对照测试 diff「dab 参数序列」而非像素，浮点容差 1e-5 可 CI 自动回归。
- **B（终局）**：画世界PRO 管线平移到 Vulkan Compute，全 GPU。关键决策——**手感参数层先留 CPU、冻结后再搬 GPU**，dab 生成做成可插拔子模块，手感不达标降级 E 只是一次模块切换。性能满分（消除 stamp 生成+上传两道工序，端到端预算 ~10–15ms）。
- **C**：核心矛盾是「模型不匹配」——Skia 是 draw-call 模型，dab stamp 是批量像素 blit，`drawImage` 适配带来三项不可消除 overhead，威胁合成 <2ms。用 0.5 分性能换功能广度红利，适合「不碰 GPU 细节」或快速验证。
- **D**：bgfx 方案清晰但「现在用不上跨 API 红利」。唯一触发点是 iOS/Metal/WebGPU 需求——届时 dab 与合成 `.sc` 无需改动，只加 `--profile metal` 近乎免费获得 iOS 渲染。作为储备，现在不开发。
- **A**：交叉编译黑洞收敛为一次性脚本（NDK r18b 交叉编译 + vendor config.h + 主 app r27+ 只链接），但复杂度+可控性双输被 E 全面压制。残余价值——host 版 libmypaint 作白盒移植的正确性对照基准。

## 四、跨 agent 收敛的关键共识

1. **主线 = E 起点 → B 终局**。E、B 两个 agent 独立得出同一结论，A/C/D 从反面印证（A 输在交叉编译、C 输在模型不匹配、D 输在红利用不上）。
2. **「照抄 libmypaint（ISC 许可）去 glib 移植」是三条路线（E/B/D）共享的技术底座**——dab 算法一次移植，三处复用。
3. **host 版 libmypaint 作对照基准**是移植正确性的关键抓手（E 与 A 都强调）。
4. **可插拔架构让路线切换是「模块切换」而非「重构」**（B 的「dab 可插拔子模块」、D 的「只动 render/bgfx/ 一目录」都印证）。

## 五、最终决策

```
【主线】路线 E：白盒移植 libmypaint dab 算法 → 自研 C++ 内核（CPU dab）+ Vulkan 合成
        │  验证手感 + 无交叉编译 + 全掌控 + 可 CI 回归
        ▼  后续优化
【终局】路线 B：把 dab 生成逐段搬进 compute shader → 全 GPU 形态
        │  性能天花板，对齐画世界PRO，端到端 ~10–15ms
        ▼
        因为 dab 算法代码自研（ISC 可改），GPU 化是「改自己代码」而非「换库」
```

- **A** 降级为「host 对照基准 + 兜底」（仅当能复用 mypaint_ffi 预编译产物时才考虑作为捷径）。
- **C** 作「先跑通、后替换」的临时垫脚石（团队不碰 GPU 细节时）。
- **D** 作「未来 iOS 扩展」储备（iOS/Metal 需求坐实才激活 `render/bgfx/`）。
