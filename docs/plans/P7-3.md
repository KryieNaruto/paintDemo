## 0. 先行代码核验（计划撰写前实读结果）

1. `app/src/main/java/com/dgcamp/paint/ui/PaintScreen.kt:142-173`：帧循环 `LaunchedEffect { while(true) { withFrameNanos { if (dirty) { nativeReadback → copyPixelsFromBuffer → bitmap = bmp; dirty=false } } } }` ——**读回/上屏以 vsync 为节拍**，与 `docs/调研/AD平台手感延迟分析.md` §2 判定一致。
2. `app/src/main/java/com/dgcamp/paint/ui/PaintScreen.kt:138,159`：`val bmp = remember { Bitmap.createBitmap(...) }` 复用单一实例；`bitmap = bmp` **写同一引用**。Compose `mutableStateOf` 默认 `structuralEqualityPolicy`（`==`），Bitmap 未重写 equals → 同引用写入从第二帧起不触发重组 → **Canvas 不重绘**（分析文档 §4 重绘信号疑点）。
3. `app/src/main/java/com/dgcamp/paint/ui/ReadbackScheduler.kt`：类已存在（`onInput`/`onStrokeEnd`/`shouldReadbackNow`/`timeUntilReadableNs`/`version`/`isThrottled`），带 JVM 无头单测 `ReadbackSchedulerTest.kt`，**但 main 下未接线**（`grep ReadbackScheduler app/src/main --include=*.kt` 仅命中类自身文件）。
4. `app/src/main/java/com/dgcamp/paint/MainActivity.kt:27-30`：方案选择注释自认「方案 (c)（读回循环移出 withFrameNanos）只解耦 SDK 读回节奏，不改变 Compose 上屏仍以 vsync 为节拍的现实，对感知帧率无增量」——本计划正是做方案 (c)**并在其上补双缓冲强制重绘 + 主线程减负**，把「增量」从「无」变为「读回即时 + 重绘可靠 + 帧时回落」。

## 1. 目标

把 AD 消费端读回/上屏从 Compose vsync 门控中解耦：接入 `ReadbackScheduler`（输入驱动读回 + 最小间隔节流 + deadline 等待），读回/像素搬运移出 `withFrameNanos` 关键路径，并用**双缓冲交替引用**修复 `bitmap=bmp` 同引用不重绘的问题。净效果：真机连续绘制 Frame 从 20ms（50fps）回到 ≤16.7ms（60Hz），感知延迟从 ~1–2 帧降到 ≤1 帧。

**不承诺**：突破面板物理刷新率（Compose present 仍 vsync，见 §7 不做）。

## 4. 详细设计

### 4.1 接入 `ReadbackScheduler`（替换 `dirty` 门控）

`PaintScreen.kt` 手势回调与读回循环的契约替换：

```kotlin
// 手势回调：不再是「置 dirty」，而是「申请读回」
val scheduler = remember { ReadbackScheduler() }

onDragStart = { offset ->
    strokeActive = true
    scheduler.onInput()
    // ...坐标映射 + nativeStrokeBegin 不变
}
onDrag = { change, _ ->
    change.consume()
    strokeActive = true
    scheduler.onInput()
    // ...坐标映射 + nativeStrokeTo 不变
}
onDragEnd = {
    strokeActive = false
    scheduler.onStrokeEnd()          // 抬笔：排空后补一次最终读回
    ctx.nativeStrokeEnd()
}
onDragCancel = { onDragEnd 同语义 }
```

语义对齐 `ReadbackSchedulerTest.kt:29`（「input triggers immediate readback not gated by vsync」）：`onInput()` 置 pending，`shouldReadbackNow()` 立即为 true（首读回不等 vsync），后续受 `minIntervalNs`（16ms）节流。

### 4.2 读回循环移出 `withFrameNanos`（输入驱动 + deadline 等待）

```kotlin
LaunchedEffect(Unit) {
    while (true) {
        // 有 pending 且到节流期才读回；否则 sleep 到下次可读时刻（deadline，非忙轮询）
        while (!scheduler.shouldReadbackNow()) {
            val waitNs = scheduler.timeUntilReadableNs()
            if (waitNs <= 0) break
            delay(waitNs / 1_000_000)   // delay(millis) 悬浮恢复，主线程空闲
        }
        val rb0 = System.nanoTime()
        val rc = ctx.nativeReadback(rbBuf)
        val rb1 = System.nanoTime()
        readMs = (rb1 - rb0) / 1_000_000f
        if (rc == 0) {
            rbBuf.rewind()
            // 双缓冲：写入「当前未显示」的那块，再以新引用交还 Compose → 必触发重组
            val target = if (bitmap === bmpA) bmpB else bmpA
            target.copyPixelsFromBuffer(rbBuf)
            bitmap = target            // 新引用（交替 A/B），Compose == 判定必不相等 → 重组
            scheduler.onReadbackComplete()
        } else {
            lastError = "readback failed rc=$rc"
            scheduler.onReadbackComplete()   // 清 pending，回循环头重试
        }
    }
}
```

要点：

- **双缓冲**：`val bmpA = remember { Bitmap.createBitmap(cw, ch, ARGB_8888) }; val bmpB = remember { ... }`。`bitmap = target` 每次写的是与当前不同的引用（A↔B 交替），Compose `structuralEqualityPolicy` 判定 `newValue == oldValue` 恒为 false → **每帧必重组、必重绘**。同时消灭「同引用不重绘」病理，且零每帧分配（两块预分配）。
- **readback 不再等 vsync**：读回循环在 `LaunchedEffect`（AndroidUiDispatcher.Main）上跑，但**不受 `withFrameNanos` 节拍约束**——输入到达 → `onInput()` → 循环醒来即读回；`delay()` 只在节流/无 pending 时悬浮，主线程其余时间空闲。
- **`delay` 单位换算**：`timeUntilReadableNs()` 返回 ns；`delay` 接受 Long(millis) 或 Duration。用 `delay(waitNs / 1_000_000L)`（截断到 ms）即可；节流 16ms 场景误差 <1ms 可忽略。
- **读回仍主线程**：`nativeReadback`（0.6ms）+ `copyPixelsFromBuffer`（3.1MB，~1-2ms）仍短暂占主线程，但不再与 vsync 帧同步叠加，且 16ms 节流把频率压在 ≤60Hz。若真机证明主线程仍抖动，见 §4.4 降级方案。

### 4.3 FPS 浮层保留（轻量 ticker）

移除 `dirty` 后的原 `withFrameNanos` 循环不再做读回，仅保留 FPS 计数（D6-3 验收浮层不能丢）：

```kotlin
LaunchedEffect(Unit) {
    var frames = 0; var last = System.nanoTime()
    while (true) {
        withFrameNanos { now ->
            frames++
            if (now - last >= 500_000_000L) {
                fps = frames * 1e9f / (now - last).toFloat()
                frameMs = 1000f / (if (fps > 0f) fps else 1f)
                frames = 0; last = now
            }
        }
    }
}
```

该 ticker 反映**显示刷新节拍**（验收 1 的 Frame 读数来源），与读回循环解耦。

### 4.4 主线程仍抖动的降级方案（仅在真机验证发现时启用）

若 §4.2 读回+copy 在主线程仍造成帧抖动（Frame 持续 >16.7ms）：

- 把 `nativeReadback` + `copyPixelsFromBuffer` 移到后台线程（`withContext(Dispatchers.Default)`），仅在完成后的 `withContext(Dispatchers.Main) { bitmap = target; scheduler.onReadbackComplete() }` 回主线程。
- 前提：`rbBuf`（direct buffer）与 target Bitmap 在后台线程写入是安全的（未上屏的 Bitmap 可跨线程写像素，Android 允许；只要不在后台读 `bitmap` 状态即可）。
- 默认不启用（引入跨线程复杂度），作为真机实测不达标的备选。

### 4.5 新增 JVM 单测（双缓冲交替引用语义）

`app/src/test/java/com/dgcamp/paint/ui/BufferSwapRedrawTest.kt`（纯 Kotlin，不依赖 Android）：

```kotlin
class BufferSwapRedrawTest {
    // 语义模型：Compose state 对「同引用写入」判等不重组；对「交替新引用」必重组。
    // 用两个"引用"对象模拟 A/B 交替，断言状态值永远在 A/B 间切换且永不为同一对象。
    @Test fun `alternating refs never equal current`() {
        val a = Any(); val b = Any()
        var current: Any? = null
        val swaps = mutableListOf<Any>()
        repeat(6) { i ->
            val target = if (current === a) b else a
            // 关键断言：写入前 target 必 ≠ current（否则 Compose == 判定会跳过重组）
            assertNotEquals(current, target)
            current = target
            swaps += target
        }
        // A/B 严格交替
        assertEquals(listOf(a, b, a, b, a, b), swaps)
    }

    @Test fun `same-ref write is no-op by structural equality`() {
        val o = Any()
        val a = mutableListOf(o); val b = mutableListOf(o)
        // 同引用写入：结构相等判定为 true（模型层），不触发"重绘信号"
        assertTrue(b[0] === a[0])
    }
}
```

> 该测试是对「双缓冲=必重组」语义的模型验证（`==` 引用相等在 Compose state 的行为）；真实重组行为依赖 Compose 运行时，以真机验收 2 为准，测试作为回归护栏防未来误改回单缓冲。

## 6. 风险

1. **Compose 重组行为假设**：`bitmap = target` 交替引用是否必然触发 Canvas 重组依赖 Compose 运行时对 `mutableStateOf` 的判等（`==` 引用相等）——本计划 §4.2 双缓冲设计基于该机制，但**未在真机实证前不可视为定论**；真机验收 2 是最终裁定，若重组仍不触发，改用 `ReadbackScheduler.version()` 作为显式重绘状态（`val v by remember { mutableIntStateOf(0) }`，读回后 `v = scheduler.version()`，Canvas 读 `v`）兜底。
2. **后台线程 copy（§4.4）跨线程写 Bitmap**：未上屏 Bitmap 跨线程写像素在 Android 上合法，但需保证 target 未同时被 Compose 读；双缓冲天然保证「当前显示的 buffer 不写」，风险低。仅按需启用。
3. **节流 16ms 与高刷输入**：120Hz 输入下读回被节流到 60Hz，部分输入点合批上屏——present 本身 ~60Hz（Frame 20ms 真机），不劣化；若换高刷真机，可构造 `ReadbackScheduler(minIntervalNs = 8_000_000L)`。
4. **真机人工验收**：验收 1-3 需真机，SDK 仓库沙箱无 GUI/真机；沿用 P7-1/P7-2 惯例，host 自动化（单测）为可验证替代，真机数据由有硬件条件的人工补齐，如实标注。

## 7. 不做

- **不突破面板刷新率**：Compose present 仍 vsync（MainActivity.kt 方案 (b) SurfaceView+GL `eglSwapInterval(0)` 属更大重构，未纳入本任务；本任务完成「读回即时 + 重绘可靠 + 帧时回落」，将感知延迟压到 ≤1 帧）。SurfaceView/GL 上屏留作 P7 线后续独立任务。
- 不改 SDK（`paint-android/sdk/`）任何文件（`dgcReadbackPixels` 契约、快照缓存、engine 攒批均不动）。
- 不改 `MainActivity.kt` 的 `requestMaxRefreshRate` 逻辑。
- 不做 modeler 预测生效（那是 P7-4 的范围，本任务只保证读回/重绘链路即时可靠）。
