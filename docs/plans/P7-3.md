## 1. 目标

把 AD 消费端「读回 + 3.1MB 像素搬运 + 上屏」从 Compose 主线程关键路径彻底移出：

- 读回/像素搬运迁到**单线程后台 dispatcher**（消灭主线程 3.1MB memcpy 与 native 调用 → 30fps 根因）。
- 用**双缓冲（`bmpA`/`bmpB` 交替引用）**承接「写后台缓冲、主线程只做引用交换」的线程安全需求，并天然替代 `frameVersion++` 完成强制重绘（任务线点名的「双缓冲交替引用强制重绘」）。
- 保留并复核既有 `ReadbackScheduler`（输入驱动 + 16ms 节流 + deadline 等待，7db4d5a 已落地），保证读回节拍 ≤60Hz、不劣化。

净效果：真机连续绘制 Frame 从 30fps（主线程被打爆）回到 **≤16.7ms（60Hz）**，感知延迟 ≤1 帧，笔迹实时刷新无滞后。

**不承诺**：突破面板物理刷新率（Compose present 仍 vsync，见 §10）。

## 5. 详细设计

### 5.1 `ReadbackScheduler` 线程安全核对（不改代码，仅确认结论）

拟把重活移到后台线程后，`ReadbackScheduler` 的调用线程分布变为：

- **主线程**：`onInput()`/`onStrokeEnd()`（gesture 回调）、`timeUntilReadableMs()`、`onReadbackComplete()`（worker 的 collect 分支，仍在主线程）。
- **后台线程**：只有 `nativeReadback` + `copyPixelsFromBuffer` 落在这个线程，**完全不触碰 scheduler**。

即 scheduler 的全部状态读写仍收敛在**主线程**（collect 与 gesture 均主线程），后台线程只做纯数据搬运、不读 scheduler。**因此无需给 `ReadbackScheduler` 加锁/改 atomic**，7db4d5a 的实现原样保留。若执行阶段改用「整段循环搬到后台 dispatcher」的替代结构（§5.3 明确不推荐），则必须先把 `pending`/`lastReadNs`/`version` 改为线程安全，故本计划**不采用**该替代结构。

### 5.2 双缓冲 + 读回迁后台线程（`PaintScreen.kt` worker 改造）

```kotlin
// 双缓冲：两块预分配 Bitmap（零每帧分配；2×3.1MB≈6.2MB，可忽略）
val bmpA = remember { Bitmap.createBitmap(cw, ch, Bitmap.Config.ARGB_8888) }
val bmpB = remember { Bitmap.createBitmap(cw, ch, Bitmap.Config.ARGB_8888) }
// 单线程后台 dispatcher：串行化 nativeReadback+copy，避免并发触碰 rbBuf/back 位图。
// limitedParallelism(1) 是 Dispatchers.IO 的视图，无需 close（不泄漏 Executor）。
val readbackDispatcher = remember { Dispatchers.IO.limitedParallelism(1) }

LaunchedEffect(Unit) {
    snapshotFlow { dirty }.collect { isDirty ->
        if (!isDirty) return@collect
        var retry = true
        while (retry) {
            val waitMs = scheduler.timeUntilReadableMs()
            if (waitMs > 0) delay(waitMs)          // 主线程悬浮，非忙轮询
            // 后台缓冲 = 当前未显示的那块；与 Compose 正在绘制的 front 严格隔离
            val back = if (bitmap === bmpA) bmpB else bmpA
            val (rc, ms) = withContext(readbackDispatcher) {
                val rb0 = System.nanoTime()
                val rc = ctx.nativeReadback(rbBuf)         // 后台线程
                val rb1 = System.nanoTime()
                val ms = (rb1 - rb0) / 1_000_000f
                if (rc == 0) {
                    rbBuf.rewind()
                    back.copyPixelsFromBuffer(rbBuf)       // 3.1MB memcpy 移出主线程
                }
                rc to ms
            }
            readMs = ms                                     // 回主线程再写 Compose 状态
            if (rc == 0) {
                bitmap = back                               // 交替新引用 → == 恒不等 → 必重组
                scheduler.onReadbackComplete()
                dirty = false
                retry = false
            } else {
                lastError = "readback failed rc=$rc"
            }
        }
    }
}
```

要点与正确性论证：

- **双缓冲线程安全**：`back` 在**主线程**由 `if (bitmap === bmpA) bmpB else bmpA` 算出（即「当前未显示」那块）；`withContext` 在后台线程写 `back` 像素，写完后 `withContext` 返回（dispatcher 切换建立 happens-before，主线程可见该写）；主线程才 `bitmap = back` 把它翻到 front。任一时刻「正在显示」的 buffer 不被后台线程写，front/back 永不并发触碰，无需锁。
- **交替引用必重组**：`Bitmap` 未重写 `equals`（引用相等），`bitmap` 状态在 `bmpA`↔`bmpB` 间交替写**不同对象**，Compose `mutableStateOf` 默认 `structuralEqualityPolicy` 判 `new==old` 恒为 false → 每读回必重组、必重绘。**`frameVersion` 及其 Canvas 首行读取可删**（冗余，且避免两套重绘信号并存）。首帧 `bitmap==null` → `back=bmpA`，随后严格交替。
- **读回不再占主线程**：主线程每读回周期只剩「算 back + `withContext` 挂起 + 回主线程写 `bitmap`/状态」的极小开销；`nativeReadback`（0.6ms）+ `copyPixelsFromBuffer`（3.1MB）全在后台。
- **`readMs` 语义不变**：仍只量 `nativeReadback` 本身（rb0..rb1，~0.6ms），copy 在 rb1 之后不计入，与现状一致。
- **读回节拍不变**：`scheduler.timeUntilReadableMs()` 仍在主线程 collect 分支，16ms 节流照旧 ≤60Hz → 对 SDK 渲染线程的 `requestFlush` 频率与 7db4d5a 完全相同（见 §7 冲突检查）。
- **`dirty`/`retry` 语义保留**：失败不清 `dirty`/不调 `onReadbackComplete`，回循环头重试，维持 7db4d5a 的「失败重试不吞 pending」语义。

### 5.3 不采用的替代结构（及原因）

把「整个 collect 循环」搬到后台 dispatcher 虽然更彻底，但会迫使 `scheduler` 跨线程读（`shouldReadbackNow`/`onReadbackComplete` 在后台、`onInput` 在主线程）→ 需给 `ReadbackScheduler` 加锁/atomic，破坏其「纯 Kotlin 无锁、JVM 单测友好」现状，且收益为零（主线程重活已被 §5.2 移走）。故不采用。**若真机复测仍显示主线程抖动，优先查 `delay(waitMs)` 是否因 `snapshotFlow` 重发把读回速率推超 60Hz，而非退回整段搬后台。**

## 7. 冲突检查：是否打回/削弱 P7-1/P7-2 的批量 composite、flush 节流去抖收益

结论：**不冲突，不削弱**。逐条对照：

1. **读回节奏未变**：P7-2 在 SDK 侧给 `flush_requested_` 加了 `kMinFlushIntervalMs`（4ms）节流，防「高频 readback 打散批量 composite」。Android 侧 `ReadbackScheduler` 的 16ms 节流把读回频率钉在 ≤60Hz（< 4ms 窗口），本任务**只改执行读回/copy 的线程，不改变读回频率**（16ms 节流逻辑与 7db4d5a 完全一致，仍在主线程 collect 分支判定）。→ `requestFlush` 触发频率不变，批量 composite 的攒批节奏不受影响。
2. **不引入阻塞 flush**：本任务不碰 `nativeFlush`/`dgcFlush`（绘制路径已在 7db4d5a 去掉阻塞 flush；`nativeFlush` 仅 `nativeExportPng`/清空按钮等非每帧路径用），不重新引入 P7-1 之前的「每帧同步 drain」病理。
3. **`copyPixelsFromBuffer` 移后台不改变 SDK 侧任何语义**：copy 是纯 CPU 消费者侧动作，与 SDK 渲染线程/flush 无交互。
4. **一个需点出的边界（非冲突，仅如实标注）**：读回迁后台后，主线程不再因 3.1MB memcpy 掉帧，读回 worker 理论上能比「主线程被打爆」时更精准地贴合 16ms 节拍触发。但这仍是 ≤60Hz 的既有上界，不会突破 P7-2 论证的「读回频率不得高于攒批节拍」约束。若真机出现批量吞吐退化迹象（概率极低），首查是否 `snapshotFlow`/`dirty` 交互导致读回速率异常翻倍（7db4d5a 注释已提到「`if(!isDirty) return@collect` 防冗余读回」这一坑），而非本任务的双缓冲/后台线程本身。

## 10. 风险

1. **主线程抖动是否彻底消除，取决于 `nativeReadback` 是否真的完全脱离主线程关键路径**：`withContext(readbackDispatcher)` 保证 copy/readback 在后台，但主线程仍要做「算 back + 挂起 + 回主线程写 `bitmap`」与 Compose 重组/drawImage 缩放。若真机仍 >16.7ms，需用 systrace 定位主线程剩余热点（可能落在 `drawImage` 缩放而非本任务范围），属新发现，停下报人工，不在本计划内悄悄改上屏链路。
2. **Compose 重组假设**：`bitmap=back` 交替引用是否必然触发 Canvas 重绘依赖 Compose 运行时对 `mutableStateOf` 的 `==` 判等（`Bitmap.equals` 为引用相等，不同实例必不等）。真机验收 3 是最终裁定；若意外不重组，回退方案是保留 `frameVersion`（`ReadbackScheduler.version()` 信号）作为第二重绘信号——本计划删 `frameVersion` 的决策可据此回退，成本极低。
3. **后台线程 JNI/`g_sdk` 并发**：`g_sdk` 是 init 后只读的全局裸指针，`nativeDestroy` 仅 `onDispose` 调用、不与绘制循环并发；`nativeReadback`/`nativeStrokeTo` 并发访问 `g_sdk` 不构成指针竞态（指针值不变），SDK 内部已 mutex/condvar 串行化。风险低，但执行阶段真机压测时应留意无崩溃/无 SIGSEGV。
4. **真机人工验收缺失**：验收 1/2/3 均需真机，沙箱通常无真机。按 §8，任务大概率停在 `need-human`，这是预期流程结果，不是失败；不得用自动化测试豁免。
5. **paint-android 脱离本 worktree 的 git 追踪**：两个仓库物理路径不同，正常操作不混淆，但执行阶段须显式确认本 worktree `git diff` 不含 `paint-android` 路径内容，且 sdk submodule 同步（§9 步骤 0）只发生在 `paint-android` 仓库内。

## 11. 不做

- 不突破面板刷新率（Compose present 仍 vsync；`MainActivity` 方案 (b) SurfaceView+GL `eglSwapInterval(0)` 属更大重构，留作独立任务）。
- 不改 SDK（`paint-android/sdk/`）任何文件（`dgcReadbackPixels` 契约、快照缓存、engine 攒批、flush 节流均不动）。
- 不改 `jni/paint_android_jni.cpp`/`PaintNative.kt`（`nativeFlush` 保留供 `nativeExportPng`/清空等非每帧路径）。
- 不改 `ReadbackScheduler.kt`（线程安全核对结论为无需改，见 §5.1）。
- 不做 modeler 预测生效（P7-4 范围，本任务只保证读回/重绘链路即时可靠 + 主线程减负）。
