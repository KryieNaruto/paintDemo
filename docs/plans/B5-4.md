# B5-4 · SDK RenderDoc 程序化抓帧 实施计划

> 对应任务书：`docs/tasks/detail/RenderDoc抓帧.md`
> 任务行：`SDK RenderDoc 程序化抓帧：renderdoc_app.h 运行时注入 + Start/EndCapture 包 composite dispatch，Windows 下 RenderDoc 可抓到 present 与 SDK 管线（人工验收）`
> 依赖：B2-1（Vulkan 离屏后端 + `brush_composite.comp` dispatch，已落地）；B4-1（dab GPU 化，已在 main，抓的是当前完整 GPU 管线）。

## 一、目标

给 SDK 加 RenderDoc **程序化抓帧**能力：运行时动态加载 RenderDoc 库、经 `RENDERDOC_GetAPI` 取 `RENDERDOC_API_1_1_1`，在 `VkBackend` 的 composite dispatch 前后调 `StartFrameCapture(vkDevice)` / `EndFrameCapture(vkDevice)`，使纯离屏（无 swapchain、无 `vkQueuePresentKHR`、独立 VkDevice）的内核管线**无 present 也可被抓**。默认关闭，无 renderdoc 库 / 未启用时零回归。宿主 present 帧仍走 RenderDoc 常规抓帧。

## 二、验收标准（抄自任务书 `docs/tasks/detail/RenderDoc抓帧.md`，不自编）

**验收**（人工验收：本机 Windows MSVC + paint-pc 宿主）

- Windows 编译 SDK 与 paint-pc 宿主并启动，RenderDoc 下：
  1. 常规抓帧能抓到宿主 **present 帧**（画面正确上屏）。
  2. 同一 RenderDoc 会话内，程序化抓帧能抓到 **SDK 内核管线**：`brush_composite.comp` compute dispatch 可见，shader 源码 / 资源绑定可查看。
- 无 renderdoc 库 / 未启用环境下**零回归**：现有 host `ctest` 全绿（含 B5-3 确定性、B4-1 CPU/GPU 对照）；`android-arm64` preset 仍可编出 `.so`。
- 人工验收记录：RenderDoc 会话截图 / 抓帧文件路径 + 结果登记。

**评审打「通过」的必要条件**（抄自任务书）：

**SDK 工程约束（本任务必须满足，落入验收）**：

- 所有权一律 RAII：RenderDoc 库句柄用 `std::unique_ptr` + 自定义删除器（Windows `FreeLibrary` / POSIX `dlclose`），全仓无裸 `new`/`delete` 所有权（一律 `make_unique`/`unique_ptr`）。
- Pimpl 边界：对外 C ABI 不暴露任何 RenderDoc / 内部类型；新增 C API 开关（如有）仅 `int` 返回，头文件不含 RenderDoc 头与任何 C++ 符号。
- 泄漏验证：host `DGCPAIN_SANITIZE`（ASan + LSan）下跑所有权循环测试，验证库句柄 / 包装对象反复 create/destroy 无泄漏。

## 三、依赖现状（已核实 worktree 代码）

- `render/vulkan/vk_backend.cpp`：
  - `VkBackend::Impl::EnsureDevice()`（L290 起）自建 VkInstance/VkDevice（**无 surface 扩展、无 layer**，L303-307），选 COMPUTE|TRANSFER|GRAPHICS 队列族，创建 commandPool/commandBuffer/pipeline/descriptor 等（全部 RAII 守卫 `VkTopHandle`/`VkDeviceHandle`）。
  - `VkBackend::Impl::CompositeLocked()`（L602-636）：`BeginCommands()` → 逐 stamp `vkCmdBindPipeline`/`vkCmdBindDescriptorSets`/`vkCmdPushConstants`/`vkCmdDispatch` → `SubmitAndWait()`。**composite dispatch 唯一落点在此**，画布 storage image 常驻 `VK_IMAGE_LAYOUT_GENERAL`，无 per-dispatch barrier（canvas 不进交换链）。
  - `SubmitAndWait()`（L577-592）单 commandBuffer 提交 + `vkWaitForFences` 阻塞完成。`device` 为 `VkTopHandle<VkDevice,...>`，可隐式转 `VkDevice`。
- 线程模型：`composite()` 由 `Engine::renderLoop()`（`core/engine.cpp` L191）调用，`clearCanvas/readback/exportPNG` 由 C API 线程调用；`VkBackend` 用 `mutex_` 串行化（`vk_backend.h` L47）。抓帧 Start/End 落在同一提交线程（render 线程），由 mutex 保证与其它提交互斥。
- 对外 ABI：`sdk_api/dgc_paint_c_api.h` 只暴露 `DgcContext*` 不透明句柄（Pimpl：`unique_ptr<Impl>`，见 `dgc_paint_c_api.cpp` L21-48），无 RenderDoc 相关类型。
- CMake：顶层 `CMakeLists.txt` 用 `if(DGCPAIN_RENDER_VULKAN AND EXISTS .../CMakeLists.txt) add_subdirectory(...)` 路由；`render/vulkan/CMakeLists.txt` `target_sources(dgc_paint PRIVATE vk_backend.cpp)`。三方库供给约定：`third_party/stb`、`third_party/nlohmann` 为 vendor 单头/源。`CMakePresets.json` 含 `host-linux`、`host-linux-sanitize`、`host-windows`、`android-arm64`。
- renderdoc 现状：全仓无 `renderdoc_app.h`、无任何 renderdoc 注入代码（仅文档提及 RenderDoc 抓帧）。**需采购 vendor 单头**。

## 五、实施步骤

### 步骤 1 · 采购 vendor 单头（本机 Linux 可做）

从 RenderDoc 官方取 `renderdoc_app.h`（版本 1.1.1 结构，MIT 许可），vendor 到 `third_party/renderdoc/renderdoc_app.h`，**保留原始 MIT 版权头**并注释来源（RenderDoc 官方 `renderdoc_app.h`）。该头为纯 C（`RENDERDOC_CC` 调用约定宏 + `extern "C"`），无链接依赖。仓库三方库供给约定为 vendor 单头（同 stb/nlohmann），故不引入 fetch-deps 条目。

### 步骤 2 · RAII 包装类（本机 Linux 可做）

新增 `render/renderdoc/renderdoc_capture.h/.cpp`，`class RenderDocCapture`（内部模块，不进 C ABI）：

- **所有权（RAII，禁裸 new/delete）**：库句柄用 `std::unique_ptr<void, LibCloser>` 持有；`LibCloser::operator()(void* h)` 在 `_WIN32` 下 `FreeLibrary((HMODULE)h)`，POSIX 下 `dlclose(h)`。句柄获取用 `LoadLibraryA`/`dlopen`（返回裸句柄 → `reset`/`make_unique` 收编，不 `new`）。
- **借用指针非拥有**：`RENDERDOC_API_1_1_1* api_` 由 DLL 持有，仅借用；成员声明序 `api_`（非拥有）先于 `lib_`（拥有），析构逆序先 `lib_` 卸载 DLL、后 `api_` 平凡析构，且不在析构中解引用 `api_`（避免 dangling 访问）。
- **懒加载 + 优雅降级**：构造读环境变量 `DGC_RENDERDOC=1`；未设置 → `disabled_=true` 全程 no-op。启用时 `EnsureLoaded()` 才 `LoadLibrary/dlsym("RENDERDOC_GetAPI")` 并 `RENDERDOC_GetAPI(eRENDERDOC_API_Version_1_1_1, &api_)`；任一步失败（库不存在 / 符号缺失 / 版本不符）→ 记 stderr 一次、置 `disabled_`，后续 no-op，**不报错不影响现有离屏路径**。
- **接口**：`startFrameCapture(void* device)` / `endFrameCapture(void* device)`（用 `RENDERDOC_DevicePointer`=`void*`，不依赖 vulkan.h），`available()`；可选 `configureFromEnv()` 调 `SetCaptureFilePathTemplate` / `SetCaptureOptionU32`（捕获目录、文件数，由 `DGC_RENDERDOC_DIR` 等 env 驱动）。
- **Pimpl 边界说明**：本类是 `dgc_paint` 内部实现（`render/` 内部头），不暴露给 C ABI；对外仍只经 `DgcContext*` 不透明句柄。其内部成员用 `unique_ptr`，符合「对外 Pimpl 隐藏实现」的同一原则。

### 步骤 3 · 挂接 composite dispatch（本机 Linux 可做）

改 `render/vulkan/vk_backend.cpp`：

- `VkBackend::Impl` 增加 `std::unique_ptr<RenderDocCapture> rdc;`（`vk_backend.h` 前向声明）。
- `EnsureDevice()` 末尾（`deviceReady = true` 后）：`rdc = std::make_unique<RenderDocCapture>();`（构造即读 env，未启用内部降级）。
- `CompositeLocked()`（L602）在 `canvasReady`/`stamps.empty()` 早退检查**之后**：
  - `if (rdc) rdc->startFrameCapture(device);`（`device` 隐式转 `VkDevice` → `void*`）
  - 现有 `BeginCommands()` → dispatch 循环 → `SubmitAndWait()` 不动
  - `if (rdc) rdc->endFrameCapture(device);` 于 `SubmitAndWait()` 之后
- 语义：整段 composite commandBuffer（bind pipeline/bind descriptor/push constants/`vkCmdDispatch` + 提交完成）被 Start/End 包住；canvas 常驻 GENERAL、无显式 barrier，故「含对应 barrier」以 commandBuffer 的 begin→submit 边界承载。Start/End 与 dispatch 在同一线程（render 线程）且被 `mutex_` 串行，不破坏确定性/时序。

### 步骤 4 · CMake 接线（本机 Linux 可做）

- `render/renderdoc/CMakeLists.txt`：`target_sources(dgc_paint PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/renderdoc_capture.cpp)`；`target_include_directories(dgc_paint PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/../../third_party/renderdoc)`。
- 顶层 `CMakeLists.txt`：加 `option(DGCPAIN_RENDERDOC "RenderDoc runtime injection (programmatic capture)" ON)`；`if(DGCPAIN_RENDERDOC AND DGCPAIN_RENDER_VULKAN AND EXISTS ${CMAKE_CURRENT_SOURCE_DIR}/render/renderdoc/CMakeLists.txt) add_subdirectory(render/renderdoc) endif()`。
- 无外部链接依赖（纯运行时 dlopen/LoadLibrary），Android `android-arm64` preset 仍走 POSIX `dlopen` 路径编译通过，运行时默认关、库不存在 → no-op，`.so` 照常产出。

### 步骤 5 ·（可选）C API 开关（本机 Linux 可做，保持 Pimpl 边界）

新增 `int dgcSetRenderDocCapture(DgcContext* ctx, int enable)`：返回 `DGC_OK`/`DGC_ERR_NULL_CONTEXT`，`enable != 0` 时强制启用抓帧（等价 env 开关，供 paint-pc 宿主程序化开关）。**头文件仅新增 `int` 返回函数声明，不含 RenderDoc 头、不含任何 C++ 符号**；实现经 `ctx->impl_->backend` 内部转发（新增 `IRenderBackend` 虚方法或经 `VkBackend` 内部 `rdc` 指针），C ABI 仍不暴露内部类型。若本步骤与最小 ABI 面冲突，可退回仅 env 开关（任务书「（可选）…计划阶段定」，默认以 env 为主开关）。

### 步骤 6 · 本机 Linux 验证（编译 + 注入点 + 管线挂接）

- `cmake --preset host-linux` 编译全绿；`ctest`（含 B5-3 确定性、B4-1 CPU/GPU 对照、B2-1 offscreen）全绿 → **零回归**。
- `cmake --preset host-linux-sanitize`（ASan+LSan）跑 `test_ownership_loop` + 新增 `test_renderdoc_capture`，验证句柄/包装对象反复 create/destroy 无泄漏。
- 如本机装有 RenderDoc Linux（`librenderdoc.so` + lavapipe），可 `DGC_RENDERDOC=1` 跑 `dgc_cli run <script>` 冒烟：验证 `RENDERDOC_GetAPI` 命中、Start/End 不崩、PNG 输出像素不变（抓帧内容是否可读以 Windows 人工为准）。

### 步骤 7 · Windows 人工验收（Windows 机器，需人工）

1. 装 LunarG Vulkan SDK + RenderDoc；`cmake --preset host-windows` 用 MSVC 编 SDK（钉 MultiThreadedDLL，见 `cmake/msvc_runtime.cmake`）。
2. 从 RenderDoc「Launch Application」启动 paint-pc 宿主（进程级注入，使 RenderDoc hook 到 SDK 自建的独立 VkInstance）。
3. 常规抓帧验证抓到宿主 **present 帧**（画面正确上屏）。
4. `DGC_RENDERDOC=1` 环境变量启动，同会话内画笔迹触发 composite，程序化抓帧验证抓到 **SDK 内核管线**：`brush_composite.comp` compute dispatch 可见、shader 源码 / 资源绑定可查。
5. 记录：RenderDoc 会话截图 / `.rdc` 抓帧文件路径，追加登记到 `docs/tasks/detail/RenderDoc抓帧.md`。

## 七、风险

1. **独立 VkInstance 不被 RenderDoc hook（最高风险）**：SDK `EnsureDevice()` 自建无 layer 的 VkInstance（`vk_backend.cpp` L303-307），RenderDoc 抓 Vulkan 依赖其 layer 生效于该实例。前提是宿主从 RenderDoc「Launch Application」启动（进程级注入，hook 所有 `vkCreateInstance`，含 SDK 后续懒建的实例）。**回退方案**：`DGC_RENDERDOC=1` 时在 `vkCreateInstance` 的 `enabledLayerCount`/`ppEnabledLayerNames` 追加 `VK_LAYER_RENDERDOC_Capture`（先 `vkEnumerateInstanceLayerProperties` 探测存在，无则降级不报错）。此回退在步骤 7 验证阶段按需启用。
2. **捕获时序/thread**：RenderDoc `StartFrameCapture` 需与提交同线程。当前 `composite()` 在 render 线程、`mutex_` 串行，Start/End 内联在 `CompositeLocked` 内即满足；风险低，但需确认 `clearCanvas`/`readback`（C API 线程）不与 composite 交错导致 EndFrameCapture 缺帧——由 `mutex_` 保证。
3. **env 开关误开影响确定性**：默认关 + 未加载即 no-op，不影响 B5-3 像素级确定性；但若 Windows 上 `DGC_RENDERDOC=1` 且 RenderDoc 注入改变 dispatch 时序，需在验收时确认「未启用环境」用例不带该 env。
4. **Android 编译**：wrapper 走 POSIX `dlopen`，Android NDK 有 `dlfcn.h`/`dlopen`，编译应通过；若 NDK 头差异导致编译错，加 `#if defined(__ANDROID__)` 编译为空实现兜底。
5. **可选 C API 增加 ABI 面**：新增导出符号可能影响既有 ABI 快照，如不确定则仅用 env 开关（步骤 5 可裁剪）。
