## 1. 背景：为什么不能直接抄任务线方向就动手（spec §7 结论）

spec 已落地 4a（合并 composite + 读回刷新为一次 GPU 提交）+ 4c（预测尖 stale-tip 顺序修复），
真机（MDP1221）复测：

| | 输入→读回 lag | 输入→上屏 lag | 肉眼落后 |
|---|---|---|---|
| 4a/4c 修复前基线 | 6ms | 15.5ms | 明显，>5mm |
| 4a/4c 修复后 | 6ms | 16ms | 与修复前几乎无区别，明显，>5mm |
| Ink（对照） | n/a | 6ms | 肉眼 0 延迟 |

4a 预期能省掉的「一次独立 GPU 提交往返（~2-3ms）」在真机端到端延迟上**没有体现出可测收益**。
spec §7 列了三个未验证根因候选，明确写「根因待查，留给后续独立任务」：

1. 4a 合并命中率在真机连续快速挥摆场景下可能不及预期（未用真机插桩验证过，host 测试验证的
   是构造场景）。
2. 真正瓶颈可能在 GPU 提交往返之外（Compose 重组/draw 调度、bitmap 双缓冲切换等真机侧未
   插桩环节）。
3. 模型器自身滞后（wobble+spring）可能比 spec §1 估算的更大。

本计划 §2 先给出**基于现有代码路径重新推导**的分析结论，再在 §4 用真机实测验证/证伪，最后
才在 §5 决定具体要改哪里——不允许跳过这一步直接把「readback 去 16ms 节流」当成已证实的
修复方案来实现。

## 2. 现状代码实证（关键：dgcReadbackPixels 实际做什么）

逐层读代码得到的、比 spec 更细的一个事实（spec investigate 时未写透，是本计划新增的分析）：

- `dgcReadbackPixels`（`sdk_api/dgc_paint_c_api.cpp:410-439`）内部只做两件事：① 对
  `engine_->requestFlush()` 做一次原子 store（非阻塞 catch-up）；② `backend_->readback(rgbaOut)`。
- `VkBackend::readback()`（`render/vulkan/vk_backend.cpp:1423-1435`）**不碰 GPU、不取
  `mutex_`**——只是 `cache_mutex_` 保护下的一次纯 CPU `memcpy`（从渲染线程维护的 `cache_`
  快照拷出）。也就是说：**消费端每调一次 `dgcReadbackPixels`，SDK 侧的耗时恒等于「一次原子
  store + 一次 3.1MB memcpy」（优化 4 后 ~0.9-1ms 量级），与当时渲染线程是否正在 GPU 提交、
  提交了几次、merge 命中与否完全无关**——GPU 提交（composite + 4a 合并的刷新）全部发生在
  独立的渲染线程上，`readback()` 调用方永远不等它。
- `cache_` 真正被刷新（GPU→CPU 拷贝，含 4a 合并的 composite+refresh 一次提交）的频率由
  **渲染线程自己的节奏**决定，被 `Engine::requestFlush()` 里的 `kMinSnapshotRefreshIntervalNs`
  节流到 **≤ 1 次 / `kMinFlushIntervalMs`（4ms）**（`core/engine.cpp:43-56,135-161`）——这是
  P7-2 定的、独立于消费端调用频率的 SDK 内部节流，本任务不改。

**由此得到一个可由代码直接证明、不需要猜测的推论**：`dgcReadbackPixels` 单次调用耗时的理论
上界远小于 1ms 级（纯 memcpy），4a 优化的「省一次 GPU 提交往返」发生在渲染线程、消费端调用方
从不同步等待它——**4a 对「dgcReadbackPixels 单次调用耗时」这个指标从架构上就不可能有可观测
收益**，因为它优化的是一个消费端永远不会等待的异步路径。这直接解释了 spec §7「4a 预期收益
在真机端到端延迟上没有体现」的现象，且给出的解释比 spec 三个候选根因里的候选②（"瓶颈可能在
GPU 提交往返之外"）更具体：**瓶颈几乎肯定在 GPU 提交往返之外，因为 GPU 提交往返本来就不在
`dgcReadbackPixels` 的同步调用路径上**。

再看消费端（`paint-android`）：`ReadbackScheduler.kt`（`app/src/main/java/.../ui/ReadbackScheduler.kt`）
把「事件到达」到「真正调用 `dgcReadbackPixels`」之间加了 `minIntervalNs`
节流，**默认值 `DEFAULT_MIN_INTERVAL_NS = 16_000_000L`（16ms）**——这个数字与 spec §7
测得的「输入→读回 lag」「输入→上屏 lag」（均 ≈16ms）在量级上高度吻合，而 SDK 侧的真实
处理耗时（memcpy）理应远小于此。`PaintScreen.kt` 的 `drawLagProbe`（onInput → Compose
`Canvas` draw 真正执行那一刻）比 `lagProbe`（onInput → readback 完成）还要再高出若干 ms，
对应的是 Compose 状态写入（`bitmap = back`）之后要等**下一个 vsync 才会真正 recompose+draw**
这一段（Android/Compose 单一 Choreographer 帧管线的固有特性，不经过 SDK）。

**Phase 0 要验证的，就是把上面这个「代码分析结论」在真机连续快画场景下实测坐实**（不能只凭
读代码就下结论去改数字），具体见 §4。

## 3. Phase 0：真机根因排查（先做，不可跳过）

### 3.1 候选① 4a 合并命中率（spec 候选一）

**预测**（依 §2 分析）：命中率对本任务要修的「输入→上屏 lag」这个症状**大概率不是主因**
（渲染线程有 GPU 提交往返的最坏情况下，也在消费端 16ms 读回窗口内轻松完成，不会拖慢
`readback()` 的 memcpy），但**必须**按用户要求实测验证，不能只靠分析下结论。

**测量方式**（真机，复用已埋 hook，投入即弃的诊断变体，不进最终交付 diff）：

1. 在 `paint-android` 的一个**临时诊断分支/scratch commit**（不合并进 `task/A8-3`）里：
   - `app/build.gradle.kts` 的 `externalNativeBuild.cmake.arguments` 临时追加
     `-DDGCPAIN_TEST_HOOKS=ON`（复用现有 `option(DGCPAIN_TEST_HOOKS ...)`，`CMakeLists.txt:34`，
     默认 OFF，本次仅诊断构建打开）。
   - `jni/paint_android_jni.cpp` 临时新增（`#ifdef DGCPAIN_TEST_HOOKS` 包住）三个 JNI 方法，
     直接转发已存在的 `extern "C" std::uint64_t dgcTestCompositeCount(DgcContext*)` /
     `dgcTestSubmitAndWaitCount(DgcContext*)` /（可选）`dgcTestSnapshotRefreshCount(DgcContext*)`
     （声明方式同 `tests/test_snapshot_refresh_throttle.cpp:38-43`：这三个符号不在公开头
     `dgc_paint_c_api.h` 里，消费端自行 `extern "C"` 前置声明即可调用，因为 `DGCPAIN_TEST_HOOKS`
     开启时它们已编进 `.so`）。**不新增 SDK 公开符号，不碰 `dgc_paint_c_api.h`。**
   - `PaintScreen.kt` HUD 临时加一行 `composite=X submit=Y`（`#ifdef` 无法用于 Kotlin，改用
     一个 `BuildConfig`/Gradle flag 或直接判断 JNI 方法是否存在的方式門控，诊断分支专用）。
2. 真机（MDP1221，走既有 adb 反向隧道协议）装诊断 APK，人工用真实手指以 spec §1 的
   ~600mm/s 速度连续快速挥摆画线（**不用 `adb shell input swipe`**——已在此前投入验证过合成
   swipe 时序与真实手指差异巨大、不能用于延迟数字验收，见 `docs/superpowers/plans/
   2026-09-04-mode-a-render-pipeline-merge-submission.md` Task 5 Step 4 的既定协议）。
3. 画完一笔后读 HUD 上的 `composite`/`submit` 计数，计算 `submit - composite`：
   - 若该差值在整段快速挥摆过程中**基本不随笔画长度线性增长**（只在起笔/收笔各产生固定的
     小常数，如 `ClearTipLocked` 抬笔时的 1 次独立提交），判定为**候选①证伪**——merge 命中率
     健康，4a 按设计工作，不是本次症状的根因。
   - 若该差值随挥摆持续时间**线性增长**（意味着中途大量走了未合并的独立刷新提交路径），
     判定为**候选①成立**——升级为需要真实 SDK 代码修复的 bug，**停下**，不在本任务内直接
     动手改，回 build-pipeline 报告需要单独排查/开新任务（因为这属于「SDK 生产代码要改」，
     超出「只读小改」的任务边界，且 4a 的实现逻辑需要重新审阅）。
4. 诊断分支收尾：**无论结果如何，诊断用的 JNI 方法 + gradle flag + HUD 行不进入
   `task/A8-3` 最终提交**（防止把仅供一次性排查用的代码带进产品 diff）；结论写进本计划
   执行阶段的 EVIDENCE 记录（或 spec 追加一节，仿 spec §7 格式）。

### 3.2 候选② 瓶颈是否真在 GPU 提交往返之外（spec 候选二）

**预测**（依 §2 分析，比 spec 候选二更具体）：是。且不需要新插桩——**复用现有、已在生产
构建里的 HUD 三个数字**（`readMs`、`lagProbe.avgLagMs()`「输入→读回」、
`drawLagProbe.avgLagMs()`「输入→上屏」），因为 `readMs` 恰好就是 `dgcReadbackPixels`
单次调用的纯耗时（§2 已证明其架构上界是 memcpy 量级，不含 GPU 提交）。

**测量方式**（真机，不需要诊断分支，用现有已发布 HUD 即可，与 §3.1 同一次真机连续挥摆里
顺带记录）：

1. 真机连续快速挥摆（同 §3.1 场景，同一次操作即可覆盖两个候选，不必分两次装机测试）时，
   记录若干次 `readMs` 读数（应保持低值，若 4a+优化4 均生效，预期 ~1-3ms 量级，不随挥摆
   持续时间增长）。
2. 同时记录 `lagProbe.avgLagMs()`（输入→读回）与 `drawLagProbe.avgLagMs()`（输入→上屏）。
3. 判定：
   - 若 `readMs` 显著小于 `lagProbe.avgLagMs()`（例如 readMs ~1-3ms 而 lagProbe ~6-16ms），
     **候选②成立**——差值（`lagProbe - readMs`）主要来自消费端 `ReadbackScheduler` 的
     `minIntervalNs` 节流等待，瓶颈确认在 SDK 的 GPU 提交往返之外，落在消费端调度层。
   - 若 `readMs` 本身就已经很大（与 `lagProbe` 同量级），说明 §2 的分析在真机上不成立
     （可能是真机上 `cache_mutex_` 竞争、内存带宽压力等 host 未复现的因素），**候选②的
     "GPU 提交往返" 需要重新定义范围**——停下，把这个反常现象记录清楚，回 build-pipeline
     报告，不能直接套用 §5 的消费端节流方案（因为如果 SDK 侧本身真的慢，改消费端节流治标
     不治本）。
   - 另记 `drawLagProbe.avgLagMs() - lagProbe.avgLagMs()`（Compose 重组/draw 调度那一段，
     不经 SDK）：这一段的量级决定了 §5 的「尽早换帧上屏」有没有本任务范围内可做的空间
     （见 §5.3）。

### 3.3 候选③ 模型器自身滞后被低估（spec 候选三）

**范围声明**：本任务验收标准是「body 拖后 ≤~1 帧」，任务行给的修复手段是「readback 去
16ms 节流 + 尽早换帧上屏 + 必要时低延迟 present」——**全部是渲染管线/调度层手段，不含
调 modeler 参数**。候选③（wobble/spring 参数）不在本任务修复范围内。Phase 0 只记录观察
（若 §3.1/3.2 的改动落地后真机复测仍有肉眼可见落后，且 `readMs`/`lagProbe` 已经很小，
那么剩余落后大概率来自候选③，留给后续任务，不在本任务内展开新的 tuning）。

| 4 | **A8-2 预测瞬态 wet-tip 层**（`prediction_interval_ms` 默认 20ms，与本任务的 readback `minIntervalNs` 是两个不同常量：前者是 modeler 预测点生成间隔，后者是消费端读回调用节流）| 读回频率提高后，`RefreshReadbackCacheLocked` 的 merge（`tipHasContent_` 为真时）触发次数会相应提高，但代价已被 4a 合并进单次提交，且只在「有 tip」时才付（A8-2 §8 冲突表已论证过一次，本任务只是提高了触发次数而非改变单次代价）。| 不冲突，但 §5.4 的真机 fps 回归**必须覆盖「预测开启」场景**（不能只测预测关闭），因为这是本任务新引入的、A8-2 没测过的「更高频读回 × wet-tip merge」组合。 |

## 5. 方案（依 Phase 0 结论为「候选①②预期成立」的分支展开；若 Phase 0 结果与预期不同，
   按 §3.4 决策树停下，不执行本节）

### 5.1 降低消费端 readback 节流（任务行「readback 去 16ms 节流」的落地）

- 改 `paint-android` `ReadbackScheduler.kt`：`DEFAULT_MIN_INTERVAL_NS` 从 `16_000_000L`
  改为一个**真机实测确定**的更小值，候选梯度（由激进到保守，真机逐档验证，取满足下述
  「不回归」门槛的最小值）：
  1. `4_000_000L`（4ms，等于 SDK 侧 `kMinFlushIntervalMs`——低于此值纯属浪费，见 §4 表 1）；
  2. `8_000_000L`（8ms，留一档中间余量）；
  3. 若 4ms/8ms 均导致真机 fps 掉破 60（P7-2 门槛），退回 `16_000_000L`（不变），如实记录
     「本任务在当前真机上未能安全降低该节流，需要后续任务配合其它手段」，不强行降低造成
     fps 回归换取 lag 数字好看。
- 更新类文档注释：说明「16ms 是 4a 落地前定的、当时每次读回的 GPU 代价较高；4a 后代价降到
  合并单次提交，重新测得可以降到 Xms 而不掉帧」，并保留 P7-3 原有的「为什么曾经是 16ms」
  的历史注释（不删除，追加新注释，保留决策沿革可追溯）。
- **不改** `shouldReadbackNow()`/`timeUntilReadableNs()`/`onReadbackComplete()`/双缓冲/
  deadline 等待机制的逻辑，只改这一个常量（`replace_all` 风险最小的改法）。

  当年特意跳过的部分**——在紧密提交笔点的同时，以模拟的高频节奏（如每 4-8ms 一次，用
  `std::chrono` 真实 sleep 或计数节流，不依赖 wall-clock 抖动）穿插调用 `dgcReadbackPixels`
  （而不是像现有测试那样完全不中途读回），断言：
  - `dgcTestSubmitAndWaitCount(ctx) - dgcTestCompositeCount(ctx)` 的增量在整个连续绘制期间

### 5.3 「尽早换帧上屏」：评估结论 = 本任务范围内空间有限，明确边界

- 依 §3.2 的分解（`drawLagProbe.avg - lagProbe.avg` = Compose 重组/draw 调度那一段）：这一段
  由 Android/Compose 单一 Choreographer 帧管线决定（`bitmap = back` 状态写入后必须等下一个
  vsync 才会被 recompose+draw），**不经过 SDK，也不经过 `ReadbackScheduler`**——是 Bitmap+
  Compose 架构下的固有 1-vsync 量级下限。
- 本任务范围内可做的、不改变架构的微调（若真机测得这段确有可压缩的「非必要」部分）：
  - 复核 `LaunchedEffect(Unit) { snapshotFlow { dirty }.collect { ... } }` 协程调度路径，
    确认 `bitmap = back` 这次状态写入前后没有可去掉的多余 dispatcher 切换/无关重组触发点
    （轻量代码 review，非架构改动）。
  - 不引入新的强制 invalidate/提前绘制机制——Compose 声明式模型下没有「比下一个 vsync 更早
    画出来」的合法手段，强行 hack（如 `View.invalidate()` 之外的手段）超出本任务「只读
    小改」范围且风险不可控。
- **明确评估结论（落到本计划，不在代码里做）**：进一步压缩这一段的唯一真实手段是 spec §4b
  的 swapchain 直接上屏（消灭 Bitmap+Compose 整条 CPU 侧链路），spec §4a/4b 交付顺序小节
  已经明确决定「先落地 4a、真机验证收益后，4b 再单独走一轮完整的申领→计划→审阅→测试流程」
  ——4b 需要新 SDK C API（`dgcBindOnscreenSurface` 等）+ 平台原生 surface 生命周期管理 +
  消费端渲染架构级改动，**不满足本任务「SDK 只读小改」的边界**，也不应该在 A8-3 里顺手夹带
  实现。若 §5.1 降低节流后真机复测仍不满足「body 拖后 ≤~1 帧」，剩余缺口应归因于这个已知的
  架构下限，作为独立结论写进验收产出，交由后续任务（4b）处理，不在本任务内强行达标。

### 5.4 「必要时评估低延迟 present」：评估结论

- 见 §5.3——低延迟 present（swapchain 直接上屏）就是 4b，评估结论 = **不在本任务实现**，
  理由同上（超出「只读小改」边界 + spec 已定的独立分工顺序）。本任务完成「评估」这一动作
  本身（写在本计划里），满足任务行「必要时评估」的字面要求，不代表要做出「必要」的实现。

## 9. 风险与取舍

- **R1（最高）Phase 0 结论与 §2 分析不符**：如果真机实测 `readMs` 本身就很大（与分析矛盾），
  说明 host 未复现的真机侧因素（内存带宽、`cache_mutex_` 竞争等）才是真正瓶颈，此时 §5 的
  「降低消费端节流」方案基础不成立，必须先停下重新排查（§3.4），不能因为已经写好计划就
  强行按原计划推进。
- **R2 节流值降低导致真机 fps 回归**：§4 表 2 已识别为真实的既有决策冲突（P7-3 定 16ms 时
  的前提已被 4a 改变，但没有真机数据验证新值安全）。**取舍**：逐档真机验证（4ms→8ms→16ms
  不变），只接受不引入 fps 回归（<60fps）的最小候选值；若所有候选值都无法在不掉帧前提下
  提供可感知的 lag 改善，如实报告「本任务未能进一步降低」而非强行降低造成真机可感知卡顿。
- **R3 诊断专用代码误入最终交付**：§3.1 的诊断 JNI/gradle flag 必须在收尾时确认不出现在
  `task/A8-3` 分支的最终 diff 里（`git diff`/`git log` 核对），执行阶段清单需要显式包含
  这一步骤，防止「一次性排查工具」变成长期技术债或误导性的「隐藏 debug 后门」留在生产
  消费端代码里。
- **R4 「body 拖后 ≤~1 帧」验收结论依赖人工肉眼判定**：与 A8-1/A8-2 先例一致，真机数据为
  硬门槛人工验收项，不接受「沙箱局限」豁免；host 自动化（新增 host 测试 + ctest 全绿 +
  Kotlin 单测绿）为可验证替代，但不能替代真机人工判定本身。
- **R5 候选③（模型器滞后）未被本任务处理，验收目标可能因此打折扣**：若 §5.1/§5.3 落地后
  真机复测仍有肉眼可辨落后但已确认主因转移到候选③，如实记录并交由后续任务（不在本任务
  内展开新的 modeler tuning，超出任务行给定的「渲染管线/调度」修复范围）。
