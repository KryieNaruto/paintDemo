## 1. 目标与「批量吞吐 vs 防孔洞」tradeoff 的具体数值分析

**目标**：给 `flush_requested_` 的非阻塞置位加节流，使高频 `requestFlush()`
（`dgcReadbackPixels`/`dgcExportPNG` 驱动）不再能把 `renderLoop()` 逼到逐 stamp / 极小批量
flush；同时不重新引入 `d64c2fa` 之前的阻塞孔洞或 `f96456e` 之前的滞后孔洞。

### 1.1 关键事实：既有攒批上限兜底已经独立于 `flush_requested_` 提供了滞后上界

§0.2 已核实：`kMaxBatchDurationMs=4ms` 的时间检查，在"队列持续有新 stamp 到达"场景下，
**每次新 stamp 被 `try_pop` 到都会被求值一次**（不是"每 4ms 才检查一次"，而是"检查时判断
距批开始是否已过 4ms"）；"队列瞬时为空"场景下则由队列已空分支无条件立即 flush。

推论：**无论 `flush_requested_` 节流策略如何设计，`renderLoop()` 的最大滞后（即"读回可能
比最新输入落后多久"）都已经被 §0.2 的两条既有兜底钉死在 ≤ `kMaxBatchDurationMs`（4ms，
繁忙持续输入下）或 ≈0（输入变稀疏/停止时，队列很快变空触发即时 flush）**——这个上界是
P7-1 已经设计并通过验收的、和"节流 `flush_requested_`"这个新改动完全正交的机制。

### 1.2 节流方案：`kMinFlushIntervalMs`，取值与 `kMaxBatchDurationMs` 相同（4ms），复用同一常量

在 `renderLoop()` 内新增"距上次实际 flush 完成的时间戳"`lastFlushTime_`（渲染线程本地
变量，不需要原子/跨线程同步——见 §3.1），把"是否响应 `flush_requested_`"的判定改为：

```
haveRequest = flush_requested_.load()               // 只 peek，不清零
intervalOk  = (now - lastFlushTime_) >= kMinFlushIntervalMs
overCap     = batchStampCount >= kMaxBatchStamps || (now - batchStart) >= kMaxBatchDurationMs
if (overCap || (haveRequest && intervalOk)) {
    if (haveRequest) flush_requested_.store(false);  // 仅在"本次将要 flush"时才消费该请求
    flushBatch();
    lastFlushTime_ = now;
}
```

`kMinFlushIntervalMs` 取值 **等于 `kMaxBatchDurationMs`（4ms），复用同一个常量**（不是巧合
错开的第二个数字），理由是数值可推导而非拍脑袋折衷：

- 由 §1.1 可知，`overCap` 本身已无条件保证"批处于繁忙输入下滞后 ≤4ms"。如果
  `kMinFlushIntervalMs < kMaxBatchDurationMs`，`flush_requested_` 快速路径就能在
  `overCap` 本该生效的窗口内提前触发更多次 flush——这正是当前 bug 的成因（`0ms` 节流，
  即 P7-1 现状），只是把"完全不节流"换成"节流到比 4ms 更短的某个数"，仍然可能把批量
  收益打回去，只是打回的程度较轻——**这不是把两难消除，只是把它调轻**，不满足"两全"
  要求。
- 如果 `kMinFlushIntervalMs > kMaxBatchDurationMs`，`flush_requested_` 快速路径会比
  `overCap` 更慢触发，等于让它在繁忙输入场景下完全失去意义（`overCap` 总是先触发），
  但在"输入稀疏、`overCap` 时间检查因为没有新 stamp 到达而迟迟不被求值"的场景下，
  会让读回额外等待超过 4ms——而 4ms 正是 P7-1 论证过的"远小于任一目标帧时间、不会在
  人眼可感知窗口内出现孔洞"的安全边界（见 `core/engine.cpp:22-26` 现有注释），调大它
  没有收益、只有下行风险，不可取。
- **`kMinFlushIntervalMs == kMaxBatchDurationMs`（4ms）是唯一让"`flush_requested_` 快速
  路径的最大触发频率"不超过"`overCap` 本身已经承诺的频率上界"的取值**：繁忙持续输入下，
  `overCap` 已经在 ≤4ms 粒度触发 flush，`flush_requested_` 快速路径被节流到同样 ≤4ms
  粒度后，**不会比 `overCap` 更频繁**，因此不会把批量吞吐进一步打回（批大小下界仍由
  "4ms 窗口内自然到达的 stamp 数"决定，与 P7-1 验收通过时的批大小量级一致）；输入稀疏
  /队列变空场景下，队列已空分支仍然无条件立即 flush，不受本节流影响，滞后不会因此
  变差。换言之：**本方案不是在"批量吞吐"与"防孔洞/滞后"之间取一个折衷点，而是让
  `flush_requested_` 路径的触发频率上界收敛到既有 `overCap`/"队列已空"两条机制已经
  独立提供的上界之内，使其变成这两条机制的严格子集，不会比它们更差，也不需要比它们
  更好**——因此不存在"必须牺牲一方换取另一方"的两难。

### 1.3 数值留痕（帧预算换算，供评审对照，非新论据，仅复用 P7-1 已有推导）

- PC 120fps 预算 = 8.33ms/帧。按 `kMinFlushIntervalMs=4ms` 的**理论最坏情形**（每 4ms 必
  有一次因 `flush_requested_` 触发的 flush，且恰好每帧覆盖两次该窗口），GPU
  `SubmitAndWait` 单次开销约 0.73ms（[[sdk-perf-bottlenecks]] 记录的批量 composite 优化
  根因数据），两次合计 ≈1.46ms，占 8.33ms 预算的 ~17.5%，留有 ~6.87ms 给
  readback memcpy/present/编码等其余工作——量级上支持 ≥120fps 目标；这只是留痕演算，
  **不是本任务判定通过与否的依据，真实 fps 以 §6 真机实测数据为准**。
- Android 60fps 预算 = 16.67ms/帧，同样的最坏情形（≈2 次/帧提交）远比 P7-1 之前
  "每 vsync 帧一次阻塞 `dgcFlush()`（Mali 单次提交开销可达 174ms，见
  [[sdk-perf-bottlenecks]]）"轻得多；Android 侧真正的量级改善主要来自 §2.2 消费端去掉
  阻塞 `nativeFlush()` 调用本身，SDK 侧节流是次要贡献但同样必要（防止去掉阻塞调用后
  `nativeReadback` 内部的 `requestFlush()` 又在 Android 侧以 vsync 频率重新触发同样的
  "小批量 flush"问题——vsync 频率通常远低于 PC 关 vsync 后的读回频率，但仍需节流保证
  一致性与未来"Android 侧也关闭帧率限制/加大 readback 频率"时不再复发）。

**结论：本方案在设计层面能同时满足"不打散批量"（§1.2 第三条）与"不引入孔洞/滞后"
（§1.1 既有兜底不受影响），不是自行拍板的折衷取舍，故本计划不因这一条触发「停下报人工」
——但 §6 明确保留"真机数据不达标则任务不能收尾"的独立硬门槛，两者不是同一件事：本节
只回应"设计上是否存在两难"，不代表真机测得的数字必然达标。**

## 3. 详细设计

### 3.1 `core/engine.h`/`core/engine.cpp`：节流机制实现

`core/engine.h`（私有成员区，紧邻 `flush_requested_`）新增局部状态说明性注释（实际变量
放在 `renderLoop()` 函数局部而非成员，因为只被渲染线程读写，见下）：

```cpp
// flush_requested_ 注释追加（P7-2）：非阻塞置位可能来自远高于 renderLoop 攒批节奏的
// 调用频率（如 PC 关 vsync 后 dgcReadbackPixels 的忙循环调用）。renderLoop() 对该标志
// 的"响应"频率做了节流（kMinFlushIntervalMs，见 engine.cpp），未达节流间隔时不清零
// 该标志（保留请求，不静默丢弃），下一次循环检查间隔已过时会补上；节流窗口与既有
// kMaxBatchDurationMs 攒批时长上限取同一数值（复用常量），使该路径的最大触发频率
// 不超过既有攒批兜底本就承诺的上界，理论上不会比 P7-1 验收通过时的批量吞吐更差。
```

`core/engine.cpp` 匿名命名空间：

```cpp
constexpr std::size_t kMaxBatchStamps = 512;
constexpr auto kMaxBatchDurationMs = std::chrono::milliseconds(4);
// P7-2：flush_requested_ 节流窗口。刻意与 kMaxBatchDurationMs 取同一值并直接复用该
// 常量（不引入独立数字）——理由见 docs/plans/P7-2.md §1.2：既有攒批时长上限已经在
// "持续繁忙输入"场景独立保证 ≤kMaxBatchDurationMs 的滞后上界，节流窗口取更小的值
// 只会让 flush_requested_ 快速路径抢在该上界生效前提前触发、重新压小批大小（P7-1
// 回归的病理）；取更大的值则在"输入稀疏、overCap 时间检查得不到新 stamp 触发机会"
// 场景下让读回多等，没有收益。两者相等是唯一能让该路径最大触发频率不超过既有兜底
// 承诺频率、因而不会打回批量吞吐的取值。
constexpr auto kMinFlushIntervalMs = kMaxBatchDurationMs;
```

`renderLoop()` 改造（仅改 `try_pop` 成功分支内的判定，其余不变）：

```cpp
std::vector<RenderBatch> batch;
std::size_t batchStampCount = 0;
std::chrono::steady_clock::time_point batchStart{};
// P7-2：仅渲染线程本地读写（无跨线程访问），不需要原子/锁；初值设为"很久以前"
// （epoch）确保 start() 后第一次收到请求即可立即响应，不因初值巧合被节流。
auto lastFlushTime = std::chrono::steady_clock::time_point{};

// ...flushBatch() lambda 不变，末尾追加 lastFlushTime 更新（见下）...

while (true) {
    if (stop_.load(...)) return;
    RenderBatch stamps;
    if (brush_to_render_.try_pop(stamps)) {
        if (batch.empty()) batchStart = std::chrono::steady_clock::now();
        batchStampCount += stamps.stamps.size();
        batch.push_back(std::move(stamps));

        const bool haveRequest = flush_requested_.load(std::memory_order_acquire);
        const auto now = std::chrono::steady_clock::now();
        const bool intervalOk = (now - lastFlushTime) >= kMinFlushIntervalMs;
        const bool overCap = batchStampCount >= kMaxBatchStamps ||
                              (now - batchStart) >= kMaxBatchDurationMs;
        if (overCap || (haveRequest && intervalOk)) {
            // 仅在"本次确实要 flush"时才消费该请求：overCap 触发时若 haveRequest 也为真，
            // 说明这次 flush 同样满足了那次 catch-up 诉求，一并清零；未触发 flush 时绝不
            // 清零，保证请求不被静默丢弃（P7-2 硬要求）。
            if (haveRequest) {
                flush_requested_.store(false, std::memory_order_release);
            }
            flushBatch();
            lastFlushTime = std::chrono::steady_clock::now();
        }
        continue;
    }
    if (!batch.empty()) {
        flushBatch();      // 条件 3：队列已空，不受节流影响（§1.2 已论证不受影响）。
        lastFlushTime = std::chrono::steady_clock::now();
        continue;
    }
    std::this_thread::yield();
}
```

无新增原子变量、无新增跨线程等待：`lastFlushTime`/`batchStampCount`/`batchStart` 均为
`renderLoop()` 函数局部变量，只被渲染线程自己读写，不需要 `std::atomic`；`flush_requested_`
的 `load`/`store` 用法与 P7-1 时的 `exchange` 用法内存序等价（`acquire` 读 + `release`
写），未引入更弱的内存序假设。

## 4. 新增回归测试：`tests/test_flush_throttle_regression.cpp`

任务书产出 3 第一条要求"新增一个模拟'readback 调用频率远高于渲染批次自然形成速度'的
回归测试……验证批量 composite 的平均批大小/吞吐没有被打回到接近逐条处理的水平（给出
具体量化断言）"。C API 层面无法直接读到"composite 调用次数/批大小"这类内部指标（Pimpl
边界不对外暴露 `Engine`），故设计为**两段**，互补覆盖"字面调用 `dgcReadbackPixels`"与
"量化批大小"两个要求：

### 4.1 第一段（白盒，`Engine` 级）：量化平均批大小

依据 §0.3 的等价性证据（`dgcReadbackPixels` 对渲染线程的全部影响 = 一次
`requestFlush()`），直接 `#include "core/engine.h"`，仿 `tests/test_engine.cpp` 的
`CountingBackend` 模式扩展一个 `BatchCountingBackend`（记录 `composite()` 调用次数**与**
每次调用的 stamp 数总和，用于算平均批大小），运行两个并发线程：

- `producer` 线程：`engine.submitInput(...)` 连续提交约 2000 个 `StrokePoint`（`Begin` +
  循环 + `End`），每点间 `sleep_for(200~500us)`（与 `test_continuous_input_regression.cpp`
  同款节奏，约 2000~5000 点/秒，覆盖"持续繁忙输入"场景）。
- `hammer` 线程：从 `producer` 启动到结束全程，**不加任何 sleep**，紧凑循环调用
  `engine.requestFlush()`（模拟"能达到的最高频率"——真实忙循环 `dgcReadbackPixels` 的
  上限就是 CPU 能跑多快，白盒直接用 `requestFlush()` 复现同一效果，且比全量走 C API +
  真实 Vulkan 后端的 `memcpy` 开销更快、更接近"理论最高频率"这个上限场景）。

`producer.join()` 后，主线程 `hammer.join()`（先置一个 `std::atomic<bool> done` 供
`hammer` 循环退出条件，RAII 显式 `join`，不 `detach`），再 `engine.stop()`（触发最后一批
`flushBatch`，与既有 `test_engine.cpp` 用法一致）。

量化断言（阈值给出具体依据，非拍脑袋）：

- `avgBatchSize = totalStampsComposited / compositeCallCount >= kMinAvgBatchSize`。
  `kMinAvgBatchSize` 取 **4**：producer 节奏 2000~5000 点/秒，`kMinFlushIntervalMs`=4ms
  节流窗口内自然到达的 stamp 数期望为 8~20 个（`2000~5000/s × 4ms`），`4` 是留了 2~5 倍
  调度抖动安全边际后的保守下界——只要平均批大小不跌到"个位数低端"，就证明没有退化到
  "接近逐条处理"（P7-1 回归时的病理是平均批大小趋近 1）。
- `compositeCallCount` 不超过 `producerDurationMs / kMinFlushIntervalMs(4ms) × 1.5`
  （1.5 倍留给 `kMaxBatchStamps` 命中/调度抖动的余量）——直接证明节流确实生效（限制了
  由 `hammer` 触发的响应频率），而不是"侥幸因为 CPU 慢所以看起来没退化"。
- `engine.flush()`（drain 屏障）在 `hammer` 持续运行期间调用一次，断言在有界时间内
  返回（复用 `test_engine.cpp` 的 `2000ms` 上限风格），证明节流没有引入新的无界等待。

### 4.2 第二段（黑盒，C API 级）：字面覆盖"高频调用 `dgcReadbackPixels`"

沿用 `test_continuous_input_regression.cpp` 的 `producer` 结构（同仓库既有约定：各测试
文件各自复制小工具函数，不新增共享头），但读回循环**去掉 `CountInk`**（该函数逐像素
扫描 512×512，本身构成天然节流，达不到"最高频率"），只在固定次数间隔（如每 200 次
迭代）才采一次 `CountInk` 样本，绝大多数迭代只做 `dgcReadbackPixels` 本身：

```cpp
long calls = 0;
while (!producerDone.load()) {
    dgcReadbackPixels(ctx, buf.data());
    ++calls;
    if (calls % 200 == 0) { /* 记一次 CountInk 采样，供孔洞检查用 */ }
}
```

断言：
- 记录整个循环期间 `calls` 与耗时，算出实际达到的调用频率（`calls / elapsedSeconds`），
  仅打印到 stderr 供人工/评审对照（不作为通过条件，因为该数字受宿主 CPU 影响不稳定），
  但要求其**显著高于**（如 ≥5 倍）`test_continuous_input_regression.cpp` 现有循环的量级
  （后者因 `CountInk` 开销被天然限速），佐证本测试确实覆盖了"调用频率远超其影响所能
  达到的最高有效频率"的场景。
- 孔洞判据复用既有口径：`producer.join()` 后最后一次采样与 `dgcFlush()+dgcReadbackPixels`
  权威值的差值占比 `<15%`（与 `test_continuous_input_regression.cpp` 同一阈值，任务书
  产出 3 第一条要求"孔洞判据仍与现有 test_continuous_input_regression 一致地通过"）。
- 单次调用耗时上限沿用 `test_perf_regression.cpp`/`test_continuous_input_regression.cpp`
  的 `20ms`（非 ASan）/`150ms`（ASan）口径，不新造阈值。

## 8. 风险

1. **`kMinFlushIntervalMs=4ms` 是否足以解决真机 70fps→7fps 的实际差距，仍需真机数字
   验证**：§1.3 的帧预算换算是理论留痕，不是保证；若真机实测显示仍未达标（例如
   Windows 侧还存在本计划未预见的其它瓶颈，如 readback 本身的内存拷贝在真实分辨率下
   比测试画布更大更慢），需要回到设计阶段重新分析——不允许为了"让数字好看"而在没有
   新证据支撑的情况下继续调大/调小节流窗口。
2. **Android fps 提升主要依赖消费端去掉阻塞 `nativeFlush()`，SDK 侧节流是否会不小心
   重新引入延迟**：需在真机测试时同时观察"是否出现新的孔洞/滞后感"（不仅看 fps 数字），
   若节流窗口在 Android 真实 vsync 节奏下（16.67ms/帧）导致读回明显滞后于绘制，需要
   结合 §6.2 实测数据重新评估 `kMinFlushIntervalMs` 是否该与 `kMaxBatchDurationMs`
   脱钩（分别调优 PC/Android 场景），但这已超出本计划§1.2 论证的"复用同一常量"范围，
   若真机数据显示需要脱钩，应作为新发现在 `task-test`/`task-finish` 阶段明确记录，
   必要时停下报人工而非在代码里悄悄加平台特判绕过评审。
3. **`paint-android` 仓库改动脱离本 worktree 的 git 追踪**：`task-execute`/`task-test`
   阶段操作者需自行确保没有把 `paint-android` 的改动误提交进 `demo` 仓库的
   `task/P7-2` 分支（两个仓库物理路径不同，正常操作不会混淆，但需要在执行阶段的
   `git status`/`git diff` 检查中显式确认 `demo` worktree 的 diff 不包含
   `paint-android` 路径下的任何内容）。
4. **新增白盒测试（§4.1）的量化阈值（`kMinAvgBatchSize=4`、`compositeCallCount` 上界
   系数 1.5）为工程估算**：需在执行阶段结合实际 host 运行结果核验是否偏差过大；若
   实测平均批大小远高于 4（如达到 8-20，符合 §4.1 理论推导），说明阈值留有安全边际，
   属正常；若实测反而接近 4 甚至更低，需要重新检查节流实现是否有 bug（例如
   `lastFlushTime` 更新时机错误、`load`/`store` 内存序问题），不能直接放宽阈值敷衍
   通过。
5. **本沙箱大概率无法完成 §6.2 的真机实测**：这是本计划最大的已知风险，也是本任务
   相对 P7-1 最大的流程改进点——**明确不允许**用"沙箱局限 + 已如实标注"来让任务
   越过这一步直接收尾（`.claude/skills/paint-dev/SKILL.md` 新增硬规则），任务大概率
   会在完成 SDK 实现 + host 自动化测试后停在 `need-human`，等待人工在真实硬件上补测，
   这是**预期且正确的流程结果**，不是失败。
