## 1. 目标

把 Mode A 交互态显示从「离屏 composite → readback(3.1MB) → CPU → 贴图上屏」改为
「离屏 composite → blit → swapchain present」（全程 GPU 内部、无 CPU 像素搬运），消灭
readback 固有 ~10ms 级延迟地板，让 SWAPCHAIN 模式逼近 Ink ~5ms。SDK 侧为主体（本 worktree
`render/vulkan/` + `sdk_api/`）；消费端（paint-android）改动同任务但落在独立仓库 worktree。

## 3. 现状（worktree 核实，非抄 spec）

代码文件在 A8-5 worktree HEAD `8f67c42` 与 main `b4b3e0e7` **逐字节相同**（`git diff
8f67c42 main` 对 `render/vulkan/*`、`sdk_api/*`、`core/engine.cpp` 均 SAME）——spec §3 的
行号引用在 worktree 直接成立。核实要点：

- **C API 已就位，无需新增符号**：`sdk_api/dgc_paint_c_api.h:77`
  `DGC_API int dgcSetSurface(DgcContext*, void* nativeWindow, int w, int h)`；
  `sdk_api/dgc_paint_c_api.cpp:163-178` 实现：`ctx->impl_->backend->init(nativeWindow, w, h)`
  （`:175`），null 后端接受 `nativeWindow == NULL`（headless）。`dgcResize` 在 `:180`。
  `core/types.h:22` `using PlatformSurface = void*`——消费端把 `ANativeWindow*` 转 `void*`
  传入即达 SDK。
- **present() 已挂在节奏上**：`IRenderBackend::present()` 纯虚；`core/engine.cpp:444`
  渲染循环每轮 composite 后已调 `backend_->present()`；`VkBackend::present()` 现为 no-op
  （`vk_backend.cpp:1389-1391`，注释「§4.0.5」）。**engine 无需改动**。
- **VkBackend 现为纯离屏**：`vk_backend.h:14-21` 注释明示「无 surface 扩展 VkInstance +
  离屏 Canvas storage image，不创建 swapchain，present() no-op；窗口/swapchain 路径本期不做
  （init 收到非空 surface 时记录未实现）」——本任务翻转此预设，头注释要更新。
- **init 翻转点**：`vk_backend.cpp:1352-1360` `init(surface,w,h)`：`surface==nullptr` →
  `initOffscreen(w,h)`；否则只 `fprintf("windowed surface path not implemented (B2-1)")`。
- **实例/设备扩展未 enable WSI**：`EnsureDevice()`（`:458`）`VkInstanceCreateInfo` 无任何
  ppEnabledExtensionNames（`:472-475`）；设备级仅在启用 fwidth 时
  `enabledExtensionCount=1`（`:551-559`）。→ 需补实例级 `VK_KHR_surface`+
  `VK_KHR_android_surface`、设备级 `VK_KHR_swapchain`（Android 条件）。
- **RAII 模板已具备**：`vk_backend.cpp:269` `VkTopHandle<H, Destroy(H,alloc)>`（实例级：instance/
  device）；`:312` `VkDeviceHandle<H, Destroy(VkDevice,H,alloc)>`（设备子对象）。Impl 内
  `canvasImage/tipImage/displayImage/readbackBuffer` 等全为 `VkDeviceHandle`（`:374-415`）。
  - `VkSwapchainKHR`：`vkDestroySwapchainKHR(VkDevice, ...)` 直接匹配
    `VkDeviceHandle<VkSwapchainKHR, vkDestroySwapchainKHR>`。
  - `VkSurfaceKHR`：`vkDestroySurfaceKHR(VkInstance, ...)` 需 instance 参数，**现模板不匹配**，
    需新增一个「绑 instance 的 surface 守卫」（仿 `VkDeviceHandle` 加 instance 成员，或同
    模式新模板），值语义/禁拷贝/可移动/`reset()` 幂等——本计划把这一件列为必须新增的 RAII
    件（§5 SDK 清单第一项新增内容）。
- **源选择逻辑现成可复刻**：`RefreshReadbackCacheLocked`（调用点注释 `:1235`；实现区
  `:1246-1269`）即「`tipHasContent_` 有 tip → 先做一次 canvas+tip→displayImage 的 merge
  dispatch，再以 displayImage 或 canvasImage 为源」，merge 管线/barrier 约定同 A8-2
  （merge 管线建于 `:666` 区域）。present 的源选择与其**同一口径**，只把终点从
  `vkCmdCopyImageToBuffer`（`:1203`）换成 `vkCmdBlitImage` → swapchain image。
- **SDK 内现无任何 swapchain/blit 代码**：无 `vkCmdBlitImage`、无 blit pipeline（blit 是纯
  transfer 能力，不需 shader pipeline）；canvas/tip/display 常驻 GENERAL 布局。present 需
  新增：acquire、swapchain image 布局过渡（UNDEFINED→TRANSFER_DST_OPTIMAL→PRESENT_SRC）、
  blit、queuePresent、out-of-date 重建。
- **teardown 锚点**：`DestroyDevice()`（`:1319`-`:1343`，尾段 `device.reset();
  instance.reset(); deviceReady=false`）。swapchain/surface 须在其前按
  swapchain→surface→device→instance 顺序释放。
- **构建/工程事实**：
  - Android 构建 `DGCPAIN_ANDROID`（root CMakeLists:8-11，`CMAKE_SYSTEM_NAME=Android`），
    产 SHARED `libdgc_paint.so`（`:62`，B5-1），preset `android-arm64`；Android 下
    `DGCPAIN_PRECOMPILED_SPV` glslc 预编译（render/vulkan/CMakeLists.txt:38-48）；Android
    诊断走 `__android_log_print`（root:93-95）。
  - `DGCPAIN_SANITIZE`（root CMakeLists:37-44）＝ host GCC/Clang ASan+LSan，显式
    `NOT DGCPAIN_ANDROID`（Android leak 不可用）→ 泄漏验证在 host 构建跑。
  - **LTO 硬约束**：SDK 现有 CMake 无 flto/LTCG/thinlto 选项；工程纪律（skills 历史 commit
    b73acf3）明确「构建一律关闭 LTO」，本任务任何构建/pre-set 都不得引入 `-flto`/`/GL`
    `+LTCG`/thinlto（链接期整程序位码进内存会 OOM）——§5 改动清单不新增任何 LTO 选项。
  - vk_backend.cpp 同一 TU 同时编 host 与 Android：Android 专属的
    `<vulkan/vulkan_android.h>`/`<android/native_window.h>` 与 `vkCreateAndroidSurfaceKHR`
    调用须 `#ifdef DGCPAIN_ANDROID` 隔离，避免 host（linux/lavapipe 无该平台头）编译炸；
    WSI 函数符号加载方式（loader 直链 vs `vkGetInstanceProcAddr/DeviceProcAddr`）列入
    §10「执行期现场核实」（现有代码直调 vkCreateInstance 等核心原型、链接 libvulkan）。
- **消费端（paint-android，同任务跨仓部分）现状**：JNI `nativeInit(w,h)` 纯离屏；RenderMode
  现 3 态（SDK离屏 / A8-4 SurfaceView / Ink）；ReadbackScheduler + 双缓冲 bitmap +
  `presentBitmapToSurface` 上屏链路待 SWAPCHAIN 态废弃；SurfaceView 承载已有 A8-4 先例
  （`PaintSurfaceHost.kt`）。A8-4 结论（SurfaceView lockCanvas 直绘 12ms≈SDK 11.8ms，绕

  不作为可用渲染模式并入（spec §7）。

## 4. 设计

离屏 `canvasImage` 仍是**唯一权威**（composite 照旧画进它；determinism/dgcExportPNG/离屏
对照/CLI 硬约束全部不变）。新增**可选** onscreen 路径只负责「把 GPU 已有的结果显示出去」：

```
触笔 → engine 攒批 → composite 画进 canvasImage (+预测批画进 tipImage)
     → present()（已绑定 swapchain 时）：
          acquire swapchain image
          → 源选择：tipHasContent_ ? (先 merge canvas+tip→displayImage) : canvasImage
          → blit 源 → swapchain image（布局过渡 UNDEFINED→TRANSFER_DST_OPTIMAL→PRESENT_SRC）
          → queuePresent
     （全程 GPU 内部；离屏/未绑定 → 保持 no-op，现有行为零变化）
```

- **触发节奏**：engine 渲染循环**每轮 composite 后已调 present()**，触笔进→攒批→composite
  →present 天然输入驱动；预测尖（tip 每批变）同一节奏刷新，**不引入新轮询**（预测激活期无
  真实笔点时 tip 静止不必重复 present，跟 A8-2 现状一致，spec §5.3）。
- **所有权**：`VkSwapchainKHR` 走既有 `VkDeviceHandle<VkSwapchainKHR, vkDestroySwapchainKHR>`
  值语义；`VkSurfaceKHR` 因销毁需 instance，新增仿 `VkDeviceHandle` 的 instance-bound RAII
  守卫。析构顺序 swapchain→surface→device→instance（成员逆声明序，或 `DestroyDevice` 显式
  reset——两者取一，确保不晚于 device/instance 释放）。全 SDK 零裸 new/delete。
- **显示源选择**：复刻 `RefreshReadbackCacheLocked` 的 merge 口径到 present 前——仅
  `tipHasContent_` 为真时付一次 merge（canvas+tip→displayImage），与离屏读回同一条件，
  不重复写一份 merge 实现。
- **present mode**：查询 surface 能力，优先 `VK_PRESENT_MODE_MAILBOX_KHR`，不支持退 FIFO；
  记录实际选中 mode。
- **错误/生命周期**：acquire/present 遇 `VK_ERROR_OUT_OF_DATE_KHR`/`VK_ERROR_SURFACE_LOST_KHR`
  置失效标志 → 重建 swapchain 后重试/继续，不崩溃（错误处理为主路径要求）。`dgcResize`/
  `resize(w,h)` 在 onscreen 态分支重建 swapchain。前后台切换由消费端断开/重传 surface 触发
  重建。完整状态机（旋转多模式/多窗口/销毁竞态）为已知限制，本轮不扩张。
- **消费端**：`RenderMode.SWAPCHAIN` 第 4 态；JNI `Surface`→`ANativeWindow_fromSurface`→
  `dgcSetSurface`；SWAPCHAIN 态下废弃 readback→Bitmap→上屏（ReadbackScheduler/双缓冲不再
  参与显示），画布承载在 SurfaceView 上由 SDK 直接 present；导出按钮仍走 `dgcExportPNG`
  （离屏权威路径）。HUD `readMs` 在 SWAPCHAIN 态标 N/A；延迟探针打点挪到 present 完成
  （与离屏 `drawLagProbe` 对等时机，口径可比）。离屏对照与 Ink 对照保留，三态同机 A/B/C。

- `VkSwapchainKHR`：`VkDeviceHandle<VkSwapchainKHR, vkDestroySwapchainKHR>`（销毁签名匹配）。
- `VkSurfaceKHR`：销毁签名 `vkDestroySurfaceKHR(VkInstance, ...)` 与现模板不匹配 → **新增
  instance-bound 守卫**（仿 `VkDeviceHandle`，额外持 instance；或同模式新模板），同样值语义
  约束。禁止裸 `new`/`delete`、禁止裸指针成员；surface 创建失败走既有错误路径（fprintf +
  状态判定，不抛半初始化句柄）。
- 析构顺序 swapchain→surface→device→instance：或靠 Impl 成员逆声明序，或在
  `DestroyDevice`（`:1319`）device.reset() 前显式 reset，与既有「子对象→device→instance」
  纪律一致；重复调用（幂等 reset）安全。

### 6.2 Pimpl 边界（对外 ABI 面）

- 对外经既有 C ABI：**本任务不新增 C API 符号**——复用 `dgcSetSurface`/`dgcResize`；
  `DgcContext` 仍不透明句柄，`VkSurfaceKHR`/`VkSwapchainKHR`/`ANativeWindow*` 全部封在
  `VkBackend::Impl` 内部，不暴露进 `sdk_api/dgc_paint_c_api.h` 或任何公开类型。
- 头文件只改注释/预期零结构改动；公开方法签名不变。

### 6.3 泄漏验证方式

- host `-DDGCPAIN_SANITIZE=ON`（root CMakeLists:37-44，ASan+LSan，host GCC/Clang）构建跑
  全量离屏 ctest：新句柄守卫（surface/swapchain 创建即销毁路径）不得有 leak/越界；离屏权威
  路径零回归亦由此确认。
- Android 侧无 LSan（CMake 已显式排除）；真机内存面靠消费端无资源累积 + 前后台反复切换
  观察（不崩溃、surface 重建不泄漏句柄）。

### 6.4 构建约束

- **一律关闭 LTO**：任何 preset/flag 不得带 `-flto`/`/GL`+`/LTCG`/thinlto（链接期整程序位码
  进内存会 OOM）——SDK 现有 CMake 无该选项，本任务改动不得引入。
- `DGCPAIN_SANITIZE` 仅 host；Android 编译照 `--preset android-arm64`（glslc 预编译
  `DGCPAIN_PRECOMPILED_SPV`，不需 libshaderc）。
- Android 专属头/调用（`vulkan_android.h`/`vkCreateAndroidSurfaceKHR`）用 `DGCPAIN_ANDROID`
  隔离，host 编译不受影响。

## 9. 风险与取舍

- **R1（最大不确定）swapchain 在 Mali/MTK 的 present mode 行为未知**：MAILBOX 支持度/稳定性
  需真机实测；这是逼近 Ink 的关键变量。测出 MAILBOX 不稳 → 如实退 FIFO 记录，不强行。
- **R2 消费端再换一次渲染承载**：SurfaceView（A8-4 已铺）+ ANativeWindow 接线与 Compose
  状态隔离需小心。沿用 A8-4 已验证的 SurfaceView 承载方式（在 paint-android `task/A8-5`
  分支并入 A8-4 模式/或直接复用其代码）。
- **R3 WSI 函数符号加载与 host/Android 双 TU**：Android 专属头/调用须 `DGCPAIN_ANDROID`
  隔离；WSI 函数用 loader 直链还是 proc-addr 需现场确认（现有代码直链核心原型）。若 host
  链接报缺符号 → 走 proc-addr 或把创建调用整体 `#ifdef`。
- **R4 离屏与 onscreen 双路径维护成本**：权威仍是离屏；若真机后 onscreen 稳定，可后续评估
  onscreen 为默认、离屏收编为导出专用（本期不做）。
- **R5 present 每轮独立 submit 的开销**：composite 已 submit 一次，present blit 再 submit
  一次 → 两段 GPU 提交/等待。先按简单路径实现实测；若真机证明显著拖累 fps 再评估与 composite
  合并/fence 复用（spec §5.3 不引入轮询）。不作为预优化。
- **已知限制（不扩张）**：仅 Android、竖屏正常前台 + 基本 surface 重建；旋转/多窗口/销毁
  竞态、后台复杂状态机记录留后续任务。
- **非目标**：不做 PC swapchain（paint-pc 另开）；不改预测模型/stroke modeler；不新增 C API
  符号；A8-4 `SDK_SURFACE_VIEW` 模式不并入作可用模式（spec §7）。
