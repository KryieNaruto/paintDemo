# A8-1 · Jetpack Ink 渲染 A/B 对照 实施计划

> 对应任务书：`docs/tasks/detail/JetpackInk渲染A-B对照.md`（线8-渲染对照）。
> 本计划为**计划阶段产物**，不实现、不测试、不评审。
> 前置参考：`docs/plans/ink-rendering-android-ab.md`（build-pipeline 审阅门 81/100 的既有 task 级计划，本计划保留其任务分解，补充 SDK 工程约束、冲突与取舍、自动化/人工验收边界）。

## 1. 目标

在 **paint-android（消费者仓库）** 增加一条 Jetpack Ink（androidx.ink 1.0.0 stable）低延迟渲染路径（Mode B），与现有 SDK（Vulkan 离屏 → readback → 贴图）路径（Mode A）在**应用内一键开关切换**，量化两路径的延迟差距与手感差异，作为「SDK 渲染路线是否替换为 Ink」的**对照决策宿主**。

**仓库拓扑（本计划的正确性前提）**：

- `demo`（本仓库，SDK = dgc_paint）→ 作为 paint-android 的 `sdk/` submodule（`.gitmodules` 指向 `paintDemo.git`，branch=main，`--remote` 跟随最新）。
- `paint-android`（消费者仓库，改动主体在本仓）：`app/` 持有 Compose UI + JNI（`PaintNative`），`sdk/` submodule 提供 `libdgc_paint.so`。
- **A8-1 全部代码改动落在 paint-android**；demo/SDK 侧**零 diff**（仅本计划文档落在 demo `docs/plans/`，属正常文档流程，非代码改动）。

**方向（brainstorming 结论，已核实）**：ink 内置 modeler 与 SDK `core/stroke_predictor`（B1-5 白盒移植）同算法，换预测无功能收益；真正差异在**渲染**——ink 以矢量 mesh 低延迟上屏、无像素 readback；SDK 现路径是 Vulkan 离屏 → readback（3.1MB memcpy）→ 贴图。故方向为 **ink 拿延迟收益 + SDK 路径原样保留作基线**。

## 3. SDK 工程约束（必含）

> 本任务**不触碰 dgc_paint 库任何代码**（零 diff），故下述约束为**不变式守卫**——RAII/Pimpl/Sanitize 因「零改动」而**平凡满足**，但须显式声明并落到验收/风险，防止执行期手滑碰 SDK。

### 3.1 所有权设计（RAII）

- dgc_paint 内所有权一律 RAII，禁止裸 `new`/`delete` 持有所有权；用 `std::make_unique`/`std::unique_ptr`（以及内部 `std::shared_ptr` 仅限确需共享的资源）。
- **本计划结论**：不新增、不修改任何 dgc_paint 所有权代码。Mode A 沿用现有 `DgcContext`（`dgcCreate`/`dgcDestroy` 生命周期由 JNI 层 `PaintNative.nativeInit/nativeDestroy` 管理），Mode B 完全在 Kotlin/Compose 侧（`InProgressStrokes` 自管输入与渲染），不产生跨 JNI 的新所有权。

### 3.2 Pimpl 边界（对外 ABI 面）

- 对外功能一律经不透明句柄：`sdk_api/dgc_paint_c_api.h` 的 `typedef struct DgcContext DgcContext;`（不透明句柄，实现细节藏于 `.cpp`）。消费端只看到句柄 + C 函数，看不到 C++ 类/虚接口。
- **本计划结论**：不新增、不修改 C API。Mode B 不经 SDK C API（ink 自绘），故不扩展句柄面；Mode A 的 JNI 调用点原样保留。

### 3.3 泄漏验证方式（DGCPAIN_SANITIZE）

- 现有 `CMakeLists.txt` 提供 `option(DGCPAIN_SANITIZE ...)`，host GCC/Clang debug 下开启 ASan + LSan（`-fsanitize=address,leak`）；Android NDK 下 LSan 不可用，显式排除。
- **本计划结论**：本任务零 SDK 改动，故不触发新的 sanitize 跑测需求；作为回归守卫，R3 的「SDK 零 diff」已覆盖「不引入新泄漏/新所有权」这一层。若执行期被迫触碰 SDK（见 3.4），必须同时跑 `DGCPAIN_SANITIZE=ON` 的 host 构建 + 相关单测。

### 3.4 「如需触碰 SDK，先停下」硬规则

- 本计划**零 SDK 改动**是结论而非假设：ink 渲染路径是 Android-only 的 Compose 侧 mesh 上屏，与 SDK 的 Vulkan 离屏架构正交，无任何理由改 `core/`、`render/`、`kernels/`、`sdk_api/`。
- 若执行期发现必须改 SDK（例如「想给 SDK 加一个 `IRenderBackend` 实现 ink」），**立即停下**：那属于「替换」而非「对照」，超出本任务边界（见 §6 非目标），需回 build-pipeline 重新 brainstorm，不得在本任务内擅自改动。

## 5. 实施步骤（task 级，沿用既有 plan 的分解）

> 详细逐 step 代码与命令见 `docs/plans/ink-rendering-android-ab.md`，此处给步骤骨架 + 本计划新增的约束点。所有构建命令以 paint-android 为 cwd。

### Task 1 — 引入 androidx.ink 1.0.0 + minSdk 核实

1. `app/build.gradle.kts` 追加 ink 依赖集（`ink-nativeloader` / `ink-rendering` / `ink-strokes` / `ink-authoring-compose` / `ink-brush-compose` / `ink-geometry-compose` / `ink-storage`，统一 `1.0.0`，禁 rc/alpha）。
2. `./gradlew :app:assembleDebug` 确认依赖解析。
3. **minSdk 核实**：解包 ink AAR 的 `AndroidManifest.xml` 读 `minSdkVersion`，与 `minSdk=26` 对齐。结论落报告（`docs/ink-ab-comparison.md`）。见 §7 取舍-1（bump vs API 门控，不静默选）。

### Task 2 — 模式开关 + ink 渲染路径（能画，R1/R2）

1. 核实 `InProgressStrokes`/`StockBrushes`/`CanvasStrokeRenderer` 的 1.0.0 确切签名（唯一外部 API 面，照官方参考，不占位）。
2. 新建 `InkStrokeCanvas.kt`（`InProgressStrokes` + 默认 `StockBrushes` 钢笔类刷）。
3. `PaintScreen.kt` 加 `internal enum class RenderMode { SDK, INK }` + `remember { mutableStateOf(RenderMode.SDK) }` + 顶部开关（右上角「⚙ 参数」上方同款样式）。
4. 画布层分支：INK 走 `InkStrokeCanvas`，SDK 走原 `Canvas.drawImage`。
   - **新增约束（对照正确性关键，非性能优化）**：切到 INK 时，外层 `detectDragGestures`（喂 SDK 的 `nativeStrokeBegin/To/End`）必须短路——否则 ink 上屏的同时 SDK 仍在离屏渲染+readback，既浪费又造成 ink 笔迹与 SDK bitmap 叠加/双笔。实现：把外层 `pointerInput`/读回触发按 `renderMode == SDK` 短路，或让 ink 模式的 `InProgressStrokes` 自建输入层独占（二者取一，见 §7 取舍-5）。
5. `./gradlew :app:assembleDebug` + 真机：切 Mode B 画一笔可见（R1），切回 SDK 原链路正常（R2/R3 部分）。

### Task 3 — 延迟/手感测量埋点（TDD，R4）

1. 写失败测试 `LatencyMetricsTest.kt`（`FrameTimeAccumulator.p50/p99`、空样本返 0、`LatencyProbe.avgLagMs`、无输入先上屏忽略）。
2. 跑 `:app:testDebugUnitTest --tests "LatencyMetricsTest"` 确认失败。
3. 实现 `LatencyMetrics.kt`（`FrameTimeAccumulator` + `LatencyProbe`，纯 Kotlin，无 Android 依赖）。
4. 跑测试确认 4 用例全绿。
5. 接入 `PaintScreen` 两模式：
   - SDK：`onDragStart/onDrag` 调 `lagProbe.onInput(...)`，readback 成功路径调 `lagProbe.onFramePresented(...)`，vsync 循环记每帧 `frameAcc.record(...)`；`readMs` 沿用现有。
   - INK：记帧时（vsync 循环已覆盖）；延迟代理标注「不适用（无 readback）」，HUD `readMs=0`。
6. HUD 按模式输出：SDK `FPS / Frame(p50/p99) / Readback`；INK `FPS / Frame(p50/p99) / Readback: n/a(无readback)`。

### Task 4 — 离屏输出图像（硬约束，R5）

1. 核实 `CanvasStrokeRenderer.create/draw` 签名（照参考，`create` 是否接受 null `TextureBitmapStore`、`AffineTransform.identity()` 构造）。
2. 新建 `InkPngExporter.kt`：on-device 已完成笔画经 `CanvasStrokeRenderer.draw` → Bitmap 背的 Canvas → `compress(PNG)`。
3. INK 模式 HUD 加「导出 PNG」，收集 `onStrokesFinished` 累积笔画，导出到 `filesDir/ink_snapshot.png`。
4. **SDK 基线复用（不改 SDK）**：host 上 `demo/build/host-linux/cli/dgc_cli`（或先 `cmake --build build/host-linux`）跑同一脚本离屏 → PNG，作为 Mode A 执行图像。

### Task 5 — 真机 A/B 验收 + 对比报告（R6，人工为主）

1. 同一设备（记录型号/刷新率）两模式各采一组：连续画 20s，记 Frame p50/p99 + Readback + avgLag，各 3 轮取中位。
2. 手感对照：同一手势（快速直线/圈/折线/快速点画）两模式各画，人工记「领先/滞后/抖动」。
3. 写 `docs/ink-ab-comparison.md`：设备信息、两模式延迟对比表、手感结论、minSdk 约束、是否值得换渲染的结论与建议。

## 6. 非目标（明确不做）

- 不改 demo / `sdk/` submodule 任何代码（`core/stroke_predictor.*`、`render/*`、`kernels/*`、`sdk_api/*`）。
- 不评估画笔效果、不评估预测保真（SDK stroke modeler 与 ink modeler 同算法，已核实等价）。
- 不把 ink 打进 SDK 作新 `IRenderBackend`（延迟收益在消费端 mesh 上屏，不在 SDK 离屏架构内）。

- **主路是应用内开关**；独立 APK 锁死 ink 仅作退路，非主交付。

## 7. 冲突与取舍（≥2 个站得住脚的方案，均不静默选）

### 取舍-1：minSdk —— bump minSdk vs API 门控（**待 Task 1 Step 3 实测后定夺**）

- 背景：ink 1.0.0 的 `android.graphics.Mesh` 是 API 34 引入，paint-android 现 `minSdk=26`。
- 方案 A（bump minSdk=34）：简单，但放弃 API 26–33 设备覆盖。
- 方案 B（API 门控）：minSdk 保持 26，INK 模式仅 `Build.VERSION.SDK_INT >= inkMinSdk` 可用，低版本显示「本机不支持 ink」占位。
- 任务书原文「需 bump 或 API 门控」两案并列授权，**本计划不预设结论**，Task 1 Step 3 实测 ink 实际 minSdk 后选，并记入对比报告。

### 取舍-2：模型器等价下的潜在混杂（**明确标注，非静默**）

- 对照目标是「渲染路径延迟」，但 SDK 模式用 SDK stroke modeler、ink 模式用 ink 内置 modeler；两者同算法（B1-5 白盒移植），但实现/调校可能微差，延迟差**混杂了模型器差异**。
- 方案 A（照现状：各用各的 modeler）：公平反映「整条路径端到端」差异，正对决策意图（「整条 SDK 渲染路线要不要换 ink」），且忠实 ink 的「零延迟端到端」卖点。
- 方案 B（两模式统一用 SDK modeler 输出点喂 ink 渲染）：可纯隔离渲染差异，但 `InProgressStrokes` 自含输入+modeler，无法轻易注入外部 modeler 输出，工程量剧增且破坏 ink 卖点，**工程上不可行/不忠实**。
- **结论**：选 A（默认，与既有 plan 一致），但报告须注明「延迟差含渲染+模型器综合差异；模型器已核实同算法，预计贡献可忽略」。不静默宣称「纯渲染差异」。

### 取舍-3：延迟代理 vs 真 input-to-photon（**明确标注，非静默**）

- `LatencyProbe` 是「输入→帧」代理，非严格 input-to-photon（后者需 Perfetto trace 或高速相机）。
- 主路用代理（可自动化、可 TDD、可脚本化），真机手感人工为准；报告如实标注代理性质，不把代理值当真实端到端延迟。

### 取舍-4：应用内开关（主）vs 独立 APK 锁死 ink（退路）

- 任务书已定案：主交付 = 应用内开关；独立 APK（`buildConfigField` 锁 `DEFAULT_RENDER_MODE`）仅退路。非取舍，记录以闭合。

### 取舍-5：INK 模式下 SDK 输入层短路方式（**需在 Task 2 Step 4 落实其一**）

- 切 INK 后，外层 `detectDragGestures`（喂 SDK）与 `InProgressStrokes`（ink 自建输入层）并存时存在双重消费/双笔风险。
- 方案 A：外层 `pointerInput` 按 `renderMode == SDK` 短路（INK 模式完全不喂 SDK，readback worker 因 `dirty` 恒 false 自然停摆）。
- 方案 B：依赖 `InProgressStrokes` 内部吞掉输入、外层不 consume（风险：Compose 指针分发语义下不可靠）。
- **结论**：选 A（显式短路，对照正确性关键，见 Task 2 Step 4 约束），方案 B 仅作真机观察到的兜底说明。**此为对照正确性而非性能优化，不属「绕开既有优化」**。

## 8. 约束核查：不绕开/不削弱既有优化

对照本项目 memory 与 P7 系列/性能优化决策，逐项确认本方案为**加法（并行路径）**而非减法：

| 既有优化（Mode A / SDK 路径） | 落点 | 本方案影响 |
|---|---|---|
| 批量 composite + 包围盒 dispatch（Mali 174→2.4ms） | `render/vulkan` 内核 | 不触碰；Mode A 原样 |
| readback HOST_CACHED + invalidate（memcpy 10→0.9ms） | SDK 读回路径 | 不触碰 |
| P7-1 非阻塞 readback（catch-up 取代阻塞 flush） | SDK 读回 | 不触碰 |
| P7-2 读回节流（打散批量修复） | `ReadbackScheduler` | 不触碰；文件原样 |
| P7-3 双缓冲 + 后台 readback + vsync 解耦 | `PaintScreen` + `ReadbackScheduler` | 不触碰；INK 模式分支之外原样 |
| P7-4 真实时间戳 `dgcStrokeToAt` | JNI + SDK | 不触碰 |

**结论**：Mode B（ink）是新增的**并行**渲染路径，天然无 readback/无 Vulkan 离屏，与上述全部优化正交；本计划**不删除、不修改、不短路 Mode A 的任何既有路径**（Task 2 Step 4 的「INK 短路 SDK 输入」是**模式切换的正确性要求**，不是对 Mode A 的削弱——切回 SDK 即恢复全链路）。**未发现与既有优化/架构的实质冲突**。

**唯一需警惕的回归风险**：INK 模式下 Mode A 的 `LaunchedEffect(Unit)`（vsync 循环 / readback worker）仍常驻生命周期。若输入未短路，`dirty` 会被置 true 导致 readback 持续跑——这正是取舍-5 必须显式短路的原因；短路的只是「喂输入」，worker 逻辑本身不动。

## 10. 风险
