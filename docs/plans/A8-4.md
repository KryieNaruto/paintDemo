## 1. 背景与验证假设

`docs/plans/A8-3.md` + spec §8.2 真机（MDP1221）实测已经证伪「消费端读回调用频率/SDK 读回
调度是瓶颈」这个假设：`ReadbackScheduler.DEFAULT_MIN_INTERVAL_NS` 从 16ms 放宽到 4ms（4x），
「输入→上屏」lag（`drawLagProbe`）**完全不变**（16ms→16ms），「输入→读回」lag（`lagProbe`）
反而从 6ms 恶化到 12ms。spec §8.2 给出的解释：`drawLagProbe - lagProbe`（Compose 重组/draw
调度那一段）随读回变快而**此消彼长地扩大**（10ms→4ms），但**总量恒为 16ms**——这是「下游有
一个不随上游提速而提前的硬性 vsync 边界」的典型 signature。

`PaintScreen.kt` 现有链路（`bitmap = back` 那行注释已经写明）：

```
读回完成（后台线程 memcpy）
  → 回主线程写 Compose 状态 `bitmap = back`（mutableStateOf 判等恒 false）
  → 等下一次 Choreographer 帧回调（withFrameNanos）
  → snapshot 生效 → 触发 recompose
  → layout（Canvas 尺寸/zoom 相关）
  → draw phase 真正执行 `drawImage`（`drawLagProbe.onFramePresented()` 打点处）
  → Compose 提交给 SurfaceFlinger
```

**本任务要验证的假设**：上面这条链路里，「等下一次 Choreographer 帧回调 → recompose →
layout → draw」这几步，比 Jetpack Ink（`InProgressStrokes`，HWUI 前缓冲直绘，A8-1 已确认
其「输入→上屏」lag 只有 4-6ms）多付出的调度开销，是 16ms 与 4-6ms 之间那段差距的主要来源
之一。验证手段：换成 `SurfaceView`（在拿到新读回像素的**同一个后台线程调用序列里**直接
`lockCanvas()`/`drawBitmap()`/`unlockCanvasAndPost()`），完全跳过 `mutableStateOf` 写入 +
等 Choreographer 帧回调 + recompose + layout 这几步，只保留必要的 draw 操作本身，测「输入→
上屏」lag 是否显著低于 16ms。

**如实的心理预期声明（避免选择性解读数据）**：SurfaceView 直绘依然要等 `unlockCanvasAndPost`
之后由系统合成/SurfaceFlinger 在下一个 vsync 呈现——它省掉的是**应用侧**的调度排队（Compose
状态派发 + recompose + layout），不省掉物理 vsync 本身。如果 16ms 的真正主因是"物理 vsync
扫描"（60Hz 屏幕的硬限制）而不是"Compose 应用侧排队"，那么换 SurfaceView **不会有明显改善**
——这正是本任务要证实或证伪的问题，计划本身不预设答案。

## 3. 设计

### 3.1 `RenderMode` 三态：新增 `SDK_SURFACE_VIEW`

```kotlin
internal enum class RenderMode { SDK, SDK_SURFACE_VIEW, INK }
```

- `SDK`（现状，Compose `Canvas`+`drawImage`）与 `INK`（Jetpack Ink）**逻辑零改动**——三态
  切换开关（现有顶部「渲染: SDK（点按切换）」文字按钮）改为三段循环
  `SDK → SDK_SURFACE_VIEW → INK → SDK`，切换时机与现有逻辑一致（切离 SDK 前收尾进行中
  笔画、`lagProbe.clear()`/`drawLagProbe.clear()`/`frameAcc.clear()` 重置样本、切回 SDK 系
  `dirty = true`——`SDK_SURFACE_VIEW` 归入「SDK 系」，共享这几条收尾规则）。
- `SDK_SURFACE_VIEW` 复用 **与 `SDK` 完全相同**的输入处理/JNI 调用路径（`nativeStrokeBegin`/
  `nativeStrokeToAt`/`nativeStrokeEnd`、`dirty`/`strokeActive`/`scheduler.onInput()` 等），
  只有「读回像素如何显示」这一步不同。实现上把 `pointerInput` 块里 `renderMode == RenderMode.SDK`
  的分支条件改为 `renderMode == RenderMode.SDK || renderMode == RenderMode.SDK_SURFACE_VIEW`
  （或提炼成一个 `val isSdkFamily = renderMode != RenderMode.INK` 局部变量，在 `clearCanvas`/
  预测开关按钮可见性/HUD 文案分支等多处复用，减少散落的枚举比较）。

### 3.2 呈现路径：`PaintSurfaceHost.kt`（新文件）

新增纯 Kotlin 辅助函数（可 JVM 单测，无 Android 依赖）：

```kotlin
/** 给定 Surface 物理尺寸与画布逻辑尺寸+缩放，算出 drawBitmap 的 src/dst 矩形（整数像素）。
 *  镜像 Coords.kt computeCanvasViewport 的语义（居中子视口），返回值供调用方构造
 *  android.graphics.Rect（本函数不依赖 android.graphics，保持纯 Kotlin 可测）。 */
internal data class SurfaceDrawRects(
    val srcLeft: Int, val srcTop: Int, val srcRight: Int, val srcBottom: Int,
    val dstLeft: Int, val dstTop: Int, val dstRight: Int, val dstBottom: Int,
)

internal fun computeSurfaceDrawRects(
    surfaceW: Int, surfaceH: Int,
    canvasW: Float, canvasH: Float, zoom: Float,
): SurfaceDrawRects {
    val (vx, vy, vw, vh) = computeCanvasViewport(canvasW, canvasH, zoom)   // 复用 Coords.kt
    return SurfaceDrawRects(
        srcLeft = vx.toInt(), srcTop = vy.toInt(),
        srcRight = (vx + vw).toInt().coerceAtLeast(vx.toInt() + 1),
        srcBottom = (vy + vh).toInt().coerceAtLeast(vy.toInt() + 1),
        dstLeft = 0, dstTop = 0, dstRight = surfaceW, dstBottom = surfaceH,
    )
}
```

- `computeSurfaceDrawRects` 与 Compose 路径 `drawImage(srcOffset/srcSize/dstSize)` 的算法
  等价（同一个 `computeCanvasViewport`），保证 **D6-2 缩放/居中视口在两条呈现路径下行为
  一致**——这是人工背景 6 提出的第二个风险点的解决方案：不重新设计缩放逻辑，只是把已经
  验证过的纯函数结果喂给不同的绘制 API。
- Android 侧薄封装（不做纯函数单测，真机人工验收覆盖）：

```kotlin
/** 在调用方所在线程（约定：readbackDispatcher 单线程，序列化调用，不与其它线程并发
 *  lockCanvas）里，把 [bitmap] 直接画到 [holder] 持有的 Surface 上。holder 为 null
 *  （Surface 尚未创建/已销毁）时安全跳过，返回 false。 */
internal fun presentBitmapToSurface(
    holder: SurfaceHolder?, bitmap: Bitmap, canvasW: Float, canvasH: Float, zoom: Float,
): Boolean {
    val h = holder ?: return false
    val canvas = try { h.lockCanvas() } catch (e: Exception) { return false } ?: return false
    try {
        val r = computeSurfaceDrawRects(canvas.width, canvas.height, canvasW, canvasH, zoom)
        canvas.drawBitmap(
            bitmap,
            android.graphics.Rect(r.srcLeft, r.srcTop, r.srcRight, r.srcBottom),
            android.graphics.Rect(r.dstLeft, r.dstTop, r.dstRight, r.dstBottom),
            null,
        )
    } finally {
        h.unlockCanvasAndPost(canvas)
    }
    return true
}
```

- 异常兜底（`lockCanvas` 在 Surface 尚未 ready/已销毁时可能返回 null 或抛异常）：本函数内
  跳过本次呈现、返回 `false`、不崩溃（`lockCanvas`/`unlockCanvasAndPost` 用 `try/finally`
  严格配对，见 §7.3）——**本函数自身不重试**；「Surface 尚未 ready」这一种情况由 §3.3 读回
  worker 层兜底（`presented == false` 时不清 `dirty`，下一轮读回周期重试，见 §9 R3 已实现
  的小补丁），已消耗的 readback 仍计入 `ReadbackScheduler` 节流预算，不会忙等。双缓冲语义
  保证不丢数据（只是可能跳过一帧显示，对 correctness 无影响）。

### 3.3 `PaintScreen.kt` 接线

- `Box` 内新增分支（放在现有 `when (renderMode)` 里，`SDK` 与 `INK` 分支之间，位于 Compose
  子节点列表中**其它 HUD/按钮之前**，保证叠加顺序——Compose 同一 `Box` 内后声明的子节点在
  Z 序上绘制在先声明子节点之上，`AndroidView` 与普通 Compose View 混排时同样遵循这个顺序，
  这是人工背景 6 第一个风险点的默认解法，§6 会用真机人工验证是否需要额外 Z 序处理）：

```kotlin
RenderMode.SDK_SURFACE_VIEW -> {
    AndroidView(
        modifier = Modifier.fillMaxSize(),
        factory = { context ->
            SurfaceView(context).apply {
                holder.addCallback(object : SurfaceHolder.Callback {
                    override fun surfaceCreated(h: SurfaceHolder) { surfaceHolderRef.value = h }
                    override fun surfaceChanged(h: SurfaceHolder, f: Int, w: Int, ht: Int) {}
                    override fun surfaceDestroyed(h: SurfaceHolder) { surfaceHolderRef.value = null }
                })
            }
        },
    )
}
```

  其中 `surfaceHolderRef = remember { Ref<SurfaceHolder?>(null) }`（普通引用，非 Compose
  state——与现有 `lastDrawnBitmap` 同款写法，写入不触发重组）。

  **`Ref` 加 `@Volatile`（未提交修复，须随实现一并提交）**：`surfaceHolderRef` 写在主线程
  `SurfaceHolder.Callback` 回调里、读在 `readbackDispatcher` 后台 IO 线程的
  `presentBitmapToSurface` 调用里，是跨线程无显式同步的读写——纯 Kotlin `var` 字段在 JMM 下
  不保证跨线程可见性（`withContext` 只为同一协程调用链建立 happens-before，不覆盖 Android
  框架在另一线程发起的外部回调写入）。真机（MTK MDP1221）复现为「切到 SurfaceView 模式后
  画布持续黑屏，直到另一次无关的主线程写入才把可见性带过来」，`@Volatile` 消除这个陈旧读。
  `Ref` 类实现改为 `private class Ref<T>(@Volatile var value: T)`（其余单线程用途如
  `lastDrawnBitmap` 无副作用，只是多一层保险）。

- 读回 worker 内新增分支（`withContext(readbackDispatcher) { ... }` 块里，memcpy 完成之后，
  仍在后台线程内）。实际落地（`085d03f` + 未提交修复）如下，`presented` 标志是未提交修复
  新增的（见本小节末尾说明）：

```kotlin
val (rc, ms, presented) = withContext(readbackDispatcher) {
    val rb0 = System.nanoTime()
    val r = ctx.nativeReadback(rbBuf)
    val rb1 = System.nanoTime()
    val m = (rb1 - rb0) / 1_000_000f
    var p = true   // 非 SDK_SURFACE_VIEW 路径无「呈现」这一步，恒视为已完成
    if (r == 0) {
        rbBuf.rewind()
        back.copyPixelsFromBuffer(rbBuf)
        if (renderMode == RenderMode.SDK_SURFACE_VIEW) {
            // 核心验证点：呈现发生在同一后台线程调用序列里，不经 mutableStateOf/
            // Compose 状态派发/等 Choreographer 帧回调/recompose/layout。
            p = presentBitmapToSurface(surfaceHolderRef.value, back, cw.toFloat(), ch.toFloat(), currentZoom)
            // 只在真正呈现成功（unlockCanvasAndPost 已调用）时才打点，否则会把「压根没上屏
            // 的一帧」记成已上屏，污染核心交付物的延迟数字（诚实口径，见 §8.3）。
            if (p) drawLagProbe.onFramePresented()
        }
    }
    Triple(r, m, p)
}
readMs = ms
if (rc == 0 && presented) {
    if (renderMode != RenderMode.SDK_SURFACE_VIEW) {
        bitmap = back               // 仅 Compose 路径才写状态触发 recompose
    } else {
        lastPresentedSurfaceBitmap.value = back   // 非 Compose state，纯引用记录
    }
    lagProbe.onFramePresented()
    scheduler.onReadbackComplete()
    dirty = false
    retry = false
} else if (rc == 0) {
    // §9 R3：readback 本身成功，但 SurfaceView 尚未 ready（切模式瞬间的正常竞态，holder 为
    // null 或 lockCanvas 失败）——不清 dirty，回到循环头（受 scheduler 节流约束，不会忙等）
    // 重试呈现，直到真正画到屏幕上为止；已消耗的 readback 仍计入节流预算，避免与真实失败
    // 路径一样反复打读回。
    scheduler.onReadbackComplete()
} else { ... 不变 ... }
```

  **未提交修复说明（须随实现一并提交）**：`presented` 标志 + `rc == 0 && presented` 判定 +
  `else if (rc == 0)` 重试分支，以及上一小节的 `@Volatile`，是 `085d03f` 之后针对真机
  MDP1221 复现的「切到 SurfaceView 后持续黑屏」补充的修复——`085d03f` 原提交里
  `presentBitmapToSurface` 的返回值被丢弃、`drawLagProbe.onFramePresented()` 无条件打点、
  holder 未 ready 时也照常清 `dirty`（导致首帧缺失后不再补画）。修复前真机表现为黑屏/打点
  口径失真，修复后「Surface 未 ready 不清 `dirty` 重试」+「只在真正上屏才打点」，与本计划
  §8.3 诚实口径和 §9 R3 的小补丁预期一致。

- `backBufferFor` 的 `current` 参数：Compose 路径用 `bitmap`（Compose state）；
  `SDK_SURFACE_VIEW` 路径改用 `lastPresentedSurfaceBitmap.value`（普通 `Ref`，与
  `lastDrawnBitmap` 同款）。两条路径共享同一对 `bmpA`/`bmpB` 物理缓冲，但各自维护自己的
  「当前前台是哪块」记录——因为 `renderMode` 单值互斥（同一时刻只有一条路径在跑读回
  worker 的对应分支），不会出现两套记录同时写同一缓冲的并发问题。取 `back` 的那行改为：

```kotlin
val current: Bitmap? = if (renderMode == RenderMode.SDK_SURFACE_VIEW)
    lastPresentedSurfaceBitmap.value else bitmap
val back = backBufferFor(current, bmpA, bmpB)
```

- **为什么不干脆保留 `bitmap = back` 顺手也写一下**：写了就会触发一次 Compose 重组（哪怕
  `SDK_SURFACE_VIEW` 分支里没人读 `bitmap` 拿去 `drawImage`），这恰恰是本任务要验证「跳过
  与不跳过 Compose 派发有没有区别」的自变量，必须严格跳过，否则实验对照就失真。

### 3.4 HUD 扩展（复用现有文案结构，不新增探针语义）

  此协议，本任务沿用）。
- 不允许选择性只报告"改善"的那次测量、丢弃"无改善"的重复测量样本——真机测量应重复至少
  2-3 次挥摆取稳定读数（HUD 数字本身已是均值，见 `LatencyProbe.avgLagMs()`），若同一模式
  下多次测量数字有较大波动，如实记录范围而非只取最有利的一次。
- 不允许通过修改 `drawLagProbe`/`lagProbe` 的打点位置语义来人为制造"改善"的假象——本任务
  `drawLagProbe.onFramePresented()` 在 `SDK_SURFACE_VIEW` 分支里的打点位置（`presentBitmap
  ToSurface` 调用之后）必须与 `SDK` 分支里的打点位置（`drawImage` 真正执行那一刻）在语义
  上对等——都是"这条路径认为的、像素真正被提交去显示的那一刻"，不能一边卡得早一边卡得晚
  制造不公平对比。
- **已落地（未提交修复）的诚实口径强化**：`SDK_SURFACE_VIEW` 分支的
  `drawLagProbe.onFramePresented()` 现改为**只在 `presentBitmapToSurface` 返回 `true`
  （真正完成 `unlockCanvasAndPost`）时才打点**——避免把「Surface 未 ready、压根没上屏的
  一帧」记成已上屏而虚报延迟改善。这与 `SDK` 分支「`drawImage` 真正执行那一刻」的口径对等
  （都是「像素真的被提交去显示」而非「试图提交但失败」），是 §8.3 原则的正向落地。

## 9. 风险与取舍

- **R1（最高）Compose+SurfaceView 混排 compositing 异常**（人工背景 6 风险点 1）：
  `AndroidView` 包裹的 `SurfaceView` 与其它 Compose 子节点（HUD/按钮/面板）共存在同一
  `Box` 里，理论上遵循 Compose 声明顺序的 Z 序叠加（标准做法，视频播放器等场景常见），
  但 Compose-AndroidView-SurfaceView 三层嵌套在不同 Compose 版本/OEM ROM 上historically
  有过零星 clipping/闪烁/事件穿透问题的报告，**未在本仓库验证过**。**取舍**：先按标准写法
  实现，真机验证（§5 步骤 6a）；若出现问题，备选 `TextureView`（普通 View 纹理合成，
  与 Compose 交互更可预测，但代价是它经过常规 View 绘制管线合成——**这会部分削弱本任务
  要验证的"跳过应用侧调度"效果**，需要在结论里明确注明「若最终用 TextureView 测得的
  改善/无改善，不能直接等同于 SurfaceView 假说的结论，因为 TextureView 本身的呈现路径
  与 SurfaceView 不同」）。优先 SurfaceView，只在验证性问题无法在预算内解决时才降级。
- **R2 双缓冲一致性**：`SDK_SURFACE_VIEW` 路径不写 `bitmap` Compose state，改用独立的
  `lastPresentedSurfaceBitmap`（`Ref`）追踪「当前前台」——若实现疏漏（如误用了
  `bitmap`），`backBufferFor` 会拿到错误的 `current` 判断，可能导致读回线程与
  正在展示的缓冲发生并发写（画面撕裂/闪烁）。**缓解**：§3.3 已明确设计取值逻辑，§6 真机
  笔迹正确性验证会暴露此类问题（撕裂/花屏肉眼可辨）。
- **R3 模式切换时序（小补丁已实现）**：从 `SDK`/`INK` 切到 `SDK_SURFACE_VIEW` 瞬间，
  `surfaceHolderRef` 可能还是 `null`（`AndroidView` 的 `factory`/`surfaceCreated` 回调有
  一次 Compose 组合→View 创建→Surface 创建的异步链路）——`presentBitmapToSurface` 已做 null
  兜底（返回 `false`），读回 worker 层**已实现小补丁**：`presented == false` 时不清 `dirty`、
  回到循环头重试（受 `ReadbackScheduler` 节流约束不忙等，已消耗的 readback 计入节流预算），
  直到真正画到屏幕上为止。真机验证仍需观察「切换到该模式后首帧出现的延迟」是否明显异常
  （若 holder 迟迟不 ready 导致长时间黑屏，说明 Surface 创建回调本身有问题，需另行排查）。
- **R4 验证结论的统计效力有限**：真机人工测量样本量小（几次挥摆），`drawLagProbe` 是
  均值不是分位数，与 A8-3 §8.5 讨论的"是否需要 p50/p99"是同一类权衡——本任务预期测到的
  是"16ms → 显著更低"或"16ms → 16ms"这种类别性差异（不是临界值判定），沿用 A8-3 §8.5
  的判断标准：只有当数字落在临界区间、单点读数不足以支撑判定时才需要补分位数统计，本
  计划不预先增加这个复杂度，执行阶段视真机数据实际落点决定是否需要。
- **R5 "验证性任务"被误解读为必须做出正面结论**：§8 已经用整节明确「无改善」是一个同样
  合法、同样需要被认真对待和记录的结果，执行阶段的 build-pipeline 审阅与 test-review 需要
  按这个标准评审（不能因为"没有改善数字不好看"就要求推翻或重做测量方法）。
- **R6 跨线程可见性（已发生并已修复的真实 bug）**：`surfaceHolderRef`（`Ref<SurfaceHolder?>`）
  写于主线程 `SurfaceHolder.Callback`、读于 `readbackDispatcher` 后台线程，纯 Kotlin `var`
  在 JMM 下不保证跨线程可见性——真机 MDP1221 复现为「切到 SurfaceView 后画布持续黑屏，直到
  另一次无关主线程写入才把可见性带过来」。**已修复**：`Ref` 类 `value` 字段加 `@Volatile`
  （未提交，须随实现一并提交）。这个 bug 是「Compose 状态派发本身隐含跨线程 happens-before，
  换成手工跨线程 `Ref` 后必须自己补同步」这一换路径副作用的直接体现——正是本任务验证要付出
  的一类代价，值得记录（若未来还有其它跨线程 `Ref`，须同样加 `@Volatile` 或改用原子/同步）。
