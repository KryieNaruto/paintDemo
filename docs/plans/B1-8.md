## 目标

把 `sdk_api` 与 `render` 中「裸 `new`/`delete` 手工管理所有权」收敛为「`std::unique_ptr` / `std::make_unique` 显式所有权 + RAII 析构」，全 SDK 除 `third_party` 外零裸 `new`/`delete` 所有权，并引入 ASan/LSan 构建开关与 create/destroy 压力测试证明零泄漏。C ABI 头 `sdk_api/dgc_paint_c_api.h` 一字不改，22 个函数签名不变，既有 ctest 全绿。

1. **DgcContext 经典 Pimpl**：`struct Impl; std::unique_ptr<Impl> impl_;`（`Impl` 定义留在 cpp 内），`Impl` 内 kernel/backend/engine 用 `std::unique_ptr` 持有；`dgcCreate` 用 `make_unique` + 栈上 `unique_ptr` 构建、失败自动回滚；`dgcDestroy` 幂等。
2. **工厂返回 `unique_ptr`**：`CreateDefaultRenderBackend()` 返回 `std::unique_ptr<IRenderBackend>`；`VkBackend` 构造用 `std::make_unique<Impl>()`。
3. **VkBackend RAII**：`VkBackend::Impl` 内约 20 个 Vulkan 裸句柄收敛为最小 RAII 守卫，析构/`shutdown()` 幂等。
4. **全 SDK 零裸 new/delete 所有权**（grep 验证，`third_party/stb` 等第三方除外）。
5. **C ABI 不变**：`dgc_paint_c_api.h` 22 函数签名一字不改，既有 ctest 全绿。
6. **CMake `DGCPAIN_SANITIZE`**：`-fsanitize=address,leak` 开关 + ctest 下 ASan/LSan 零泄漏。
7. **create/destroy 循环压力测试**：多轮无泄漏/无崩溃。

非目标：不改 `ui/` `platform/` `app/`；不新增消费者代码；不改 C API 头签名；不重构 `core/engine`（其 `IPaintKernel*/IRenderBackend*` 注入不拥有，本就无裸 new/delete）；不引入 vk::raii（Vulkan-Hpp 头未必可用，用手写最小 RAII 守卫）。

## 验收标准（人工授权派生，非任务书原文）

1. **DgcContext 经典 Pimpl**：`sdk_api/dgc_paint_c_api.cpp` 内 `struct DgcContext { struct Impl; std::unique_ptr<Impl> impl_; ~DgcContext(); };`（`Impl` 定义留在 cpp 内，析构器在 `Impl` 完整后 `= default`）；`Impl` 内 `kernel`/`backend`/`engine` 为 `std::unique_ptr<IPaintKernel>` / `std::unique_ptr<IRenderBackend>` / `std::unique_ptr<Engine>`；`dgcCreate` 用 `std::make_unique` + 栈上 `unique_ptr` 构建、任一构造/`start()` 抛异常时已建对象自动析构（不泄漏）；`dgcDestroy` 幂等（`nullptr` 安全、engine `stop()` 幂等、`impl_.reset()` 幂等），内部无裸 `delete`。
2. **工厂返回 unique_ptr**：`CreateDefaultRenderBackend()` 返回 `std::unique_ptr<IRenderBackend>`，内部 `std::make_unique<VkBackend>()` / `std::make_unique<NullRenderBackend>()`。
3. **VkBackend RAII**：`VkBackend::Impl` 内所有 Vulkan 句柄（instance/device/image/view/buffer/memory/sampler/fence/commandPool/pipeline/pipelineLayout/descriptorSetLayout/descriptorPool）由最小 RAII 守卫持有，析构按「子对象 → device → instance」顺序释放；`shutdown()` 幂等（重复调用安全，`vkDeviceWaitIdle` 后再释放）。
4. **零裸 new/delete 所有权**：`grep -rnE '\bnew\b|\bdelete\b' --include='*.h' --include='*.cpp' sdk_api render core` 命中项仅剩 `= delete`（删拷贝构造），无 `new X`/`delete x` 所有权表达式；`third_party/` 除外。
5. **C ABI 不变**：`sdk_api/dgc_paint_c_api.h` 与基线 `git diff` 为空（22 函数：`dgcCreate` `dgcDestroy` `dgcSetSurface` `dgcResize` `dgcBeginStroke` `dgcStrokeTo` `dgcEndStroke` `dgcCreateBrush` `dgcLoadBrushFromMyb` `dgcDestroyBrush` `dgcSetBrush` `dgcRender` `dgcClear` `dgcGetLastError` `dgcSetOffscreenSurface` `dgcExportPNG` `dgcReadbackPixels` `dgcSetRandomSeed` `dgcSetFixedTime` `dgcSetBrushSetting` `dgcSetBrushColor` `dgcUndo`）；既有 ctest（`compile_null` `test_ring_buffer` `test_engine` `test_c_api_header` `test_c_api_b1_6` `test_offscreen`）全绿。
6. **CMake `DGCPAIN_SANITIZE`**：顶层 `CMakeLists.txt` 新增 `option(DGCPAIN_SANITIZE ... OFF)`；开启时对库与测试统一加 `-fsanitize=address,leak -fno-omit-frame-pointer`（编译 + 链接）；该配置下 ctest 无 ASan/LSan 报错（Null 后端路径确定性零泄漏）。
7. **create/destroy 循环压力测试**：新增 `tests/test_ownership_loop`，循环多轮 `dgcCreate()` →（可选 `dgcSetOffscreenSurface`）→ `dgcDestroy()`，无泄漏、无崩溃、无 use-after-free/double-free。

## 所有权设计

### 当前问题（grep 实测）

```
sdk_api/dgc_paint_c_api.cpp:52  new DgcContext()
sdk_api/dgc_paint_c_api.cpp:53  new NullPaintKernel()
sdk_api/dgc_paint_c_api.cpp:55  new Engine(...)
sdk_api/dgc_paint_c_api.cpp:66-70  delete engine/backend/kernel/ctx
render/render_backend_factory.cpp:11/13  new VkBackend()/new NullRenderBackend()
render/vulkan/vk_backend.cpp:764  impl_(new Impl())
```

VkBackend::Impl 内另约 20 个裸 Vulkan 句柄靠手工 `DestroyDevice()` 逐个 `vkDestroyXxx`，顺序敏感、无异常安全、非 RAII。

### 目标所有权图

```
DgcContext (不透明句柄, cpp 内定义)
  └─ std::unique_ptr<Impl> impl_
       └─ Impl (cpp 内定义)
            ├─ std::unique_ptr<IPaintKernel>   kernel   (声明序①)
            ├─ std::unique_ptr<IRenderBackend> backend  (声明序②)
            ├─ std::unique_ptr<Engine>         engine   (声明序③)
            └─ 值成员: w/h/random_seed/fixed_time_us/fixed_time_set/
                       brush_settings/brush_colors
```

- `Engine` 构造仍收 `kernel.get()/backend.get()` 裸指针（**注入不拥有**，`core/engine.h` 注释已明确），所有权归属 `Impl` 的三个 `unique_ptr`。
- 成员**声明序** = `kernel` → `backend` → `engine`；C++ 按**逆声明序析构** = `engine`（先 stop/join 三线程，仍持有 kernel/backend 存活）→ `backend` → `kernel`。与现状 `engine→backend→kernel` 释放顺序一致。
- `DgcContext` 有 `unique_ptr<Impl>` 且 `Impl` 不完整，故析构器必须**在 cpp 内 `Impl` 完整后**定义（`DgcContext::~DgcContext() = default;`），否则隐式析构在头/声明处实例化会因不完整类型编译失败。

### Pimpl 边界

- 头 `dgc_paint_c_api.h` 仅 `typedef struct DgcContext DgcContext;`（不透明，**不改**）。
- cpp 内 `struct DgcContext { struct Impl; std::unique_ptr<Impl> impl_; ~DgcContext(); };`，`Impl` 与 `~DgcContext()` 定义紧随其后。
- 所有 `ctx->w/h/random_seed/.../brush_settings` 的直接访问点改为 `ctx->impl_->...`（机械替换，全 cpp 约 10 处）。

### VkBackend RAII 守卫（最小手写，不引入 vk::raii）

两类泛型守卫（值语义、禁拷贝、可移动、`reset()`/析构幂等）：

```cpp
// 顶层对象：vkDestroyInstance / vkDestroyDevice（2 参，无 parent device）
template <typename H, void (*Destroy)(H, const VkAllocationCallbacks*)>
struct VkTopHandle { H h = VK_NULL_HANDLE; /* reset()/release()/move 幂等 */ };

// 子对象：vkDestroyXxx / vkFreeMemory（3 参，需 device）
template <typename H, void (*Destroy)(VkDevice, H, const VkAllocationCallbacks*)>
struct VkDeviceHandle { VkDevice dev = VK_NULL_HANDLE; H h = VK_NULL_HANDLE; /* ... */ };
```

映射：`instance` → `VkTopHandle<VkInstance, vkDestroyInstance>`；`device` → `VkTopHandle<VkDevice, vkDestroyDevice>`；`image/view/buffer/sampler/fence/commandPool/pipeline/pipelineLayout/descriptorSetLayout/descriptorPool` → `VkDeviceHandle<…, vkDestroy…>`；`memory`（canvas/stamp/staging/readback）→ `VkDeviceHandle<VkDeviceMemory, vkFreeMemory>`。

`Impl` 成员**声明序** = `instance` → `device` → 全部子对象（canvas/stamp/staging/readback/fence/pipeline/pipelineLayout/descriptorLayout/sampler/commandPool/descriptorPool）。逆声明序析构 = 子对象 → `device` → `instance`，即释放顺序正确。`CreateCanvas/CreateStampTexture` 重建时 `guard.reset()` 后再装入新句柄（需给守卫提供 `reset()`/移动赋值）；原手工 `DestroyCanvas/DestroyStampTexture/DestroyDevice` 中的逐个 `vkDestroyXxx` 删除，仅保留 `DestroyDevice()` 的 `vkDeviceWaitIdle` + 复位 `deviceReady`。

### 泄漏验证方式

- **静态**：第 4 条 grep，确认非 third_party 源码无所有权 `new`/`delete` 令牌。
- **动态（ASan/LSan）**：`-DDGCPAIN_SANITIZE=ON` 构建，跑 `ctest`（重点 `test_ownership_loop`、`test_offscreen`）；Null 后端路径要求 LSan 零报告；Vulkan 后端路径见「风险」第 3 条（loader/ICD 可能贡献全局分配）。
- **压力**：`test_ownership_loop` 多轮 create/destroy 后进程退出，LSan 汇总零泄漏。

## 步骤

### 1. 工厂返回 unique_ptr

- `render/render_backend_factory.h`：`#include <memory>`；`std::unique_ptr<IRenderBackend> CreateDefaultRenderBackend();`
- `render/render_backend_factory.cpp`：`return std::make_unique<VkBackend>();` / `return std::make_unique<NullRenderBackend>();`

### 2. DgcContext Pimpl + dgcCreate/dgcDestroy 重写

`dgc_paint_c_api.cpp` 内：

```cpp
struct DgcContext {
    struct Impl;
    std::unique_ptr<Impl> impl_;
    ~DgcContext();
};

struct DgcContext::Impl {
    std::unique_ptr<IPaintKernel>   kernel;
    std::unique_ptr<IRenderBackend> backend;
    std::unique_ptr<Engine>         engine;
    int w = 0; int h = 0;
    uint64_t random_seed = 0;
    double fixed_time_us = 0.0;
    bool fixed_time_set = false;
    std::unordered_map<DgcBrush, std::array<double, DGC_SETTING_COUNT>> brush_settings;
    std::unordered_map<DgcBrush, std::array<float, 4>> brush_colors;
};

DgcContext::~DgcContext() = default;

DgcContext* dgcCreate(void) {
    g_last_error = DGC_OK;
    auto ctx  = std::make_unique<DgcContext>();
    auto impl = std::make_unique<DgcContext::Impl>();
    impl->kernel  = std::make_unique<NullPaintKernel>();
    impl->backend = CreateDefaultRenderBackend();          // unique_ptr<IRenderBackend>
    impl->engine  = std::make_unique<Engine>(impl->kernel.get(), impl->backend.get());
    impl->engine->start();
    ctx->impl_ = std::move(impl);
    return ctx.release();
}

void dgcDestroy(DgcContext* ctx) {
    if (ctx == nullptr) return;
    std::unique_ptr<DgcContext> guard(ctx);   // 无裸 delete；scope 末经析构器释放
    if (guard->impl_ && guard->impl_->engine) guard->impl_->engine->stop();  // 幂等
    guard->impl_.reset();                     // engine→backend→kernel 逆声明序析构
}
```

- 失败回滚：`make_unique`/`start()` 抛异常时 `ctx`、`impl`、`kernel`、`backend` 均为栈上 `unique_ptr`，自动析构，零泄漏。
- 全 cpp 其余函数 `ctx->w`/`ctx->h`/`ctx->random_seed`/`ctx->fixed_time_us`/`ctx->fixed_time_set`/`ctx->brush_settings`/`ctx->brush_colors` 改 `ctx->impl_->...`；`ctx->backend->...` 改 `ctx->impl_->backend->...`。

## 风险与备选

1. **Pimpl 析构器位置**：`unique_ptr<Impl>` + 不完整 `Impl` 必须把 `~DgcContext()` 定义在 `Impl` 完整之后，否则编译期报「incomplete type used in type trait/析构」。步骤 2 已按「cpp 内 `= default`」规避。
2. **引擎线程 vs 析构顺序**：`engine` 必须在 `kernel/backend` 前析构（其线程仍调用 backend）。靠 `Impl` 成员声明序 `kernel→backend→engine` 保证逆序析构 `engine→backend→kernel`；另 `dgcDestroy` 显式 `engine->stop()`（幂等）双保险。
3. **LSan 与 Vulkan loader/ICD 泄漏（最高风险）**：lavapipe/libvulkan 可能进程退出时残留全局分配，导致 Vulkan 后端路径 LSan 非零。对策：a) 压力测试的**零泄漏硬性结论以 Null 后端路径为准**（`-DDGCPAIN_RENDER_VULKAN=OFF` 下跑 `test_ownership_loop`，确定性零泄漏，证明 SDK 所有权重构本身无泄漏）；b) Vulkan 路径若报 loader/ICD 帧，用 `LSAN_OPTIONS=suppressions=<file>` 提供 `tests/lsan.supp` 屏蔽第三方帧，或仅对该用例 `ASAN_OPTIONS=detect_leaks=0` 并单独用 `test_offscreen` 的 create/destroy 冒烟 + 手动 `vkDestroyInstance` 顺序审查兜底。执行时优先 ASan（越界/UAF 检测）在 Vulkan 路径跑，LSan 零泄漏结论不因第三方 loader 单方否决本任务。
4. **`dgcDestroy` 幂等语义边界**：C ABI 下「同一指针调用两次 dgcDestroy」无法在 SDK 内拦截（调用方持有悬垂指针），真实承诺是「`nullptr` 安全 + 内部 stop/reset 幂等 + 无 double-free」；文档/头注释不承诺重复销毁同一非空指针安全。use-after-free 由 ASan 压力测试兜底（正常单次销毁路径）。
5. **`engine->start()` 半途抛异常**：`std::thread` 构造若第 2/3 个线程失败，已启动的 joinable thread 析构会 `std::terminate`。属 `Engine::start()` 既有行为（资源耗尽罕见），本任务不扩 scope；仅在步骤 2 注释说明，构建失败回滚只承诺「不泄漏对象」，不承诺「start 抛异常时优雅收线程」。
6. **VkBackend 守卫 move-in 细节**：`CreateImage/CreateBuffer/CreateImageView` 现为出参裸句柄 + 手工错误分支。RAII 化时若改为「函数返回句柄、守卫 move-in」，错误路径需保证半初始化句柄被守卫接管而非泄漏；若保留出参，则调用后立即装入守卫。二者皆可，执行时选「返回句柄 + 守卫 move-in」更 RAII 化，但需回归 `CreateCanvas` 的失败分支（`canvasImage==VK_NULL_HANDLE` 检查仍保留）。
7. **Windows/Android 的 sanitize**：`-fsanitize=address,leak` 仅 host Linux（GCC/Clang）支持；`DGCPAIN_SANITIZE` 在 MSVC 与 Android NDK 下以 `message(WARNING)` 降级，不破坏既有 `host-windows`/`android-arm64` preset（其默认 OFF）。
8. **`test_c_api_b1_6.c` 兼容**：离屏三函数在当前 Vulkan 开后返回 `DGC_OK`（B2-1 已接），压力测试 `dgcSetOffscreenSurface` 的返回码断言需在 Null/Vk 两配置下都成立（Null 后端 `supportsOffscreen()` 为 false → 返回 `NOT_IMPLEMENTED`）。压力测试对 offscreen 返回码只做「合法（OK 或 NOT_IMPLEMENTED）」，不硬断言 OK，避免 Null 配置下失败。
