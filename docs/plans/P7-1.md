## 1. 目标

`dgcReadbackPixels`/`dgcExportPNG` 改为对 `Engine::flush_requested_` 做**非阻塞置位**
（"catch up 一次、不等待"），彻底移除这两个入口上的阻塞 `engine->flush()` 调用；
`renderLoop()` 补一条不依赖 `flush_requested_`/队列判空的**攒批上限兜底**，防止连续
不间断输入下无界攒批；新增"真正连续不间断输入"回归测试，同时验证孔洞消失与
GUI 侧调用不再出现阻塞级尖峰。三线程编排（`inputLoop`/`brushLoop`/`renderLoop`）与
`VkBackend` 快照缓存机制保持不变，不引入新的跨线程阻塞等待。

## 4. 详细设计

### 4.1 `Engine::requestFlush()`（非阻塞 setter）

```cpp
// core/engine.h（新增公开方法，紧邻 flush() 声明）
// 非阻塞 catch-up（P7-1）：仅对 flush_requested_ 做一次 release store，立即返回，不等待
// 任何队列/composited_ 追平。用于 GUI/调用线程"顺路"催促渲染线程尽快找机会合批，
// 不像 flush() 那样阻塞到 drain 完成。可在引擎运行期间任意线程调用。
void requestFlush() noexcept;
```

```cpp
// core/engine.cpp
void Engine::requestFlush() noexcept {
    flush_requested_.store(true, std::memory_order_release);
}

void Engine::flush() {
    requestFlush();  // 复用，避免与原先内联的 store 重复
    // ...（drain 三段等待逻辑不变）
}
```

无堆分配、无锁、无跨线程等待——纯原子 store，`noexcept`。

### 4.2 `sdk_api/dgc_paint_c_api.cpp` 改法

`dgcReadbackPixels`（原逻辑保留，仅新增一行非阻塞 catch-up）：

```cpp
int dgcReadbackPixels(DgcContext* ctx, void* rgbaOut) {
    // ...既有 null/参数/能力校验不变...
    // P7-1：非阻塞 catch-up——顺路催促渲染线程尽快把已攒批合入下一次提交，供
    // VkBackend::cache_ 更快刷新；绝不等待（不调用 engine->flush()），故本调用
    // 耗时恒等于一次原子 store + 一次纯内存 memcpy，不随渲染线程攒批大小波动。
    if (ctx->impl_->engine->running()) {
        ctx->impl_->engine->requestFlush();
    }
    ctx->impl_->backend->readback(rgbaOut);
    g_last_error = DGC_OK;
    return DGC_OK;
}
```

`dgcExportPNG`（移除阻塞 `flush()`，改为同款非阻塞 catch-up；新增契约说明注释）：

```cpp
int dgcExportPNG(DgcContext* ctx, const char* path) {
    // ...既有 null/path/能力校验不变...
    // P7-1（契约变化）：不再阻塞 drain。导出内部走与 dgcReadbackPixels 相同的快照缓存，
    // 可能比最新输入落后 ≤1 个攒批周期（renderLoop 攒批上限兜底，见 engine.cpp，
    // 上限 kMaxBatchDuration）。调用方若需要"精确到最后一笔"的完整导出（如批处理
    // 脚本/CLI/确定性测试的 golden 对比），须显式先调 dgcFlush() 再调本函数——
    // 现有 cli/script_runner.cpp、tests/test_c_api_headless.c、tests/test_determinism.cpp
    // 均已遵循此模式（逐一核实见 §5 验证步骤），故此契约变化不破坏任何现有调用方。
    if (ctx->impl_->engine->running()) {
        ctx->impl_->engine->requestFlush();
    }
    ctx->impl_->backend->exportPNG(path);
    g_last_error = DGC_OK;
    return DGC_OK;
}
```

### 4.3 `renderLoop()` 攒批上限兜底

新增两个阈值常量（匿名命名空间，紧邻既有 `kMaxPendingInput`）：

```cpp
// 攒批上限兜底（P7-1）：连续不间断输入下 brush_to_render_ 理论上永不为空，仅靠
// "队列已空"这一条件永远等不到 flushBatch；flush_requested_ 仅由 GUI 侧
// dgcReadbackPixels/dgcExportPNG（非阻塞 catch-up）或 dgcFlush（drain）驱动，其调用
// 节奏与渲染线程攒批节奏彼此独立，存在"置位后被更快输入抢跑填满新一批"的窗口
// （任务书 P7-1 背景描述的病理）。故补第三条不依赖前两者的无条件触发：
//
//   kMaxBatchDurationMs = 4ms：PC 120fps 预算 8.33ms 的约 1/2、Android 60fps 预算
//   16.67ms 的约 1/4——保证 readback 快照缓存最大滞后远小于任一目标帧时间（不会
//   在人眼可感知窗口内出现孔洞），同时仍显著大于单次 GPU SubmitAndWait 的 ~0.73ms
//   开销（批量 composite 优化的根因一），多数正常绘制节奏下仍能攒到多个 stamp 再
//   提交，不退化回"每点一次提交"。
//   kMaxBatchStamps = 512：独立硬上限，兜底调度抖动导致时长检查被延迟的极端情况，
//   远高于 4ms 窗口内正常输入速率下的期望批大小。
constexpr std::size_t kMaxBatchStamps = 512;
constexpr auto kMaxBatchDurationMs = std::chrono::milliseconds(4);
```

`renderLoop()` 内维护 `batchStampCount`（累计 stamp 数）与 `batchStart`（本批首个
元素入列时刻，仅渲染线程本地读写，无需原子）：

```cpp
std::vector<RenderBatch> batch;
std::size_t batchStampCount = 0;
std::chrono::steady_clock::time_point batchStart{};

auto flushBatch = [&]() {
    // ...既有 flat/composite/present/composited_ 逻辑不变...
    batch.clear();
    batchStampCount = 0;  // 新增：随批一起清零
};

while (true) {
    if (stop_.load(...)) return;
    RenderBatch stamps;
    if (brush_to_render_.try_pop(stamps)) {
        if (batch.empty()) {
            batchStart = std::chrono::steady_clock::now();
        }
        batchStampCount += stamps.stamps.size();
        batch.push_back(std::move(stamps));
        // 三条触发条件（P7-1，原两条 + 新增兜底），任一满足即合批提交：
        //   1) flush_requested_ 已置位（drain 屏障 flush() 或非阻塞 requestFlush() 均可
        //      触发，语义仍是"尽快找机会合批"）；
        //   2) 攒批已超上限（本条新增：批 stamp 数 ≥ kMaxBatchStamps 或攒批时长
        //      ≥ kMaxBatchDurationMs），不依赖 1) 是否曾被置位；
        // （原"队列已空"条件见下方 try_pop 失败分支，为条件 3。）
        const bool requested = flush_requested_.exchange(false, std::memory_order_acq_rel);
        const bool overCap = batchStampCount >= kMaxBatchStamps ||
            (std::chrono::steady_clock::now() - batchStart) >= kMaxBatchDurationMs;
        if (requested || overCap) {
            flushBatch();
        }
        continue;
    }
    if (!batch.empty()) {
        flushBatch();  // 条件 3：队列已空，当前输入暂告一段落。
        continue;
    }
    std::this_thread::yield();
}
```

无新增跨线程等待：`batchStampCount`/`batchStart` 只被渲染线程自己读写；
`std::chrono::steady_clock::now()` 调用无锁、无阻塞。

### 4.4 新增回归测试 `tests/test_continuous_input_regression.cpp`

沿用 `test_readback_drain.cpp`/`test_perf_regression.cpp` 的结构与本地 `CountInk`
辅助函数（按仓库既有约定各测试文件各自复制一份小工具函数，不新增共享头）。

设计：

1. 256×256（或更大，如 512×512，覆盖更多攒批周期）离屏画布，白底清屏。
2. 后台线程 `producer`：`dgcBeginStroke` 后，紧凑循环提交约 600~800 个点（覆盖一条
   贯穿画布的长路径，如锯齿/螺旋，确保各处都有墨迹可验证），每点间 `sleep_for`
   200~500 微秒（保证 ≤1ms 节奏、SPSC 队列理论上不应观测为空），全程不调用
   `dgcFlush`；循环结束 `dgcEndStroke`，随后置位 `std::atomic<bool> producerDone`。
3. 前台线程（`main`，模拟 GUI 主循环）：在 `producerDone` 变为 true 前持续循环
   `dgcReadbackPixels`，每次调用前后用 `steady_clock` 记时；
   - 断言：无单次 `dgcReadbackPixels` 调用耗时超过一个远高于"纯内存拷贝"预期、
     但远低于历史阻塞病理（`d64c2fa` 前 max 41~104ms）的阈值——沿用
     `test_perf_regression.cpp` 的量级选取思路，取 `< 20ms`（与该文件的 50fps 安全
     阈值口径一致，避免自造新口径）；
   - 每次读回后 `CountInk` 记入采样序列 `inkSamples`。
4. `producer.join()` 后：
   - 断言 `inkSamples` 末尾若干个值（producer 收尾阶段）已达到较高比例的墨迹量
     （与下面第 5 步的权威值比较），证明"孔洞"不会长期存在；
   - 额外断言 `inkSamples` 总体呈上升趋势（如：后半程均值显著高于前半程均值），
     用于捕捉"长期卡在低墨迹量不动"的孔洞病理（而非仅看最终值）。
5. 权威对照：`dgcFlush(ctx)` + 一次 `dgcReadbackPixels` 得到 `inkFlushed`（完整画布）；
   断言 `producer.join()` 后、`dgcFlush` 前的最后一次采样值与 `inkFlushed` 的差值占比
   低于阈值（如 `<15%`——比 `test_readback_drain.cpp` 的 `<5%` 略宽松，因为本测试是
   "生产者刚结束、消费者还未来得及追上"的更严苛并发场景，5%/15% 两档均需在计划
   评审/执行阶段结合实测数据核定，不是随意数字：15% 上限仍要求"绝大多数已提交
   笔迹在生产者收尾时已合成"，与"大范围滞后/残缺"的任务书措辞对应）。
6. `dgcDestroy(ctx)`。

CMakeLists 注册位置：`tests/CMakeLists.txt` 内 `test_readback_drain`/
`test_midstroke_readback`/`test_perf_regression` 所在的
`DGCPAIN_RENDER_VULKAN AND ... render/vulkan/CMakeLists.txt` 守卫块，紧随
`test_perf_regression` 之后追加同款 `add_executable`/`target_include_directories`/
`target_link_libraries`/`add_test` 四联。

  测试惯例使用，不手写裸 `new`/`delete`）；`std::thread producer` 用 RAII 方式
  `join()`（不 `detach`），避免线程对象析构时仍 joinable 导致 `std::terminate`。
- **Pimpl 边界**：`Engine::requestFlush()` 是 `Engine` 类（内部实现类型，不跨 SDK
  外部 ABI 边界）新增的公开方法，只被同一 `.so`/`.a` 内的 `sdk_api/dgc_paint_c_api.cpp`
  调用；`DgcContext` 对外仍是不透明句柄，C API 函数签名不变，不引入新导出符号，
  ABI 面不受影响。
- **泄漏验证**：执行阶段需以 `-DDGCPAIN_SANITIZE=ON`（host GCC/Clang，见
  `CMakeLists.txt:32-41` 的 ASan+LSan 开关）重新构建并跑
  `ctest`（至少覆盖 `test_engine`、`test_readback_drain`、`test_midstroke_readback`、
  `test_perf_regression`、新增 `test_continuous_input_regression`），确认零泄漏、零
  UB；新增的后台线程（`test_continuous_input_regression.cpp`）需重点关注 ASan 对
  "线程退出前未 join"这类场景的报警，本计划已在测试设计中要求显式 `join()`。

## 6. 风险

1. **`dgcExportPNG` 契约变化影响未知消费端**：本仓库是 SDK，不含 `ui/`/`platform/`/
   `app/`；`paint-pc`/`paint-android` 是独立消费者仓库（在别处），若其存在直接依赖
   `dgcExportPNG` 隐式 drain 的调用点（本仓库内已核实 CLI/测试全部安全，见§5.3），
   需要在完成本任务后的 commit message / 交接说明中提示消费端维护者一并确认，
   或在 SDK 对外文档（如 C API 头文件注释、README）中显式标注新契约，降低跨仓库
   踩坑概率。此风险不在本任务改动范围内闭环（消费者仓库不可在本 worktree 改），
   仅做文档提示。
2. **阈值（4ms / 512 stamps）为工程估算，非实测调优**：需在执行阶段结合 host
   `ctest` 实际输出（`DGCPAIN_PERF` 编译宏下 `renderLoop`/`readback` 的 `[PERF]` 日志）
   校验是否合理；若实测偏差较大（如 4ms 内单批 GPU 提交本身就接近或超过预算），
   计划允许在执行阶段微调具体数值，只要三项验收指标仍满足即可，不视为偏离计划。
3. **新回归测试的时间类断言可能在慢速/繁忙 CI 上偏 flaky**：参考既有
   `test_perf_regression.cpp` 的宽松阈值风格（20ms vs 目标 50fps 留出安全边际），
   新测试同样预留数倍安全边际，且不使用忙等（`sleep_for`/`yield`），降低误报。
4. **并发正确性**：新测试是本仓库首次在测试代码里显式让"提交线程"与"读回线程"
   真并发运行（此前测试均为单线程顺序调用 + 短暂 `sleep_for` 模拟调度窗口）。需确认
   `Engine::submitInput`（`input_mutex_` 保护）与 `VkBackend::readback`
   （`cache_mutex_` 保护）两条路径互不冲突——按 §0 核验的现状代码结构，二者本就是
   独立锁保护的独立数据（`pending_input_` vs `cache_`），设计上不存在数据竞争；
   本仓库当前 `DGCPAIN_SANITIZE` 只含 ASan+LSan、不含 TSan，无法自动化验证数据竞争，
   若执行阶段能力允许可临时手动加 `-fsanitize=thread` 跑一次新测试作为额外证据，
   否则依赖既有代码注释里的锁设计推理作为正确性依据。
5. **人工真机验收不可在本沙箱闭环**：PC ≥120fps / Android 真机 ≥60fps 两项属人工
   记录，本 SDK 仓库沙箱历史上无 GUI/真机条件（见 D6-3 记录）；本计划仅保证 host
   自动化回归测试通过与理论设计正确，真机数据需要有对应硬件条件的人工执行者
   补齐，执行阶段应如实标注该缺口而非伪造。
