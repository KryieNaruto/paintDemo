# 实施计划 · A8-2 · Mode A 预测瞬态 wet-tip 层

> 状态：实施计划（待 build-pipeline 审阅 + 测试双门）。技术依据 = `docs/plans/ephemeral-predicted-tip-eval.md`（本任务直接引用，方案设计以它为唯一权威来源）。
> 本任务为 **SDK 侧真实改动**（不同于 A8-1 的「SDK 零 diff」）：改动落在 `core/`（engine 批次打标与分流）、`render/vulkan/`（第二 storage + merge）、`sdk_api/`（显示/导出口径分叉）。`kernels/brush` 零改动。

## 1. 目标

根治 Mode A 预测的两个架构性天花板（eval §1-2）：① `interval(16ms) < 真机显示延迟(~1.5-2帧)` 导致预测永远追不上；② 预测点永久 over-composite 进画布、沿切线外推，曲线每个 dab 沿切线突一小点（弧外毛边）。

手段：**预测点只临时显示、不永久合墨**——engine 按 `is_predicted` 把预测批次分流到一张瞬态 `tipImage`，显示 readback = 画布 + tip、导出 = 纯画布，落笔/clear/导出丢弃预测尖。预测不再永久成墨后，`interval` 可以调到 ~真机显示延迟，让预测尖真正顶到手指，根治 ①②。

## 3. 现状（代码实证，核对自 worktree）

- 数据流：`StrokePoint`（含 `is_predicted`，`core/types.h:7`）→ C API `dgcStrokeTo`/`dgcStrokeToAt` 构造 `StrokeEvent`（`isPredicted` 入 `ev.point.is_predicted`）→ `Engine::submitInput` → `inputLoop` 经 predictor `Update/Predict` 展开成 `out`（`core/engine.cpp:215-235`，预测点 `is_predicted=true`）→ 每点压成 `StrokeEvent` 进 `input_to_brush_` → `brushLoop` `kernel_->strokeTo` 产出 `StampData` 打包 `RenderBatch{stamps, count_submission}`（`core/engine.cpp:262-274`）→ `renderLoop` 攒批 flatten 后 `backend_->composite(flat)`（`core/engine.cpp:309-344`）→ `VkBackend::CompositeLocked` 全量 over 进单张常驻 `canvasImage`。
- **断点**：`is_predicted` 跨过 `strokeTo` 后不贯通——`StampData`（`core/types.h:11`）与 `RenderBatch`（`core/engine.h:105-108`）均无 `predicted` 字段 → 预测 dab 与真实 dab 一样永久合墨。
- 显示/导出共用单画布：`dgcReadbackPixels` 走 `VkBackend::readback()`（memcpy `cache_` 快照）；`dgcExportPNG` 走 `VkBackend::exportPNG()`（`ReadbackLocked` 直读 `canvasImage`，不经 `cache_`）。二者实现已天然分叉，为本任务「显示 vs 导出」分流提供了现成挂点。
- 快照刷新节流（Bug#3/P7-2）：`cache_` 只在「消费者请求（requestSnapshotRefresh，受 4ms 节流）+ drain 收尾（flushReadbackCache）」时刷新，非每 composite 无条件刷新。

## 4. 方案（落地 eval §3 推荐项）

1. **贯通 is_predicted 到批次**：`RenderBatch` 加 `bool predicted`。`brushLoop` 从 `ev.point.is_predicted` 打标。
2. **屏障语义不变**：`inputLoop` 改标 `count_submission`——最后一个**非预测点**为 true，预测点恒 false（预测事件不计数）。因 `Update()` 恒产出 ≥1 真实点（`core/engine.cpp:224-227` 注释），`composited_` 仍按「每次外部提交 +1」递增，`flush()` 语义逐位不变。
3. **后端第二 storage `tipImage`**：预测批 → 先清 tip 再 composite 到 `tipImage`（复用 `brush_composite.comp`，binding 0 改指 tipView，`kernels/brush` 与 shader 本体零改）。真实批 → 原 `canvasImage`（行为零变）。
4. **显示 vs 导出分流**：`dgcReadbackPixels` 显示路径 = canvas+tip 合并（有 tip 才付 merge）；`dgcExportPNG` = 纯 canvas（`exportPNG` 现读 `canvasImage`，天然无 tip）。`dgcClear` / `endStroke` 清 tip。
5. **interval 调大**：SDK 侧本任务只「允许」——预测不再永久成墨后，放大 `DGC_SETTING_PREDICTION_INTERVAL_MS` 不再有毛边/越界尾；实际 interval 调到 ~30ms 是消费端（paint-android）下发时机，不在本 SDK worktree 实现（见 §7 真机 handoff）。

## 6. 实施步骤

1. **批次打标（engine）**：`RenderBatch.predicted` + `inputLoop` count_submission 改标 + `brushLoop` 打标，先只打标不改分流，跑全量 ctest 确认零回归（预测 OFF 时 predicted 恒 false，行为逐位不变）。
2. **后端接口**：`IRenderBackend` 签名 + Null 桩同步；`composite(stamps, predicted=false)` 默认实参保证既有调用点（renderLoop 旧路径）编译不破。
3. **渲染线程分流**：`flushBatch` 拆 real/pred 两路；real → `composite(,false)`，pred → `composite(,true)`；clearTip 标记 → `backend->clearTip()`。
4. **VkBackend tip 层**：建 tipImage + tip descriptor set；`CompositeLocked` 按 predicted 选绑定；预测批先 `vkCmdClearColorImage(tip)` 再 dispatch（同 command buffer 一次 SubmitAndWait，不加额外 submit）；`tipHasContent_` 置位/复位。
5. **merge + 口径分叉**：新增 merge.comp + displayImage + merge 管线；`RefreshReadbackCacheLocked` 按 `tipHasContent_` 分支（有 tip → merge→cache_，无 tip → 现 canvas→cache_）；`ClearCanvasLocked` 同清 tip；`clearTip` 清 tipImage + `tipHasContent_=false`；确认 `exportPNG` 仍直读 canvasImage（恒无 tip）。
6. **C API 确认**：`dgcEndStroke` 依赖 engine 的 clearTip 标记（渲染线程 FIFO 清 tip，无跨线程竞态）；`dgcClear` 经 clearCanvas 联动；无新入参/新符号。
7. **测试**：新增 `test_wet_tip.cpp` 覆盖验收 A-D；跑既有 `test_midstroke_readback`/`test_readback_drain`/`test_determinism`/`test_continuous_input_regression`/`test_perf_regression`/`test_snapshot_refresh_throttle` 回归，确认 P7 批量/节流/确定性无回退。
8. **泄漏验证**：`DGCPAIN_SANITIZE=ON` host 构建 + 全量 ctest，ASan/LSan 零泄漏（覆盖 tip/display 资源 create/destroy + `resize` 循环）。
9. **真机 handoff**：SDK 交付 wet-tip 层 + host 测试；「曲线无毛边、笔尖跟手」由 paint-android 设 `DGC_SETTING_PREDICTION_INTERVAL_MS≈30ms` 后复测（§7）。

## 7. SDK 工程约束（必含）

### 7.1 所有权设计（RAII，无裸 new/delete）
- 新增 Vulkan 资源（tipImage/tipMemory/tipView、displayImage/displayMemory/displayView、merge pipeline/pipelineLayout/descriptorLayout）全部复用既有 `VkTopHandle<VkInstance/VkDevice,…>` / `VkDeviceHandle<VkImage/VkDeviceMemory/VkImageView/VkPipeline/…>` 最小手写 RAII 守卫（值语义、禁拷贝、可移动、`reset()`/析构幂等），声明于 `VkBackend::Impl`，按「子对象 → device → instance」逆声明序析构（`vk_backend.cpp:324-400` 现有声明序约束）。
- descriptorSet / descriptorPool 是池子句柄，随池守卫析构隐式释放，不独立 new/delete；shader module 用完即 `vkDestroyShaderModule`（与现有 `CreateCanvas`/`EnsureDevice` 的 pipeline 创建一致）。
- 本任务**不引入任何裸 new/delete**；`RenderBatch` 的 `std::vector<StampData>` 仍走 move 语义；`predicted`/`clearTip` 为值 bool 字段。

### 7.2 Pimpl 边界（对外 ABI 面经不透明句柄）
- C ABI 头 `sdk_api/dgc_paint_c_api.h` **零改动**：零新增符号、零新增公开类型；`DgcContext` 仍为不透明句柄（`struct DgcContext` 前置声明，定义在 cpp 内）。
- `IRenderBackend::composite` 签名变化、`clearTip`、tip/display/merge 全部是 **SDK 内部接口/实现**，不出现在 C ABI；消费者不可见。
- 显示/导出口径分叉是 **行为语义变化**，不是 ABI 变化（`dgcReadbackPixels`/`dgcExportPNG` 签名不变）。

### 7.3 泄漏验证方式
- `DGCPAIN_SANITIZE=ON`（host GCC/Clang，`CMakeLists.txt:37-44` 已接 ASan+LSan）构建 + 全量 ctest，重点覆盖新增 tip/display 资源在 `CreateCanvas`/`DestroyCanvas`/`resize` 循环中的释放（`DestroyCanvas` 新增 tip/display 的 reset，`reset()` 幂等）。
- 既有 `test_ownership_loop`（create/destroy 循环）继续通过，作为 ABI 层泄漏回归。

| # | 既有优化/决策 | 本方案是否会打回/绕开 | 取舍 |
|---|---|---|---|
| 1 | **P7-1 批量 composite**（每输入点 SubmitAndWait 0.73ms → 攒批一次提交） | 潜在：预测分流引入「清 tip + 预测 composite」第二条 submit。**不逐点**：预测批仍在 `flushBatch` 攒批后提交，清 tip 与预测 dabs 同 command buffer 一次 SubmitAndWait，每 flush 最多 +1 submit，仅当该 flush 含预测批（预测激活期）时发生，量级远小于 P7-1 前逐点提交 | 预测批自然小（每次 Predict 尾部几 dab）；回归测试 `test_continuous_input_regression`/`test_perf_regression` 兜底防打回。若 perf 显示 tip 清屏成瓶颈，降级为「仅清上次预测批包围盒区域」 |
| 2 | **Bug#3/P7-2 快照刷新节流**（cache_ 仅消费者请求 + drain 时刷新，防 20fps 回退） | 潜在（eval §5 点名的**最大工程风险**）：merge 若每次读回都付全画布 GPU merge 会重现 20fps 陷阱 | **merge 只在 `RefreshReadbackCacheLocked` 内、且 `tipHasContent_` 为真时付**——该函数本就被节流到 ≤4ms/次 + drain；无 tip（预测 OFF / 落笔后 / 导出）时 readback 路径与改造前逐位一致、零额外 GPU 拷贝。计划阶段给 readback/merge 预算（见 §9 R1） |
| 3 | **Mali dispatch-base 陷阱**（memory `mali-dispatch-base-gotcha`：vkCmdDispatchBase 不偏移 gl_GlobalInvocationID） | 潜在：merge.comp 全画布 dispatch 不能用 vkCmdDispatchBase | merge 用普通 `vkCmdDispatch` + gl_GlobalInvocationID 直接当像素坐标（fullscreen 无 offset）；若优化为 tip 包围盒 merge，用 push-constant offset + 普通 dispatch（与 brush_composite 的 `dispatchOffset` 同款） |
| 4 | **HOST_CACHED readback + invalidate**（memory `sdk-perf-bottlenecks` 优化 4：Mali 3.1MB memcpy 10ms→0.94ms） | 潜在：merge 输出读回不能新建 uncached 路径 | merge 输出（displayImage）读回仍走既有 HOST_CACHED readbackBuffer + `vkInvalidateMappedMemoryRanges`，复用 `RefreshReadbackCacheLocked` 的读回逻辑，不另起炉灶 |
| 5 | **A8-1 Ink 对照**（memory `a8-ink-sdk-latency-gap`：Ink 已内建「预测临时」架构） | 不冲突，可并行 | A8-2 价值 = 保留 SDK Mode A 也有低延迟手感 + 导出干净，供「不想绑 Android Ink」路径（eval §4 备选表已记）；若产品倾向交互态直接 Ink，本任务优先级可降，但已申领按计划推进 |

## 9. 风险与取舍

- **R1（最高，eval §5 点名）readback/merge 预算**：真机 Android 60fps 下，预测激活期每帧读回会触发 canvas+tip merge。merge = 1 次全画布 compute（displayImage 写）+ 1 次读回（复用 HOST_CACHED）。预算：merge dispatch 全画布 1080×720 ≈ 15k 线程、每线程 1 load + 1 store，量级 sub-ms；读回复用既有 ~1-3ms。**取舍**：merge 只在「有 tip + 被请求（节流）」时付；无 tip 时零额外成本。若真机仍超预算，降级为 CPU 双读 + tip 包围盒合成（免 merge shader，代价是 tip 区域读回），或 merge 收敛到 tip 包围盒 dispatch（R3 同款）。计划阶段已把此列为必测预算项，不静默承担。
- **R2 清 tip 的时点竞态**：若 endStroke 清 tip 在 C API 线程直调 `backend->clearTip()`，会与渲染线程的预测 composite 竞态（清早于最后一次预测 composite → tip 复现）。**取舍**：清 tip 走 engine 渲染线程 FIFO 标记（EndStroke → brushLoop 压 clearTip 批进 `brush_to_render_`），保证「所有预测批 composite 之后才清」，确定性无竞态（§6 步骤 1/3）。
- **R3 预测批计数语义**：`count_submission` 从「out 末元素」改标「最后非预测点」。若未来 predictor 管线改动导致某次提交 0 真实点（纯预测），`submitted_/composited_` 永久失配、`flush()` 卡死。**取舍**：现 `Update()` 恒产出 ≥1 真实点（`core/engine.cpp:224-227` 注释保证）；在 `inputLoop` 保留断言/兜底注释，若未来管线改动需补发 count-only 事件（与既有注释同款告警）。
- **R4 interval 调大的真机验证**：SDK 侧本任务不设 interval 默认值；真机「笔尖跟手」依赖 paint-android 把 interval 调到 ~真机显示延迟。**取舍**：interval 下发是消费端时机，本 SDK worktree 不实现（SDK 仓库约束），真机验收作为人工项 handoff 到 paint-android（A8-1 先例），host 测试为可验证替代。
- **R5 shader 双路径构建**：新增 merge.comp 需同步 host shaderc（运行时编译）与 Android glslc（构建期预编译）两条路径 + `merge_glsl.h.in`/`merge_spv.h.in`。Android 改 shader 后需重跑 cmake 重生成（memory `mali-dispatch-base-gotcha` 同款提示）。**取舍**：复用既有 brush_composite 的双路径 CMake 模板，不引入新机制。
