# 任务书 · 帧率与读回孔洞修复（线7-性能修复）

> 本任务书对应 `docs/tasks/任务线.md` 任务 **P7-1**。背景事实可回溯到：
> - `core/engine.cpp:214` —— `Engine::renderLoop()`：仅当 `flush_requested_` 被置位、或 `brush_to_render_` 队列观测为空时才 `flushBatch()`；连续输入（队列永不空且无人置位 `flush_requested_`）下可无界攒批。
> - `core/engine.cpp:77` —— `Engine::flush()`：drain 屏障，阻塞等待 `composited_ == submitted_`，仅供引擎三线程之外调用。
> - `render/vulkan/vk_backend.cpp`（`f96456e` 引入）—— `cache_`/`cache_mutex_` 读回快照缓存；`RefreshReadbackCacheLocked()` 只在 `CompositeLocked()`/`ClearCanvasLocked()` 尾部刷新；`VkBackend::readback()` 只读缓存，不触发合成、不等待渲染线程。
> - `sdk_api/dgc_paint_c_api.cpp` —— `dgcReadbackPixels`/`dgcExportPNG`（`f96456e` 后不再调用 `engine->flush()`）；`dgcEndStroke` 同样不调用 `flush()`，只提交 `EndStroke` 事件。
> - `d64c2fa`（修复孔洞，引入阻塞 `flush()`）→ PC 20fps 回归 → `f96456e`（移除阻塞 `flush()`，引入快照缓存）→ PC fps 恢复，但 Android 降至 5fps 且孔洞复现。两次修复均未跳出「readback 与渲染线程进度完全脱钩」这一根因，互为跷跷板。
> - `docs/plans/bugfix-readback-drain.md`、`docs/plans/bugfix-readback-blocks-render-thread.md` —— 两次 ad hoc 修复的历史记录与回归测试证据；其 `test_readback_drain`/`test_midstroke_readback`/`test_perf_regression` 均未能拦住本次回归，说明现有测试**不模拟真正连续不间断的输入**，需要新增。

## 背景

三个现象（PC 提速后 Android 掉到 5fps、此前 Android 提速后 PC 只有 20fps、重新抓帧孔洞依旧存在）**同源**：`dgcReadbackPixels`（含 `dgcExportPNG`）与渲染线程的批处理/flush 触发逻辑之间，要么「过度耦合」（`d64c2fa` 用阻塞 `flush()`，GUI 线程被迫等渲染线程合成完成 → 拖垮 fps），要么「完全脱钩」（`f96456e` 移除所有催促信号，纯读缓存 → 连续绘制时队列永不空，渲染线程无从触发 `flushBatch()`，攒批无界增长 → 缓存长期滞后出现孔洞，且积压批次一次性提交时的合成耗时随批变大，在 Mali 上单次 GPU 提交开销更高，表现为 Android 掉帧更严重）。

本任务修的不是「PC 和 Android 谁该牺牲」，是让 GUI 线程的读回请求能**非阻塞地**催促渲染线程「尽快找机会合批」，同时保留批量 composite 本身带来的吞吐收益。

## P7-1 · 读回请求驱动合批 + 三项验收指标

**目标**：`dgcReadbackPixels`/`dgcExportPNG` 改为对 `flush_requested_` 做**非阻塞置位**（"catch up 一次，不等待"），不再调用阻塞式 `engine->flush()`；`renderLoop()` 现有的 `flush_requested_.exchange(...)` 分支据此在连续输入下也能定期被命中，防止无界攒批。若单纯置位仍不足以在极端连续输入下限制攒批上限（例如置位后又被更快的输入抢先清空该标志前来了一大批新数据），需补一个**攒批上限**兜底（批内 stamp 数或攒批时长超阈值即无条件 flushBatch，不依赖 `flush_requested_`）。

**产出**

1. `sdk_api/dgc_paint_c_api.cpp`：`dgcReadbackPixels`/`dgcExportPNG` 读缓存前，对 engine 的 `flush_requested_` 做一次非阻塞 `store(true)`（新增或复用现有 setter，不得调用 `flush()`）。
2. `core/engine.h`/`core/engine.cpp`：评估并按需补充攒批上限兜底（批大小或攒批时长阈值，具体数值计划阶段定，需有依据如目标帧预算换算）；不得引入新的跨线程阻塞等待。
3. `core/engine.cpp::renderLoop()` 及相关注释同步更新，说明新的三条 flush 触发条件（原有两条 + 新增兜底）。
4. 新增回归测试：模拟**真正连续不间断**的输入（后台线程持续 `submitInput` 不留空闲间隙，如每 ≤1ms 提交一次，覆盖数百次点，期间队列理论上不应观测为空），验证：
   - 期间多次 `dgcReadbackPixels` 采样，画布上已提交的笔迹不出现「大范围滞后/残缺」（孔洞）；
   - 期间 GUI 线程侧（即调用 `dgcReadbackPixels` 的线程）单次调用耗时不因 flush 而产生阻塞级尖峰（对比 `d64c2fa` 之前的病理）。
5. PC 与 Android 各自的量化验收见下方指标表（人工记录 + 自动化回归测试证据）。

**验收**（对应用户提出的三项目标）

| 序号 | 目标 | 验收方式 |
|---|---|---|
| 1 | PC 帧率无上限，起码达到 120fps | `paint-pc` 关闭垂直同步（D6-3 已提供开关）+ 连续绘制压力下，`test_perf_regression`（host，lavapipe 或真实 GPU）与真机人工记录均显示平均帧时间 ≤ 8.33ms（≥120fps），且不得回退出现 d64c2fa 之前的 ~20fps 级卡顿 |
| 2 | Android 帧率无上限，起码达到 60fps | 真机（基准机型 XP-Pen MDP1221, Mali-G57 MC2, 1440×2160）连续绘制压力下人工记录平均帧率 ≥60fps，且不得低于既有 batch/dispatch 优化基线（[[sdk-perf-bottlenecks]] 记录的 ~58.2fps 起点之上，因本次目标更高） |
| 3 | 修复孔洞 | 新增的「连续不间断输入」回归测试通过（见产出 4）；真机/host 重新抓帧人工确认全程无孔洞（对照用户本次反馈的复现步骤） |

**验收共同前提**：host `ctest` 全绿，含既有 `test_readback_drain`/`test_midstroke_readback`/`test_perf_regression` 零回归；`android-arm64` preset 仍可编出 `.so`；SDK 所有权/RAII 规范不变。

**依赖理由**：B1-3（engine 三线程编排/`flush_requested_` 机制已落地）、B1-6（`dgcReadbackPixels`/`dgcExportPNG` C API 已落地）、B2-1（Vulkan 离屏渲染 + 读回已落地）、D6-3（消费端 vsync 开关，PC 无上限测帧率依赖此开关关闭垂直同步）。
